# Changelog

All notable changes to butchr. Format is [Keep a Changelog](https://keepachangelog.com/en/1.1.0/);
entries are `## [x.y.z] - YYYY-MM-DD` with subsections from: `BREAKING`, `Added`, `Changed`, `Fixed`, `Removed`.
CI refuses a merge that changes `src/` or `package.json` without a new entry here.

## Versioning
- **MAJOR** — a restructuring/rewrite that breaks a lot, requiring reimplementation. Requires a `### BREAKING` section.
- **MINOR** — a new feature, or a change to an existing feature that breaks just that feature.
- **PATCH** — a fix or correction needing no consumer code changes, or very minor ones.

## [0.15.0] - 2026-08-29
### Changed
- **Epic agents run on `opus`, not `fable`.** The human's Fable capacity is exhausted fleet-wide, so `modelFor()` now spawns Epics on `opus` (Stories were already `opus`, Tasks stay `sonnet`). Running agents are unaffected — `--model` is deliberately excluded from the argv staleness check, so there is no respawn churn; the six live epic panes were switched by hand with `/model opus`. Revert the map when Fable capacity returns.

## [0.14.0] - 2026-08-29
### Added
- **A pr:* label transition now wakes the ticket's own agent even though the daemon wrote it — closing the deadlock measured on KAN-691 (a 2.5h stall on an already-approved PR, 2026-08-27) and again on 2026-08-29 07:36–07:5xZ.** Board label sync already observed the review outcome within one poll (`[labels] KAN-x +pr:approved -pr:open`), but the notify path swallowed that exact write on purpose, in two independent places (0.10.1, KAN-790): the own-write ledger (writer `"daemon"`) suppresses the ping for every watcher of a bumped ticket, and `isDaemonLabelOnlyDiff` treats a diff confined to `agent:*`/`pr:*` labels as a cross-daemon echo when no new comment appeared. Both exist to stop `agent:*` flicker from waking agents; both also happened to swallow the one label flip an author explicitly waits on. A new pure rule, `prTransition` (`src/jira-watch/diff.ts`), recognizes when a ticket's `pr:*` label differs from the previous poll and there IS one after (`none→open`, `open→approved`, `open→changes-requested`, `changes-requested→approved`, `approved→merged`, …); a pure removal (`pr:x` → no `pr:*` label — a PR closed unmerged, or the KAN-814 restart artefact) is deliberately never a transition and never wakes anyone. In `src/daemon/loop.ts`, a transition on a ticket's OWN agent is now delivered past both suppressions entirely — it's checked before either is consulted. This intentionally skips `crossDaemonSuppressed` for that key on that poll, so its comment-cursor bookkeeping doesn't advance; that's safe because the cursor is only ever compared for EQUALITY against a monotonically-growing newest-comment id, so a stale cursor can only bias a later comparison toward delivering, never toward a wrongful suppression.
- **Watchers of a ticket via the Implements chain (a story hearing its task's `pr:*`, an epic hearing its story's) deliberately keep today's suppressed behaviour.** This is a scope decision, not an oversight: the boss already hears the outcome through the author's next comment once it acts on the wake-up above; only the ticket's own agent needed the past-suppression exemption.
- **`pr:changes-requested` now exists.** `isApproved()` (`src/labels/pr.ts`) used to fold an outstanding `CHANGES_REQUESTED` into "open", making a changes-requested review invisible to the author — the same deadlock, opposite sign. `PrState` (`src/labels/plan.ts`) gains `"changes-requested"`; a new sibling `reviewState()` computes the three-way outcome (an outstanding `CHANGES_REQUESTED` beats any `APPROVED`; otherwise `APPROVED` if any; otherwise `open`) from the same latest-vote map, and `PrTracker.stateFor` now uses it. `isApproved()` itself is unchanged, for its existing callers.
- **The nudge names the transition.** `LoopDeps.notify` grows an optional third argument naming why — currently only `{ pr: { from, to } }` for a pr:* transition; every other nudge passes it as `undefined` and keeps its existing wording. The ticket's own agent gets, e.g., `[butchr] KAN-x: your PR's review state changed pr:open → pr:approved. Verify with gh pr view <n> --json reviewDecision,headRefOid and act: approved → merge your own PR; changes-requested → read the review, fix, push, ask for a re-review; merged → do your post-merge duties.` The `[notify]` log line names it too: `[notify] KAN-x ← KAN-x (pr:open→pr:approved): channel pushed, prompt delivered`.

## [0.13.3] - 2026-08-29
### Fixed
- **pr:* discovery now requires an EXACT head-ref match, not a GitHub search prefix hit.** Measured on KAN-790, 2026-08-29 00:00–00:21 PDT (recorded by the KAN-752 epic agent, KAN-790 comment 15461): `discover()` in `src/labels/pr.ts` searched `is:pr is:open head:<key> org:<org>` and cached `body.items[0]` without ever checking the hit's head ref against the key — GitHub's `head:` qualifier matches by PREFIX. KAN-790 had no PR on head `KAN-790`; the search instead returned its TASK's PR #66 (head `KAN-790-ownwrites`, base `KAN-790`), so the STORY ticket displayed the TASK PR's lifecycle: pr:open (00:00) → pr:approved (00:07) → pr:merged (00:08), all wrong for a ticket that owned none of it. `discover()` now confirms every search hit against the pull payload itself (`GET /repos/{owner}/{repo}/pulls/{n}` → `head.ref`, which the search result doesn't even carry) before returning it; a prefix-colliding hit is rejected without caching anything, so a later exact-match PR on the same key is still discoverable on a subsequent poll.
- **pr:merged is now durable across a daemon restart.** At the same incident's 00:10:04 restart, `PrTracker`'s in-memory `merged` Set was lost and discovery searched OPEN PRs only, so the cold cache found nothing for KAN-790's actually-merged PR; label sync then removed pr:merged from the ticket at 00:10:21 — and a later re-add would have been an equally spurious event. On a cold cache, `PrTracker.stateFor()` now falls back to also searching `is:pr is:merged head:<key>` (behind the same exact-head-ref filter) when the open search finds nothing. This API-based rediscovery was chosen over treating an existing pr:merged label as sticky: it's re-verified against GitHub every time, rather than re-asserting the daemon's own prior output — the latter is exactly the failure shape defect 1 produced, with no way to self-correct. Once merged is confirmed, the key is still terminal — no further requests are ever issued for it.

## [0.13.2] - 2026-08-29
### Changed
- **Reviewers now post a machine-greppable `[review] <verdict> <pr> @ <sha>` line on the author's ticket after every formal GitHub review; authors verify `reviewDecision` + `headRefOid` before merging.** A formal GitHub review (Approve or Request changes) is a GitHub event Jira never sees, and `pr:*` label discovery — the other wake path — is disabled on any daemon without `GITHUB_TOKEN_FILE`/`BUTCHR_GITHUB_ORGS` and was shown to prefix-match the wrong ticket in KAN-814, so this Jira comment is belt-and-braces: it survives the label mechanism being off or wrong. `briefs/epic.md` and `briefs/story.md` now instruct the reviewer to post exactly one `[review] APPROVED <pr-url> @ <full sha> — <one line>` or `[review] CHANGES_REQUESTED …` comment immediately after every formal review, with the sha read from `gh pr view <n> --json headRefOid` at review time (never the author's claim) — one line per review, a re-review gets its own line. `briefs/story.md` and `briefs/task.md` now instruct the author to check both `reviewDecision` APPROVED and `headRefOid` matching `git rev-parse HEAD` (via `gh pr view <n> --json reviewDecision,headRefOid`) before merging, so a stale `[review] APPROVED` for a since-superseded sha reads as "ask for a re-review," not "merge." `docs/agent-model.md` updated to match. No `src/` changes — briefs ship in `dist` via `src/agents/workspace.ts`'s text import, so this still needs a version to name.

## [0.13.1] - 2026-08-29
### Fixed
- **Staleness no longer scans /proc by cwd — it reads the pane's own foreground argv.** Measured live on the deployed daemon (butchr 0.9.2, brooswit :7717, 2026-08-29 00:14 PDT): during KAN-811's end-to-end verification, a stray unnamed pane's bare `claude --resume 8e457d9f…` (pid 236403) ended up sharing a cwd with the daemon's own healthy named pane (`butchr-kan-811`, full spawn argv, a higher pid). `HerdrHerd.staleIssues()` used to walk `/proc`, collect every process at that cwd whose `basename(argv[0]) == "claude"`, and — with both candidates' parents non-claude — `selectClaudeProcess()` (`src/agents/proctable.ts`) picked `candidates[0]`, the LOWEST pid: the stray. Verdict: STALE. The daemon then closed the HEALTHY pane and respawned it on every 15s poll until the stray was killed by hand — two `[reconcile] KAN-811 respawned: argv lacks …` lines and two `[butchr:respawn]` ticket comments, each one killing a good agent. `staleIssues()` now calls herdr's `pane.process_info` for each managed agent's OWN pane and reads the foreground process it reports directly — there is no cwd to share and no pid ordering to get wrong, so a stray process anywhere else is structurally invisible to the verdict. `foreground_processes` and a matched process's `argv` are both optional/nullable on the wire; every gap (the call throws, no `process_info`, no foreground processes, no claude among them, or a matched claude with no `argv`) is UNKNOWN, never stale, exactly as `proctable.ts`'s /proc gaps were — and each is now a named test (`test/unit/herd.test.ts`). `src/agents/proctable.ts` and its tests are deleted; `HerdrHerd`'s injectable `processSource` seam goes with it — tests supply a fake `herdr.pane.processInfo` on the fake client instead.
- **A respawn storm guard, independent of the above and required even though the argv fix already closes the measured cause.** `reconcileNow()` never respawns the same issue on two consecutive polls: a new `RespawnGuard` (`src/daemon/loop.ts`), threaded explicitly through `ReconcileOptions` (one instance created in `startLoop` and kept alive for the loop's lifetime — no module-level mutable state), opens a 5-poll suppression window on every respawn. A repeat staleness verdict for the same issue inside that window is suppressed outright (no stop, no spawn) and logged as `WARNING: [reconcile] <KEY> respawned again within 5 polls — suppressing further respawns until poll <N>`; the `[butchr:respawn]` ticket notice fires at most once per window, exactly at the respawn that opened it. A direct `reconcileNow()` call that omits `guard` gets a fresh instance every time, so existing callers and tests are unaffected.

## [0.13.0] - 2026-08-29
### Added
- **Confluence tooling round two (KAN-812): `parentId` on create, `confluence_update_page`, `confluence_search_pages`, and an explicit empty-body signal on `confluence_get_page`.** The captain's-log convention (KAN-754) shipped with a create-only toolset, which is why the convention itself said "one page per entry, never edited" and "no search tool available to agents" — those constraints were baked into the page's own text, not a deliberate design. This closes the gap:
  - `confluence_create_page` takes an optional `parentId` so a page can be filed under a chosen parent instead of the space's default; omitted, behavior is unchanged (pages still land under the SD homepage by Confluence's own default).
  - `confluence_update_page` is new: a full-body replace that handles Confluence's optimistic locking INTERNALLY (reads the page's current version, PUTs version.number + 1) — callers never hand-roll a version number. Entries stay append-only by convention; this tool exists for maintaining standing pages like the convention page itself.
  - `confluence_search_pages` is new: `titleContains` (CQL built for you, quotes escaped) and/or a raw `cql` string, optionally scoped by `spaceKey` (or `spaceId`, resolved to a key via a spaces lookup — CQL's `space` field only accepts a key) — lets an agent find its own or a ticket's prior entries without the Confluence UI. Reaches Confluence's CQL search over a second (v1) client, since confluence.js 3.2.0's v2 client has no search endpoint at all.
  - `confluence_get_page`'s result now adds `bodyRequested: true` and `bodyLength` alongside the existing fields, so a caller can tell a genuinely empty body (`bodyLength: 0`) apart from a body the API never returned — indistinguishable while the bodyFormat bug (fixed 0.5.18) was live.
  - Every new/changed wrapper is commented with the exact confluence.js 3.2.0 SDK shape it depends on (which top-level parameter keys the library actually forwards vs. silently drops) — the same top-level-key-stripping gotcha `createPage`/`getPage` already documented, now confirmed against the SDK's own `.d.ts`/`.js` for `updatePage` and `searchByCQL` too.
  - The convention page's own text (`https://wroosbit.atlassian.net/wiki/spaces/SD/pages/10715137`) needs a matching rewrite (cadence emphasis, a raw-XHTML warning near its example, the nesting/toolset corrections above) — drafted at `docs/captains-log-convention.storage.xhtml`, applied post-deploy via the new `confluence_update_page`.

## [0.12.0] - 2026-08-29
### Added
- **A kickoff prompt refused at the Claude session limit is no longer stranded forever.** Measured live on the fleet: a freshly spawned agent's kickoff landed while the account was at its session limit, the pane printed "You've hit your session limit · resets 9:50pm" and refused it, and nothing ever re-sent it — herdr's `agent_status` read `done` and the board label read `agent:idle`, indistinguishable from a finished agent, for over an hour with three tasks waiting on it. `HerdrHerd.spawn()` now verifies its kickoff actually started a turn (reusing `nudge()`'s wait/verify pattern via a new sibling `KICKOFF_VERIFY_MS`) and, if it was swallowed, recovers the same way `nudge()` does — UNLESS the pane shows a session-limit refusal, in which case re-sending is skipped (the refusal is a property of the CLI session, not the composer, so a re-send is unproven and indistinguishable from a repeat failure). A new level-triggered poller (`src/agents/session-limit-watch.ts`) instead closes the pane once past the printed reset time plus a small margin, letting the existing reconciler respawn the agent with a fresh kickoff — the exact remedy verified by hand on the incident night. Nothing is persisted: a daemon restart re-reads the same pane text and reaches the same decision. The refusal recogniser (`src/agents/session-limit.ts`) is anchored to the pane's trailing rendered content, never a phrase merely quoted in scrollback, a rendered ticket/comment body, or an agent's own narration — this exact phrase sits verbatim in the tickets that specified this feature, so an unanchored match would have closed a healthy agent's pane the moment it read them.
- **`agent:stalled` makes "idle since spawn, never spoke" visible.** An active ticket whose agent has been idle/done continuously since the daemon first observed it running, with zero comments from the daemon's own account, for at least `BUTCHR_STALLED_MINUTES` (default 10) now gets a log line and the new `agent:stalled` label instead of looking identical to a finished agent's `agent:idle`. Routed through the existing `AgentLabelStabilizer` (same 2-poll flip damping as every other `agent:*` value) with precedence over `idle`. The one Jira comment fetch this adds is gated behind the cheap in-memory precondition check, so a normal poll over the active set costs nothing extra — the qualifying set is usually empty. An agent that has ever been observed working, or that has commented at all, is never labelled stalled.
- New `BUTCHR_STALLED_MINUTES` config knob (default 10).

## [0.11.0] - 2026-08-29
### Added
- **A boss can now adopt an existing ticket with tools alone: `jira_assign`.** Re-linking (`jira_link_issues`, since 0.6.0) and re-prioritizing (`jira_set_priority`, 0.7.0) an orphan ticket already worked, but nothing could change an EXISTING issue's assignee — the board reconciler never staffs an unassigned ticket, so four adopted stories sat unstaffable on 2026-08-28 until the operator assigned them by hand in the Jira UI (agent panes carry no ATLASSIAN_* credentials to hit the REST API directly). `jira_assign(key, assignee)` closes that hole: `assignee` is either an Atlassian accountId or a role name ("story"/"task", case-insensitive) resolved through the same role→accountId mapping `jira_create_issue` staffs by (0.10.0). Unlike `jira_create_issue`, this is a pure update — it writes only the assignee field, nothing else about the ticket. A role name and a bare accountId aren't cleanly distinguishable by shape alone, so rather than invent a fragile "looks like an accountId" pattern, only one case is refused: a role name whose accountId is unset on this daemon (naming the env var, `BUTCHR_ASSIGNEE_STORY`/`BUTCHR_ASSIGNEE_TASK`) — a plain wrong accountId still fails at Jira, same as it always has. `briefs/story.md` and `briefs/epic.md` no longer instruct a Task to file with a Story `parent` (Jira refuses it here — Story and Task share a hierarchy level); both now point at `implements` for that link and mention `jira_assign` as the way to adopt an orphan. Like every other mutating tool, `jira_assign` feeds the own-write ledger (0.10.1), so a boss that re-staffs a ticket isn't then notified about its own write.

## [0.10.1] - 2026-08-29
### Fixed
- **An agent no longer gets pinged about writes it (or the daemon) just made.** A new own-write ledger (`src/jira-watch/own-writes.ts`) records the `updated` value the daemon reads back after every agent tool write (comment, transition, priority, link, create) and every label-sync write, keyed by writer. The notify loop now suppresses a ping only on an EXACT `updated` match against a recorded write — anything newer (a foreign write landing in the same poll window) still delivers, by construction rather than by heuristic. An agent's own write suppresses the ping to that agent alone; every other watcher (its boss, through the Implements chain) still hears it — this is how a task's "merged, over to you" comment reaches its story. The daemon's own label-sync writes suppress the ping for every watcher of the bumped ticket, including its own agent. The old status/summary-equality proxy (`isOwnLabelBump`, and `Snapshot.labelWrites`) is removed in favor of this one mechanism.
- **A cross-daemon label echo (one daemon's label write pinging a boss on a different daemon) is also suppressed**, via a content rule rather than a second ledger: when a poll's diff for a ticket is confined to daemon-namespaced labels (`agent:*`, `pr:*`) with status and summary unchanged, it is treated as a daemon write from any daemon. Because a same-poll foreign comment is invisible to the status/summary/updated fields alone, that branch makes one extra `comments()` call and delivers anyway if the newest comment id differs from the last one this daemon saw for that ticket — an unknown baseline (first sighting, or after a restart) always delivers, never suppresses.
- **Task→story delivery after the Implements-only routing release (KAN-769) is now pinned by tests** (`test/unit/routes.test.ts`, `test/unit/loop.test.ts`): a task that implements a story is watched by the story and never routed to the epic, and an implementer's change reaches its boss and only its boss.

## [0.10.0] - 2026-08-29
### Added
- **`jira_create_issue` now staffs and links, instead of leaving it to the caller.** On 2026-08-28 four defect stories were filed by agents as `create Story under (none)`, with no assignee and no Implements link — the board reconciler never staffs an unassigned ticket, and (since Implements is now the only routing link, 0.8.0) a link-less ticket's events route nowhere. Orphans like that are no longer possible: a Story or a Task is now ASSIGNED BY ROLE from its issuetype, regardless of `parent`, using a new role→accountId mapping on the daemon — an explicit `assignee` argument still overrides. A Story or a Task also now REQUIRES a home: a new optional `implements` argument (an issue key) is resolved ahead of `parent` for the Implements link the tool itself creates after a successful create; omitting both refuses the call. Jira refuses a Story as a Task's `parent` in this project, so for a Task `implements` is the only real route — its refusal message says so plainly, distinct from a Story's (which can genuinely parent to an Epic). Pass `implements: "none"` (case-insensitive) to file a deliberate, audited orphan — briefs already tell agents to file out-of-scope findings outside their epic; those tickets are still staffed by role, just left unlinked. The create result now always carries the new `key` plus the link outcome (`implements: { ok, to, error? }`) — a link failure is reported, never hidden behind a "failed" create that would tempt a retry into a duplicate ticket.
- **Operator action required before deploying: set `BUTCHR_ASSIGNEE_STORY` and `BUTCHR_ASSIGNEE_TASK` (Atlassian accountIds) on EVERY daemon.** After this ships, a daemon with either unset REFUSES to create a Story/Task of that role unless the caller passes an explicit `assignee` — the error names the missing env var. See `.env.example` for the production mapping. Epics are unaffected. The resolved mapping (and which roles, if any, are unset) is now printed in the daemon's one-line startup summary, so a misconfiguration is visible at boot.

### Fixed
- **`jira_set_priority` could reject a successful call (KAN-803).** Same shape as KAN-764: Jira's `editIssue` answers a successful update with an empty body, so the op resolved `undefined` and the MCP result was invalid on the happy path. The `undefined`-means-success substitution from `jira_link_issues` is now a small shared helper used by every write tool (`jira_link_issues`, the new create-then-link path, and `jira_set_priority`), so the two call sites can't drift again.


## [0.9.2] - 2026-08-29
### Fixed
- **`bun run check` no longer depends on the pane's `node`.** `typecheck` ran `tsc` through a package.json bare-script invocation, which resolves `node_modules/.bin/tsc`'s shebang against whatever `node` the pane's PATH happens to give — on panes where that resolves to node v12, tsc's own `??` syntax fails to parse (`SyntaxError: Unexpected token '?'`) even though the code being checked is fine. `typecheck` now runs `bun --bun x tsc -p tsconfig.json --noEmit`, which forces the bun runtime instead of honoring the shebang. `check` also now prints a one-line `scripts/preflight.ts` diagnostic (bun/node/tsc versions in use) before the gate runs, so a pasted gate result is self-describing; it degrades to `node: not found` rather than failing when `node` is absent, and never fails the gate on its own. The diagnostic is emitted only when the script is run directly (`import.meta.main`), so importing it — as the generated load test does — stays side-effect-free.

## [0.9.1] - 2026-08-29
### Fixed
- **Label writes never silently 403 anymore.** `updateLabels` PUTs `notifyUsers=false` so board label sync doesn't spam watchers — but Jira Cloud 403s the WHOLE write for any account lacking Administer Jira/Projects on the ticket's project, and nothing said so. The daemon now preflights `ADMINISTER_PROJECTS`/`ADMINISTER` per project on first sight (cached for the run) and logs the verdict once, naming the account, project, and remedy. An account lacking the role now gets quiet label sync gracefully degraded to notifying writes (watchers get a Jira notification per label change, but labels always land) instead of every write failing. If a write still 403s at runtime, that project flips to notifying writes for the rest of the run and the write is retried so labels land — logged once, never a per-poll spin. README documents the Administrator-project-role requirement.

## [0.9.0] - 2026-08-28
### Added
- **The daemon detects an agent whose process argv lacks butchr's spawn flags and respawns it.** When the herdr server restarts (session restart, laptop reboot, herdr upgrade), it restores each pane as a bare `claude --resume <session-id>` — butchr's `--permission-mode bypassPermissions`, `--mcp-config <workspace>/mcp.json`, and `--dangerously-load-development-channels server:butchr` are lost. The reconciler used to match a pane by name only and treat it as running, so it was never touched (measured: four epics ran flag-less for 70 minutes; the two that spoke up hit a default-mode permission prompt with nobody to answer it). `HerdrHerd.spawn()` now builds its argv through one exported `spawnArgs(spec, dir)` (`src/agents/argv.ts`), and every poll `Herd.staleIssues()` compares each running agent's REAL process argv — read by walking `/proc` (`src/agents/proctable.ts`), matched by cwd and `basename(argv[0]) === "claude"`, skipping the Bash tool/MCP server children that share the same cwd and any process this user can't read (EACCES) — against that same expected argv (`--model` and the kickoff positional are startup-only and excluded, so a `modelFor()` change on deploy can't churn the fleet). A process that can't be found at all is left alone — unknown is not stale, or a fresh respawn would itself get respawned every poll (the leaked-workspace shape from 0.5.6). A stale agent is stopped and spawned fresh (`planReconcile` gained a `respawn` output alongside `spawn`/`stop`; `reconcileNow` performs the stop-then-spawn and invokes an `onRespawn` callback — Jira knowledge stays out of `Herd`), the daemon logs one `[reconcile]` line naming every flag it found missing, and posts one `[butchr:respawn]` comment on the ticket pointing the fresh session back at it (a failed post is logged, never blocks the respawn). No persisted session-id ledger is needed: a process carrying this daemon's exact `--mcp-config` path for an issue was by construction spawned by butchr.

## [0.8.0] - 2026-08-28
### Removed
- **Relates-link routing (deprecated in 0.6.0).** The one-release deprecation bridge that let a "Relates" link route notifications alongside "Implements" is gone — `watchedKeys()` now routes only an outward-end "Implements" link, exactly as documented. `jira_link_issues` still accepts an explicit `type` for other link kinds (Blocks, Relates, …); it just no longer routes them.

### Fixed
- **A boss staffed by the same daemon as its implementer heard nothing.** `related()`'s active-set filter used to skip any other-end key that was itself already in the daemon's active set, on the assumption that "active ends are already watched" — true while the Jira parent field routed notifications (release A removed that), but false once routing moved entirely onto the Implements link: a boss (story/epic) and its implementer (task/story) staffed by the SAME daemon credential are unrelated as far as the assigned-issues loop is concerned, so the boss's own agent never saw the implementer's change go by. The active-end skip is dropped; the loop's existing `sent` dedupe (`${issue}|${about}`) still keeps the implementer's own agent from being notified about itself twice.

## [0.7.0] - 2026-08-28
### Added
- **Priority flows down the command chain.** `jira_create_issue` gains an optional `priority` (a Jira priority name, passed through verbatim — omitted, Jira's site default applies) so a boss sets a child's priority at filing, and a new `jira_set_priority` tool lets a boss re-prioritize its children as reality shifts. Priority is command metadata, not staffing: no daemon behavior reads it, only assignee + status do. `briefs/epic.md` and `briefs/story.md` now carry the duty to set and maintain their children's priority (and never their own); `briefs/task.md` notes a task's priority is set by its story.

## [0.6.1] - 2026-08-28
### Fixed
- **Escalation stability, finished.** v0.5.16 was the tourniquet: a per-pane rate cap and a fix so a refused answer re-earns the debounce instead of re-escalating instantly. Neither closed the actual hole. Measured on a live daemon after v0.5.16 shipped: three MORE escalations landed on one ticket, each quoting a WORKING agent's own pane text — the fingerprint was stable across the whole 2-poll debounce window each time, so the debounce fix could not have stopped them. The parser was accepting them as real dialogs. Root cause, confirmed against real captures: `parsePrompt` had no positional discipline on EITHER branch — ANY two `N. label` lines (numbered) or a stray `❯`/footer-shaped line (un-numbered) anywhere in a pane's scrollback could parse as a menu, including a pane that merely quotes option or footer text out of its own Jira ticket (a self-sustaining loop: butchr escalates, the comment quotes the dialog, the agent reads its ticket, the pane now contains that same text, butchr escalates again — nine comments on one ticket in six minutes was the original incident this whole fix traces back to). `parsePrompt` now requires two independent structural properties before accepting either menu shape: the confirm/select footer must immediately follow the last option (no unrelated content between them, anchored to the START of the line and to the LAST such line in the pane — a real dialog is always the last thing rendered), and exactly one option line must carry the `❯` cursor. A genuine dialog satisfies both; scrollback prose that merely mentions options or a footer satisfies at most one. Three secondary gaps closed alongside it: a blocked pane whose text fails to parse now logs once (deduplicated by content, not once per 5-second poll) instead of vanishing silently — the hardened parser rejects more panes, and a real dialog wrongly rejected must be visible, not stuck; a poll on which a pane is reported not-blocked (or reported blocked with unparseable text) now correctly resets that pane's debounce, closing a flicker case where a pane blinking blocked/idle/blocked could still reach two "consecutive" observations that were never actually consecutive; and that same flicker reset no longer discards an ALREADY-escalated pane's state — previously it silently dropped the 15-minute follow-up entirely on any pane whose herd status flickers (the normal case, not the exception) and re-adopted its own escalation comment on every flicker, which is what let the rate-cap budget below double-count. Also finished: a stale `ANSWER` comment is now refused at most once ever per pane (previously the refused comment's id was forgotten on every debounce reset and could be re-read and re-refused indefinitely on a pane that stayed blocked); the rate cap is now keyed by pane rather than by issue, since a pane can outlive its issue key in the herd; and an escalation adopted after a daemon restart (or re-discovered after its pane's dialog changed and changed back) now correctly counts against that pane's hourly budget exactly once, instead of granting a free refill or double-counting.

### Added

A one-time startup sweep also clears `agent:*` left behind by a ticket that went inactive while the daemon was down, since the 15s poll only ever sees active tickets and the reconciler's own tracking is in-memory.

## [0.5.13] - 2026-08-28
### Added
- **Blocked-prompt escalation: an unanswerable dialog becomes a ticket comment, not a stuck agent.** Before this, `chooseStartupAnswer` returning null just left the dialog exposed with nothing watching it — a human had to notice the pane sitting idle. Now, once a dialog stays blocked for 2 poll cycles (~10s) with no recognized auto-answer, butchr posts ONE `[butchr:blocked]` comment on the blocked agent's OWN ticket: the question, the numbered options, and a fingerprint (a self-contained FNV-1a hash of question+options — independent of which option is highlighted). Posting on the child's ticket is what routes it: the existing story/epic watcher wakes the reviewer automatically, no new transport. The comment is built ONLY from the question and options — never the surrounding pane, which may hold command output or secrets.
- **`ANSWER <n> <fingerprint>` / `ANSWER TEXT <text> <fingerprint>` directives answer it back.** The daemon watches comments only on issues that are currently blocked and already escalated (never the 15s Jira loop). Before delivering a single keystroke it re-reads the live pane and re-parses the dialog, and only acts if the fingerprint still matches — a stale answer aimed at a dialog that has since moved on is refused, logged, and the daemon re-escalates the CURRENT dialog instead of guessing. `ANSWER TEXT` selects a free-text/chat option (chosen by content, never by position) and sends the text, then Enter. If no reply arrives within 15 minutes, one follow-up comment nudges whoever is watching; the daemon never escalates further than that — the ticket hierarchy does. Comment reading (`AtlassianClient.comments`, with an ADF-to-plain-text flattener) and posting (reusing the already-proven `realAtlassian().addComment`) are both new; the daemon survives a restart by recognizing its own prior escalation comment instead of double-posting. `briefs/story.md` and `briefs/epic.md` now tell reviewers how to answer or refuse.
- **Redaction is enforced at the escalation boundary, not merely intended.** The comment is assembled only from the question and options, but `question` itself absorbed every preceding pane line, so terminal output above the dialog (a `cat .env`, a prior command's stdout) would have ridden along into a durable, project-readable Jira comment. Two layers, both required: `parsePrompt` now bounds the question to the 6 lines directly above the menu in BOTH its numbered and un-numbered branches (one shared `QUESTION_TAIL` constant, so they cannot drift apart), and a new exported `redact()` masks credential shapes in the question and every option — `KEY=VALUE`/`KEY: VALUE` secrets, provider tokens (`ghp_…`, `sk-…`, `xox…`, `AKIA…`), URL-embedded credentials, `Authorization: Bearer/Basic`, and long opaque blobs — replacing the value only and keeping the shape legible (`AWS_SECRET_ACCESS_KEY=[redacted]`). The question is capped at 600 characters. Filesystem paths and ordinary prose are left untouched, and the fingerprint is still computed from the UNREDACTED prompt so it keeps matching the live pane on both sides of the verification guard.
- **Review fixes (KAN-732 review of PR #27), before this ever shipped:** an answer is now consumed exactly once — a directive's comment id is recorded before its keystrokes are sent, so a dialog that stays blocked after delivery (a swallowed keystroke, a slow re-render) no longer walks debounce→escalate→adopt→re-deliver forever. `onBlocked` now guards against overlapping polls (`watchBlocked`/`watchPrompts` fire without awaiting the previous call), closing a window where two in-flight polls could both post the escalation comment. The self-reference guard now only rejects a comment that *starts with* the marker, not one that merely quotes it while replying — and a comment skipped for genuinely starting with the marker is now logged instead of silently dropped. `freeTextOption` no longer matches a bare "write", which falsely classified permission-grant options like "read and write files here" as the free-text entry.
