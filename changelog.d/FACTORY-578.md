### Fixed

- **A Codex managed session's `permissionMode` was validated and stored but never forwarded to the launched process — every mode, and absent, produced byte-identical Codex argv (FACTORY-576/FACTORY-577/FACTORY-578).** `agentLaunchConfig`'s `codex` branch (`src/agents/argv.ts`) never read `spec.permissionMode` at all; only its Claude branch did. `permissionMode` now maps onto a Codex launch's `bypassApprovalsAndSandbox`: an explicit `"bypassPermissions"` yields the unattended bypass flag; any other explicit mode (`"default"`/`"acceptEdits"`/`"plan"`/`"auto"`) yields manual approval; absent falls through to today's pre-existing default (the `jira-project` rule-engine default, or Codex's own `lizardMode` signal). An explicit `permissionMode` now wins over both of those, in both directions.

  **Operator-visible behaviour change, read before upgrading:** `SessionDefinition.permissionMode` is a required field on every managed-session manifest, so the "absent" fallback above can never apply to a managed session — every `vendor: "codex"` managed session always carries an explicit mode. This means **any existing Codex managed-session definition that does not literally say `permissionMode: "bypassPermissions"` flips from running unattended (bypass) to blocking on manual approval prompts the moment this ships.** Audit your Codex session-definition manifests before upgrading if you rely on the old (silently-ignored) unattended behaviour. This is the intended meaning of "honor the definition's permission mode", not a regression, but it is a real change in running behaviour, not merely a bugfix that only affects code paths nobody depended on.

  Respawn-on-definition-change is proven for the manual -> `bypassPermissions` direction only: the underlying `checkManagedAgentArgv` (`@brooswit/drovr`) bypass-flag comparison is one-directional (gated entirely behind `expected.includes(bypassFlag)`), so a definition edited from `bypassPermissions` back to a manual mode is not detected as stale and does not respawn its already-running pane — a pre-existing drovr limitation, unrelated to this fix, filed separately as FACTORY-579.

  No CI regression: the repo's Ubuntu `check` job (typecheck, unit+load tests, coverage gate, build) is green. A `windows` CI job also exists at this commit (`windows-latest`, every step `continue-on-error: true`) but is non-blocking by design, so it gates nothing either way.
