### Added
- **`/dashboard`'s row set is now every ticket this daemon WANTS an agent for, not only the ones it HAS one for (BUTCHR-288/BUTCHR-332).** A ticket withheld by the fleet-wide admission cap (BUTCHR-284) sits In Progress with no agent, so an agent-row-only dashboard had *no row for it at all* — "I checked and there is nothing there" and "there is something there I am not showing you" rendered identically, which is the exact distinction this endpoint exists to preserve, arriving through the row SET rather than through a field. `DashboardRow` gains a second union member, `WithheldDashboardRow` (`kind: "withheld"`), carrying `resourceKey`, `tier` (via the same `buildTier` as an agent row), the `source` whose census produced it, a `waiting: StatusFloor`, and its observing poll's own `confirmedAt`. `AgentDashboardRow` is unchanged, so this is the additive union member BUTCHR-269's own doc comment left room for rather than a redefinition.
- **A third absence state: NOT APPLICABLE by construction, distinct from "could not check".** A withheld row has no `pane` and no `agentStatus` because there is no agent to have one — nothing failed and nothing was unavailable. Those two fields are structurally absent from the variant (never `null`, never `""`, never the real `agentStatus` value `"unknown"`), and the row additionally carries an explicit `agentFields: {applicable: false, reason}` marker whose shape is deliberately NOT `IssuetypeField`'s `{checked, declinedAt}` — structural absence alone is necessary but not sufficient for a JSON consumer, who otherwise cannot tell "absent because not applicable" from "absent because the producer broke". Folding the two vocabularies together would render a perfectly healthy queued ticket as a monitoring failure (BUTCHR-116's finding, one level out) and a green suite would not notice. A single row can carry both at once — an unknown `tier.issuetype` as `{checked:false, declinedAt}` beside `agentFields: {applicable:false}` — and they stay visibly different.
- **A per-source admission census, so a failed census is a could-not-check rather than an ordinary busy fleet.** `AdmissionController.admit()` gains an optional third `source` parameter (defaulted, so `ReconcileOptions.admission`'s two-argument signature and every existing caller are untouched), and a new synchronous `census()` reports one bucket per DECLARED source: `{checked: true, confirmedAt, withheld}`, or `{checked: false, declinedAt, reason}` with reason `census-threw`, `census-untrusted` (the BUTCHR-282-shaped implausible-zero guard) or `never-reported`. `DashboardResponse` gains an additive `admission: {cap, residency, sources: [{source, census}]}` on both variants, reusing the same `deps.cap`/`lastTrusted` internals `/health`'s `AdmissionSnapshot` already reads rather than a second source.
- Per-source is load-bearing, not cosmetic: ONE controller instance is shared by the issue and project loops, whose candidate sets are disjoint, and `admit()` overwrites `lastWithheld` on every call — so a single collapsed slot would have had the project tier's ~5-minute poll blank the issue tier's withheld rows roughly twenty times per project poll, silently, with no failing test (the same hazard `admission.ts`'s own §B1 already names for the wait ledger). A decline in one source now leaves every other source's rows and census untouched, and that source's prior rows carry forward byte-identical, keeping their own older `confirmedAt`.
- Every declared source is seeded `never-reported` **at construction**, via a `sources` constructor dependency, rather than created lazily as calls arrive. A rule quantified over the sources that *have* reported is vacuously true when none has, so a fresh daemon would otherwise serve "checked, nothing withheld" before anyone had checked anything — and the issue tier alone would vouch for the whole census during the minutes before the project loop's first poll. For the same reason there is deliberately **no** single aggregate "is the census fine" boolean anywhere in the response: no field a consumer can read instead of the per-source truth.
- A withheld row's `waiting` reuses `StatusFloorTracker`/`StatusFloor` verbatim (a second, dedicated tracker instance), so it is a floor with the same provenance and the same restart semantics as an agent row's `timeInStatus` — never the admission controller's internal wait ledger, which is counted in polls across two differently-paced tiers and is not a time.

### Changed
- `admit()`'s return value, the admission ORDER (`orderByWait`/`admitWithinBudget`), the fail-safe paths' decision to withhold every candidate, `snapshot()`'s existing `{cap, residency, longestWait}` contract, and §B3's promise that neither fail-safe path touches the wait ledger, `lastTrusted` or `lastWithheld` are all **unchanged**. This increment only ever RECORDS what `admit()` already computed; the census write on each fail-safe path sits beside the existing `return []`, deliberately outside the `if (candidates.length)` logging guard — a census failure is a census failure whether or not anyone wanted a slot that poll.
- No new I/O and no new collection path: `createDashboardFeed` reads the census synchronously once per poll, from state `reconcileNow`'s own `opts.admission` already computed earlier in that same poll, and the request handler (`src/web/view.ts`) is untouched — still a bare snapshot read.
