### Fixed
- **A managed-session agent was silently stopped and re-spawned every ~12-15s because the ordinary filesystem-rule loop mistook it for one of its own leftover agents (FACTORY-47).** `ownsFilesystemAgent` (`src/rules/filesystem-type.ts`) matched any id with `resourceProvider: "filesystem"` — but BUTCHR-407/408's built-in managed-sessions rule (`startManagedSessionsLoop`) reuses that same `resourceProvider` for an unrelated, exclusively-owned resource shape. `startFilesystemLoop`'s own documented behaviour ("still stops filesystem agents left over from an earlier run — never leaves them running with no loop to stop them") then applied to every running managed-session agent whenever a daemon had zero enabled `filesystem` rules (the common case): `ownsFilesystemAgent` reported it as owned, no rule wanted it, so `stop = running − desired` stopped it every poll. The managed-sessions loop then saw it gone and spawned it again (never a *respawn* — nothing was ever stale), repeating forever with only `[spawn] … origin=spawn` in the journal and no `[reconcile] … respawned:` line — exactly the reported symptom, and never the `%2F` workspace-path encoding, a duplicate stale session, or the kickoff `cd`, all of which were ruled out live on codey first. Fixed by excluding the managed-sessions rule id from `ownsFilesystemAgent`'s match. Regression test runs `startFilesystemLoop` (zero rules) and `startManagedSessionsLoop` (one definition) against the same herd and asserts the managed session is never stopped and spawned only once.
