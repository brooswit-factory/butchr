### Fixed
- **Plan-then-apply on a UI rule write no longer gets refused by the previewer's own 2s-per-rule rate limit (N1, FACTORY-678).** `planRuleWrite` and `writeRuleEnabled` each call the SAME shared `scopeOf` for a rule being enabled, typically seconds apart (a normal plan-then-apply UI flow) — the previewer refuses a second real call on the same rule inside its own `DEFAULT_PREVIEW_RATE_LIMIT_MS` (2s) window, which `scopeOf` previously failed SAFE to `Number.POSITIVE_INFINITY`, tripping the scope ceiling on every back-to-back apply and showing the operator the literal string `"Infinity ticket(s)"`. Fixed by wrapping `scopeOf` in a shared, 10s-TTL `createScopeCache` (`src/rules/rules-write.ts`), wired once in `src/daemon/index.ts` — a plan followed by an apply now shares one real previewer call instead of racing its rate limit. A genuinely unavailable previewer (not a rate-limit refusal) still fails closed exactly as before.
- **`scope` is now bound into `planHash`** (`buildPlanHash(nextText, counts, scope)`), and `writeRuleEnabled` verifies it under the lock against a fresh, locked recomputation — so `confirm: true` can no longer land a write whose scope was never evaluated and bound to the hash the plan actually showed the operator. This intentionally invalidates every plan hash computed before this change.
- **No `Infinity`/`NaN` literal can reach an error string any more** — a non-finite scope (previewer unavailable) now renders as a safe human-readable label instead of the number itself.
- **A server-side per-client write-flood limit (N2, FACTORY-678)**, 429 + `Retry-After`, now covers all four write-shaped routes (`POST /api/rules/:id/enabled`, `PUT /api/rules/:id`, `POST /api/rules/plan`, `POST /api/undo/:backupId`) — one shared `createWriteRateLimiter` instance (`src/web/write-rate-limit.ts`), default 10 writes/min, keyed on the caller's own socket address (every legitimate caller is already same-uid-gated by `checkWriteGuard`, so there is no stronger identity to key on). Counts rejected attempts too — a flood of refused writes still touches the lock. A 429 from this limiter is audited through the SAME rejected-write pipeline as any other refusal, so the existing rejected-burst alert aggregation (B4, `src/web/audit-log.ts`) still bounds the alert count across a write-flood burst. `POST /api/rules/plan` shares the SAME budget as the other three routes; a normal plan-then-apply pair (2 requests) never trips the default budget.
- **Added the missing route-level test for the stale-lock refusal (N3, FACTORY-678)**: `src/rules/write-rules.ts`'s absolute lock path + `rm` hint were already passed through to the HTTP response body verbatim at the rules-write layer, but nothing proved it at the route boundary. Added for both a dead-pid and a live-holder lock refusal. No server-side code change was needed for N3; the UI half (`dashboard-app/src/api/rules.ts`) is out of scope here — already fixed by a separate, currently-blocked PR.
