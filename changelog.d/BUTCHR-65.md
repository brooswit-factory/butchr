bump: minor

### Added
- **A PROJECT-keyed caller is now a first-class citizen of the whole MCP tool surface (BUTCHR-62/BUTCHR-65/BUTCHR-71) — the identity a project agent will use once it exists.** `x-issue` widens from "always an issue key" to "an issue key OR a Jira project key" (e.g. `BUTCHR`), told apart with the codebase's existing exported issue-key regex — a project key never contains a hyphen, so the two can never collide. The new predicate lives in `src/resources/id.ts` (`isIssueKey`/`isProjectId`), deliberately dependency-free (a single import of the existing regex) so the sibling resource-type-abstraction work can share it without pulling in the rest of the tool layer.
- `get_doc`/`set_doc` resolve a PROJECT caller to that project's Confluence ROOT DOC (the page named by its `butchr` entity property's `rootDoc.id`) instead of a per-ticket page — reusing the existing `getProjectProperty` reader, never adding a second one. A project's root doc is never created here: it always already exists, and a missing property or `rootDoc.id` is a refusal naming the project, never a fallback to creating a stray page. Reads stay unrestricted by ownership in both directions (an issue caller can read a project's root doc; a project caller can read an issue's doc).
- `new_worker`/`adopt_worker` from a PROJECT caller create/adopt an **Epic**, one tier below, staffed by a new `epic` role (`BUTCHR_ASSIGNEE_EPIC`, same per-call refusal shape as `BUTCHR_ASSIGNEE_STORY`/`BUTCHR_ASSIGNEE_TASK`, no silent fallback to either). There is no Implements link for this relationship — a Jira project is not an issue — so it's MEMBERSHIP instead: `new_worker`'s result reports `member` (the project key), never a lying `implements`, and the write order drops the link step accordingly (rollback still covers the disposition step). The new epic's doc nests under the project's root doc automatically, via the existing bossless-bottoms-out-at-root path in `ensureDoc` — no second code path was needed.
- The shared "is this one of my own workers?" ownership check (behind `start_worker`/`shelve_worker`/`finish_worker`/`prioritize_worker`/`tell_worker`) grows a project-caller branch: ownership is membership (the worker's own `project.key` equals the caller), but membership ALONE is deliberately not enough — the target must also be an Epic, refusing a Story/Task in the caller's own project just as sharply as an Epic belonging to a different project. `finish_worker`/`tell_worker` on a project's own Epic is the cross-account review hop the whole project-tier identity design exists for (a project's Atlassian account is never the epic tier's own).
- **`report_to_boss`/`ask_boss` work for a project caller too**, posting on the project's own ROOT DOC instead of a ticket (a project has none) — the same identity tag and `[ask]` marker convention, just a different channel. This required a genuinely new capability: the Atlassian ops surface had no Confluence comment operation at all (read or write). New `commentOnPage`/`getPageComments` ops (measured live: `POST /wiki/api/v2/footer-comments` -> 201; `GET /wiki/api/v2/pages/{id}/footer-comments` -> 200; a comment does NOT bump the page's own version), and a new seam, `src/tools/speak.ts`'s `speakOnOwnChannel`, deciding "where does this resource speak" — an issue on its own ticket, a project on its own root doc — reusable by anything outside the relationship verbs (in particular, a future fix to the daemon-side blocked-dialog escalation path, which is broken for a project caller today and is explicitly NOT fixed here). `submit_to_boss` and `finish_without_a_boss` still refuse a project caller (a project never reaches a terminal state); `file_where_it_belongs` also refuses one (its case-B notice walks the caller's own Implements chain, which a project has none of).
- **`finish_without_a_boss`'s own implementation is untouched** — its project-caller refusal lives entirely in a new caller-shape gate at the tool-registration layer (`src/tools/defs.ts`), the same place a missing `x-issue` is already turned into a named refusal, so the tier-above-epics narrowing this verb is designed for stays sequenced into a later story.
- `briefs/project.md` — a brief for an agent that owns a PRODUCT, not a ticket: no ticket, no boss, no definition of done, wakes on an event and exits. Selected the same way the existing briefs are (`briefFor("project")` in `src/agents/workspace.ts`, alongside the existing epic/story/task entries), and given the same model/effort tier an epic gets (`modelFor`/`effortFor`), not the task-level default.
- A known, deliberately-unsolved hazard, written down for BUTCHR-67 to inherit rather than discover live: a project's own `report_to_boss`/`ask_boss` call posts a Confluence comment on its own root doc, and "the root doc received a comment" is one of the three wake events the project resource type will wake a project agent on — left alone, this is a self-wake loop. The existing own-write ledger (`src/jira-watch/own-writes.ts`) records JIRA writes keyed by issue and does not cover this Confluence write surface.

### Changed
- `src/tools/atlassian.ts`'s `AtlassianOps` interface gains `commentOnPage`/`getPageComments`; every test fake implementing the full interface was updated additively.
- Every relationship-verb tool description in `src/tools/defs.ts` now states its project-caller behavior explicitly, so an agent reading the tool surface (not just this changelog) can tell what a project-keyed caller gets from each verb.
