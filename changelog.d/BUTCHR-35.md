### Added
- **Ten relationship-shaped MCP tools replace the generic Jira/Confluence verbs an agent used to reach for by hand: `new_worker`, `start_worker`, `shelve_worker`, `adopt_worker`, `finish_worker`, `prioritize_worker`, `tell_worker` (boss → worker) and `report_to_boss`, `ask_boss`, `submit_to_boss` (worker → boss) (BUTCHR-35, per the settled glossary — https://wroosbit.atlassian.net/wiki/spaces/BUTCHR/pages/12484678).** Each removes a decision an agent should not be making — issue type, assignee, link direction, ticket key — and leaves only what the worker should do. `report_to_boss`/`ask_boss` take no key at all (there is no key to get wrong); `ask_boss` marks its comment with the literal `[ask]` right after the identity tag so a boss can find unanswered questions without reading every comment. Five verbs (`start_worker`, `shelve_worker`, `finish_worker`, `prioritize_worker`, `tell_worker`) refuse a key that is not one of the caller's own workers, verified fresh via the Implements link at call time (`findBossKey`, exported from `src/tools/docs.ts` — BUTCHR-27's reasoning: the link direction is the single most commonly inverted fact in this fleet, so one shared reader beats five verbs each growing their own). `prioritize_worker` additionally refuses the caller's own key. `adopt_worker` refuses a ticket already linked to a *different* boss and is idempotent against one already correctly adopted by the caller.
- **`shelve_worker(key, reason)` moves a worker to To Do, adds the shelved-exemption label, and posts the reason — all in one call.** The label is read directly out of `EXEMPT_LABEL` in `src/agents/parked.ts` (`"butchr:shelved"`), not retyped, and the write is additive (read-modify-write via the new `AtlassianOps.addLabels`) so it never drops labels the ticket already carries. The label is written BEFORE the To Do transition: if the label write fails after a transition had already landed, the ticket would be left To Do, assigned, under a live boss, with no exemption label — a textbook parked child. Labelling first means that partial failure instead leaves the ticket In Progress carrying an inert label. `adopt_worker`'s own shelve path orders its writes the same way, and treats a ticket as "already adopted" only when it is already linked, assigned by role, AND already sitting in the state its disposition names — not from the Implements link alone — so that re-running `adopt_worker` to repair a `new_worker` partial-failure survivor (linked and assigned, but not yet declared) actually applies the disposition instead of silently reporting success and changing nothing. The reason comment on `adopt_worker`'s shelve path is intentionally NOT gated on that same "state already matches" check: an orphan can already carry the exemption label (set by a human, or by a boss that has since died) while this caller has never recorded why *it* is shelving the ticket, so the reason is posted whenever any real adoption work happens at all, and only a fully idempotent re-adoption skips it — otherwise a required, validated argument would be silently discarded and the worker would end up shelved with no activation condition on record at all.
- **`new_worker`'s write ordering, not unconditional atomicity, is the shipped guarantee**, following live measurement against this daemon's own Jira credential (2026-08-31): `GET /rest/api/3/mypermissions?projectKey=BUTCHR&permissions=DELETE_ISSUES` → `{"havePermission":false}`, and a live create-then-delete round trip on a throwaway probe Epic → `DELETE /rest/api/3/issue/<key>` → 403 `"You do not have permission to delete issues in this project."` — the daemon's credential cannot delete a Jira issue on this project today. Because that is a project *permission*, not an API limitation, the new `AtlassianOps.deleteIssue` op is wired into `new_worker`'s rollback anyway: writes go create → Implements link → disposition → doc, each step chosen to be less harmful to stop at than the last, so a returned key always means a ticket with a boss and a declared disposition (never undeclared). A failure at the link or disposition step attempts the rollback delete and reports either "rolled back, nothing survives" or a named partial state (the surviving ticket key) — never a false claim of atomicity. A failure at the doc step (deliberately last) is never rolled back: `ensureDoc` (BUTCHR-27/33) is convergent, so the ticket's own first `set_doc` call completes the binding whenever that agent makes one — nothing here retries automatically. The day `DELETE_ISSUES` is granted to this daemon's credential, this same code becomes fully self-cleaning with no rewrite.
- New `AtlassianOps` ops: `addLabels` (additive read-modify-write) and `deleteIssue` (measured refused on this daemon as above; called anyway). (A `deletePage` op was also measured live during design — trashes rather than purges, so a rollback page is removed from normal discovery without being irreversibly destroyed — but was not shipped: `new_worker`'s doc step moved last and is never rolled back, so nothing calls it; left for whoever needs it to add with its first real caller.)
- **Every pre-existing tool name still resolves**, since a tool surface reaches only newly spawned agents. `jira_get_issue`, `jira_search`, `jira_add_comment` (the deliberate sideways channel for two bosses coordinating — outside what the hierarchy models), `confluence_list_spaces` and `confluence_search_pages` are retained permanently, with no deprecation note. The other eight pre-existing names (`jira_link_issues`, `jira_transition`, `jira_create_issue`, `jira_set_priority`, `jira_assign`, `confluence_create_page`, `confluence_update_page`, `confluence_get_page`) are now aliases: unchanged behavior, a deprecation note in their description naming the replacing verb, and their audit line now says so too — the removal condition (zero alias calls across a full fleet lifetime after a respawn) needs that evidence and nothing is removed in this release.
