### Fixed
- **A hung herdr socket no longer wedges the poll loop, the notify stage, and the permission-answer timer forever (FACTORY-722).** The daemon's single shared `DrovrClient` was constructed with no `timeoutMs`, so a herdr call that never settled (a socket error that produced no rejection) left `herdr.agent.list()`/`herdr.subscribe()` pending indefinitely — and every caller that serializes on one of those two calls wedged with it: `permission-answer-watch.ts`'s own in-flight guard only clears in the `.finally()` of a tick whose first await is `agent.list()`, and `HerdrHerd.runningIssues()` (read by the admission controller's shared residency check) is the same call, which is why pollLoop/notify/jira-idea/filesystem/managed-sessions all went stale together in the incident this ticket closes, not only the permission-answer timer. A new `BUTCHR_HERDR_TIMEOUT_MS` config (default 10000ms) now bounds every call the shared client makes. `DrovrClient.subscribe`/`HerdrClient.subscribe` opens its own connection outside `rpc()` and never reads that option at all (confirmed against the SDK's own source) — the daemon's `subscribeAgentStatus` wiring now applies the same deadline to that call path directly, closing the one gap the client-side option doesn't cover.
- **The permission-answer watch now runs an independent watchdog**, separate from its own sweep/tick timer, that detects a pane whose push-triggered `blocked` event has sat unconsumed for over 5 minutes (unambiguous evidence the tick itself has stopped running, not merely that one pane's own attempt failed) and force-restarts the watch: clears a wedged in-flight guard, closes and reopens the push subscription, and kicks a fresh tick. Logs `[watchdog] restarted permission-answer` and raises an ops alert.
