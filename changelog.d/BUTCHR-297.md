### Added
- **The admission cap's order now ages, so a starved candidate cannot lose every poll forever (BUTCHR-297).** `AdmissionController.admit()` (`src/agents/admission.ts`, BUTCHR-284) previously admitted this poll's spawn candidates in `planReconcile`'s bare lexicographic key order, with no memory of who lost last time. Under sustained saturation this is not a fairness nicety: measured live on two daemons across ~750 polls each, it produces WHOLE-PROJECT STARVATION BY KEY SPELLING — one daemon's permanently-excluded tail spanned ten tickets across six projects, every one of them sorting after `BUTCHR`, while a High-priority ticket sat withheld behind a Medium one for hours. FIFO, priority-awareness, and oldest-first were all independently refuted as explanations; bare lexicographic order was the only one consistent with every observation. This was a deliberate design exclusion, not a defect: the module's own header states admission is fair-share-agnostic on purpose, and the liveness property it promises — withholding, never dropping — held throughout the entire starved window. The property that was missing is now in scope. A new, separately-exported pure `orderByWait` reorders candidates by accumulated wait DESCENDING, tie-broken by the existing lexicographic key ASCENDING — so a cold start or an unsaturated fleet (every wait still 0) reproduces today's exact order byte-for-byte, and every pre-existing `admitWithinBudget`/`reconcileNow` test remains meaningful. The wait ledger lives inside `createAdmissionController`'s own closure, counted in `admit()` calls (not minutes — the controller is shared by two tiers polling at very different cadences, and a call count is the unit both already agree on for `ImplausibleZeroGuard`) and bounded by evict-after-unseen, never by "clear whatever is absent this call" (that would let the ~5-minute project tier silently wipe the 15-second issue tier's own accumulated waits roughly twenty times per project poll).
- **A candidate's wait survives a failed spawn — cleared only once a spawn actually succeeds, never on admission itself.** Admission and running are different events: at the measured 24–29% per-attempt spawn failure rate (`agent_pane_busy`, the create-then-start readiness race), a candidate can be admitted, have its counter reset, fail to spawn, and return next poll at the back of the queue having never run — starved by the very mechanism built to prevent starvation, and invisible, because a successful spawn writes no journal line and a reset counter looks exactly like a fresh arrival. This was caught before it shipped (this ticket's own first three admissions reproduced it live). `reconcileNow`'s new optional `onAdmitted` hook (`ReconcileOptions`, `src/daemon/loop.ts`) — a sibling to `admission`, not a change to its signature, matching the house pattern of `checkCrashLoop`/`checkReconcileFailure`/`checkReap` — reports `admitted` minus this poll's own `"spawn"`-staged failures, once, after the spawn `Promise.all` settles; `AdmissionController.recordSpawned` (the only thing that ever clears a ledger entry) is wired to it at both loop sites in `src/daemon/index.ts`, the same shared controller instance `admission` already uses.
- **`/health`'s `admission` field gains `longestWait`**: the currently-withheld candidate with the highest accumulated wait (`{ id, polls }`), or `null` when nothing is withheld — distinguished from "never observed" the same way `residency` already is (`residency: null` before any trusted census; `residency: <n>, longestWait: null` once observed with nothing waiting). A sibling field, never folded into `components[]` or any `ok` predicate: sitting at the cap with a long-withheld candidate is a normal, healthy, expected state under saturation.
- **The `[admission]` journal line now names each withheld candidate's current wait count** (`id(count)`, comma-separated) instead of a bare id list — the trade-off aging accepts (losing determinism from the ticket key alone) is what this buys back. The existing tokens (`cap=`, `residency=`, `withheld N/M wanted:`) are unchanged and still parseable.
