### Fixed
- **`adopt_worker` now withdraws `butchr:orphan` the moment an adopted ticket gains a boss, so the undirected-ticket query stops accumulating false positives forever (BUTCHR-108).** `file_where_it_belongs` applies `butchr:orphan` so "show me every undirected ticket" is a one-line JQL filter, but nothing ever cleared it: an orphan that was adopted, linked, staffed, worked, reviewed and merged still carried the label meaning "nobody owns this" — measured live on BUTCHR-99, which read back `["agent:idle", "butchr:orphan", "pr:merged"]` after `finish_worker`, and on the story ticket that filed this fix, which carried the label itself while adopted and In Progress. The signal degraded in exactly the wrong direction: every successfully re-homed orphan stayed in the query permanently, so precision rotted fastest when adoption was working best.
- Both `adoptWorker` (the issue-caller path: Story/Task) and `adoptProjectWorker` (the project-caller path: Epic) now clear `butchr:orphan` whenever the adopted ticket carries it, reusing the labels fetch each path already does for its own idempotence check — no extra Jira read. The project-caller clear is symmetry / defence-in-depth rather than a fix for a reachable bug, since `file_where_it_belongs` can only ever create a Story or a Task.
- Unlike the existing `butchr:shelved` (`EXEMPT_LABEL`) withdrawal, which is gated on a `"start"` disposition, the `butchr:orphan` clear runs for **both** `"start"` and `"shelve"` — the orphan label means UNDIRECTED, and a ticket adopted with `"shelve"` is exactly as directed as one adopted with `"start"`, so it must lose the label too. Like the `butchr:shelved` withdrawal, it is not gated on the `alreadyAdopted` idempotence check either: an otherwise fully idempotent re-adoption still clears a stale orphan label, so a live, directed ticket never keeps silently carrying it. Cleared before any transition, same ordering discipline as the existing `butchr:shelved` clears.
- The two labels' lifecycles were reasoned about together and are now tested together: an orphan adopted with `"shelve"` ends up correctly exempt from the parked-ticket detector (`butchr:shelved` present, `butchr:orphan` gone), and one adopted with `"start"` ends up visible to the detector exactly like any other normal directed ticket (neither label present). The two labels never end up coexisting on a live ticket.
- `butchr:orphan` stays out of `isDaemonLabel` (`src/labels/plan.ts`) — it is not daemon-owned, same as `butchr:shelved` — so the unattended sweep/reconcile machinery still never touches it; only the explicit, agent-invoked relationship verbs (`file_where_it_belongs` to apply, `adopt_worker` to withdraw) own its lifecycle.
- Updated every doc comment and tool description that documented the old, one-way lifecycle: `adopt_worker`'s and `file_where_it_belongs`'s descriptions in `src/tools/defs.ts`, the `adoptWorker`/`adoptProjectWorker` JSDoc, the `ORPHAN_LABEL` constant's own JSDoc, `fileWhereItBelongs`'s doc comment, and `src/labels/plan.ts`'s `isDaemonLabel` doc comment.
