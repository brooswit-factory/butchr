### Added

- **Reconciliation now honours a rule's `execution` mode, for all four resource providers (`jira-work`, `github-issue`, `jira-idea`, `zendesk-ticket`).** `swarm` is unchanged, byte for byte. `singleton` runs exactly one agent (BUTCHR-397's query-level identity) for the rule's whole matching workload while it has one or more matches, and stops it at zero; `persistent` runs that one agent even at zero matches, stopped only by an explicit freeze (`enabled: false`). Reconciliation converges on exactly N / 0-or-1 / 1 agents and never duplicates one — across daemon restarts (an existing running query-level agent is adopted, never re-spawned) and across a failed poll (never read as zero matches). Switching a rule's mode is a deliberate transition, LOUDLY logged (`WARNING: [execution-mode] ...`), never a silent retirement or duplication (BUTCHR-370 class).
- **A `singleton`/`persistent` rule's one agent now hears the relevant events across its whole scope** — a resource entering the query (`appeared`), status changes, and comments where the provider adapter supports them — delivered through the same related-watcher mechanism a boss already uses to hear its implementer, deduplicated per change and with the existing own-write echo suppression preserved. Swarm event routing, and the pre-existing Implements/Relates boss routing, are unchanged.
- **`account` remains plumbed only** (BUTCHR-397's scope) — no lifecycle behaviour ships here; that is story S4.
- **MCP identity for a query-level agent, defined**: it connects with `x-butchr-agent` alone (never `x-issue`), for every provider including `jira-work` — there is no single resource to name one for. `callerIdentity` recognises it as its own `CallerIdentity` variant; the `agy` workspace bridge's `.butchr-agy.json` shape for one is `{ agent, mcpUrl }`, no `issue`/`resource` field.
- **The `resourceKeyOf` hazard from BUTCHR-397's review is closed**: every call site that could have keyed a live Jira/GitHub/Zendesk lookup, or a notification's subject, off a query-level agent's own bogus `<provider>:<ruleId>:@query` id now either derives the real changed resource instead (event notifications) or is explicitly skipped for a query-level id (crash-loop/reconcile-failure comments, respawn notices) — never a lookup or comment against a key that names no real resource. `docs/execution-modes.md`'s audit table is updated to match.
- **Fleet capacity role, per the epic's decision (BUTCHR-391)**: an optional rule field `role: "worker" | "sentinel"`, default `"worker"` — independent of `execution`/`account`, validated the same way, accepted for every provider. Every rule stays a worker (counted toward `BUTCHR_MAX_AGENTS`, subject to admission withholding) unless explicitly flagged `sentinel`, in which case its agent(s) — a swarm rule's per-resource agents, or a singleton/persistent rule's one query-level agent — are never withheld and never counted toward residency; worker admission is computed as though sentinels did not exist. An agent whose rule cannot be resolved (a legacy/bare-issue agent, or a rule since removed) counts as a worker. The `[admission2]` log line and the `/dashboard` admission panel report `residency(workers)=<n> sentinels=<m>` separately (a format change from the old bare `residency=<n>`); each sentinel rule is logged once at startup.

See `docs/execution-modes.md` for the full design (identity, workspace layout, event delivery, the `resourceKeyOf` audit table, and the fleet-capacity-role mechanism).
