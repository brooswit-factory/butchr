### Fixed
- **Both project-tier comment readers (`getPageComments`, `getIssueComments`) now paginate to exhaustion instead of returning a single default/capped page.** `getPageComments` (the root-doc footer-comment axis) previously requested no `limit` and followed no cursor, so it silently returned only Confluence's default first page of 25 comments — MEASURED live: the BUTCHR project's own root doc already held 39 footer comments, and a comment it posted to itself (id `23593000`) was never observed because it landed outside that first page. `getIssueComments` (the per-epic axis) previously capped at a flat `maxResults: 20` with no pagination, silently losing any comment on an in-review epic past its newest 20. Both readers now loop until every comment is observed: `getPageComments` follows the endpoint's own `_links.next` opaque cursor at `limit: 250` per page, throwing rather than silently stopping if a present `next` link's cursor can't be parsed; `getIssueComments` pages on `startAt`/`maxResults: 100`, terminating on whichever signal the server actually reports — a known `total` reached, else a page shorter than the server's own reported `maxResults` (which Jira can cap below what was requested), else (with neither field reported) only a genuinely empty page. A shared runaway guard (`MAX_COMMENT_PAGES`) THROWS rather than returning a silently truncated list if none of those signals is ever hit. Neither op's signature or return shape changed, so every existing consumer (project-tier discovery, `check_in`, `get_doc_comments`, the `speak.ts` self-suppression read) now simply observes the full comment set with no code change of its own. Live MCP-facing descriptions and doc comments that referenced the old page-window/cap as a wake caveat (`tell_peer`, `getIssueComments`'s "same cap as the issue tier" claim, `check_in`'s inline comment, and `src/resources/project.ts`'s own doc comments) are corrected to match.
- **Deliberately NOT covered by this ticket**: the issue tier's own separate comment reader (`src/atlassian/client.ts`'s `AtlassianClient.comments()`, still capped at `maxResults = 20`, caller-overridable) is a different tier/mechanism, filed separately as BUTCHR-312. The unexplained 38-vs-39 gap between a v1 and v2 read of the same root doc (measured by a peer epic) is also out of scope and not load-bearing here. This PR is **fixed in code, not confirmed live** — merging it does not deploy it (this daemon only picks up new code on restart), and the live end-to-end confirmation (a project-tier caller observing more than 25 comments, including `23593000`) is owned by the story ticket, not this one.
