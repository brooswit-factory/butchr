### Added
- **Butchr now pins drovr's own host-neutral escalation hook, catching unrecognized dialogs Butchr's own parser might miss (FACTORY-45 Part B).** `@brooswit/drovr` bumped to 0.15.0. A new, independent poll loop (`createManagedSessionEscalationWatcher`, `src/agents/managed-session-escalation-watcher.ts`) calls that release's `createBlockingEscalationWatcher(...).poll(...)` every 5s over the whole fleet, but with `agent.sendKeys` permanently overridden to a no-op: drovr's own watcher detects and classifies dialogs, but never presses one — running its recognizer's own auto-answering fleet-wide, independently and on its own cadence alongside Butchr's existing `watchPrompts`, was found in review to be able to press a stale dialog's keys into the NEXT dialog on a slow redraw (e.g. trust's `down`+`enter` landing on development-channels' "Exit" instead). Its `onUnknownDialog`/`onDialogResolved` hook feeds the SAME minimal managed-session escalation Part A shipped (the `[managed-escalation]` journal line + `/health`'s `managedSessionEscalations` mark) whenever the pane resolves as a managed session — a keyed pane, or a non-managed keyless pane, is a no-op there, leaving Butchr's existing detection/escalation pipeline fully in charge of both, unchanged. Butchr's own dialog-answering (`src/agents/prompt.ts`) remains the SOLE answerer, fleet-wide, unaffected by this ticket — see `docs/managed-sessions.md`'s "Two detectors, one mark" for the one residual this leaves: the two independent PARSERS (never answerers) can derive different fingerprints for the same real dialog, so a single episode can log twice.
