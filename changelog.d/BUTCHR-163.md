### Fixed
- **The build-currency verdict could render `CURRENT` for a daemon running genuinely stale code, with a reassuring "fetched moments ago" beside it (BUTCHR-163).** `src/agents/build-currency.ts` gates a content match to `current` only when the comparison base's freshness can be established, but its `lastFetchedAt` input answered *"did this checkout fetch at all?"* when the gate needs *"did this checkout fetch the branch I am comparing against?"*. Those come apart in both directions, and one direction is dangerous. **Overstating (the false green):** the implementation read only `FETCH_HEAD`'s mtime, never its content, so *any* fetch — of a different remote, or an explicit URL — freshened it while `refs/remotes/origin/main` stayed stale; walking the gate with a build matching that stale base yielded `current`. **Understating (safe):** `FETCH_HEAD` is **per-worktree**, so a fetch performed in a linked worktree never touched the common dir's copy the code read — measured by controlled experiment on git 2.43.0 and independently reproduced, and this fleet's agents routinely fetch inside their own worktrees. A module comment asserted the opposite *as measured*; it is now corrected to what was actually measured, together with the asymmetry that caused the bug (`logs/refs/remotes/origin/main` is shared, `FETCH_HEAD` is not). `lastFetchedAt(remote, branch)` now derives the answer instead of reading a bare mtime: it resolves the remote's configured URL, gathers candidate `FETCH_HEAD`s from the common dir **and every linked worktree's git-dir** (a `readdir`, never a subprocess per worktree — this runs on the agent-spawn path), keeps only records whose stored provenance names that URL and that branch, and takes the newest; when nothing qualifies it reports `unknown` with the reason, never a guess. A record must also name **the sha the tracking ref currently holds** — found in review, and the reason naming the URL and branch was not enough: `git fetch <url> main` (a fetch **by URL**, not by remote name) writes a record naming origin's own URL and `main` while git updates `refs/remotes/origin/main` only for a fetch routed through the configured remote, so the record read as origin/main freshness while the ref stayed behind and the gate still walked to `CURRENT`. The sha condition is **sound rather than merely conservative**: a `FETCH_HEAD` line records the sha the fetch actually saw for that branch, so equality with what the ref holds now proves the ref is at least as fresh as that fetch — which keeps the ordinary cases (a plain `git fetch origin`, a **no-op** fetch that moved nothing, a fetch inside a linked worktree) counting, while excluding a by-URL fetch unless it saw exactly what the ref already holds. Remote URLs are compared normalised, which is load-bearing rather than defensive: git strips a trailing `.git` when recording a fetch source, so on this repo the configured URL carries the suffix while **0 of 273** `FETCH_HEAD` lines do — an exact-equality matcher matches nothing and degrades every verdict to an `unknown` that reads exactly like a principled refusal to claim, trading a false `CURRENT` for a permanent false `unknown`. **Expect more honest `unknown` verdicts than before; that is the fix working.**

### Changed
- **A currency verdict and the age of the base it was computed against can no longer be read apart (BUTCHR-163).** The gate checks that the freshness signals can be *read*, not that they are *recent* — a clone that last fetched the base a week ago still renders `CURRENT` — so the base's last-fetch time now sits on the verdict line itself (`currency: CURRENT — matches <base> content-for-content, base last fetched <iso>`), not only in the trailing `comparison base:` sentence a reader skimming for the word `CURRENT` never reaches. A staleness **threshold** was considered and deliberately declined, with the reasoning recorded in the code: being behind is not always a fault (a deliberate pin, a paused deploy during an incident, and a rollback are all legitimate), a check that cannot separate "behind because the deploy broke" from "behind on purpose" is a crying-wolf alert, and the right threshold would depend on a deploy cadence measured (BUTCHR-274) as "whenever a person acts" — there is no number to pick. Report what was observed; leave what it means to the reader. The `comparison base:` sentence no longer claims the figure is "when this checkout last fetched from a remote at all", which the narrowed derivation made untrue.
