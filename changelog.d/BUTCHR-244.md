bump: minor

### Added
- **`check_worker(key)` — the verb that can actually answer "is my worker staffed?" (BUTCHR-244).** `new_worker`/`start_worker`/`adopt_worker` never started an agent and never could confirm one exists — the disposition write is only `ops.transition(key, "In Progress")`; the actual spawn happens later, independently, in the daemon's own reconcile poll (`reconcileNow`, `src/daemon/loop.ts`), and a spawn failure there (e.g. herdr's `agent_pane_busy`) was never routed back to the caller that asked for the worker. `check_worker` closes that gap: same ownership guard as `start_worker`/`tell_worker` (`assertOwnWorker`, reused, not reimplemented), returning the worker's Jira `status` and a **three-valued** `staffing` verdict — `"staffed"` / `"not-staffed"` / `"could-not-look"` — never a two-valued one, following the same reasoning `PrLookup` (`src/labels/plan.ts`) already established for exactly this shape of mistake.
- `atlassianTools` takes a new optional 5th parameter, a narrow `(key) => Promise<boolean | null>` probe over `herd.runningIssues()` — not the whole `herd`, so `src/tools/defs.ts` (and `relationship.ts`'s `checkWorker`) stays pure over its dependencies and unit-testable with no herdr fixture. Wired at the daemon's own `atlassianTools(...)` call site (`src/daemon/index.ts`), where `herd` is already in scope. When absent, or when it can't answer, `check_worker` falls back to the ticket's own `agent:*` label (`agent:none` = active ticket, no running agent — `src/labels/registry.ts`) and names which source (`"herd"` or `"label"`) actually answered, so a label-derived verdict (up to a poll stale, further damped by the two-poll stabilizer in `src/labels/sync.ts`) is never mistaken for a live one.
- **Scope safety (AC-5), found live during this ticket's own review**: a boss checking whether its own worker was staffed queried its own herdr and got a clean, confident, wrong "not staffed" — the worker was staffed by a *different* Atlassian account, run by a *different* butchr daemon on the same host, whose herd this daemon cannot see. A herd only ever covers issues assigned to its own account (`assignee = currentUser()`, `ISSUE_JQL`, `src/resources/issue.ts`), so an empty/false probe read is not evidence of anything for a worker outside that scope. `check_worker` now checks this itself, from data already in hand — the worker's own Jira assignee (already fetched) against `ops.getMyself()`'s own identity — **before** ever calling the probe; out of scope (or scope that can't be established, e.g. an unassigned worker or a failing `getMyself()`) skips the probe entirely and falls back to the label instead (still valid — the label is written by whichever daemon actually staffs the ticket), with `probeOutOfScope: true` on the result naming why. This is a deliberate departure from the ticket's own suggested `(key) => Promise<boolean | null>`-only seam; the scope check lives in `checkWorker` itself rather than in the probe, since the daemon already holds both facts needed for it without any cooperation from the probe's own implementation.
- `new_worker`'s (and `newProjectWorker`'s / `adoptWorker`'s / `adoptProjectWorker`'s) result now carries a `staffing` field stating, in words, that the disposition write is unconfirmed and asynchronous (`STAFFING_PENDING` for `"start"`, `STAFFING_NOT_ACTIVE` for `"shelve"`) — it must be impossible to read a normal return as "an agent is running." `start_worker`'s own result gets the same statement at the tool-wiring layer. Every tool description in `src/tools/defs.ts` that used to claim a disposition or `start_worker` itself staffs an agent has been corrected to say what's actually true: it moves the ticket into the status set the reconciler spawns from, nothing more.
- **`new_worker` no longer produces a twin on a retry.** Before creating, it now checks whether the caller already has a NOT-DONE worker whose summary exactly matches (after trimming) the one requested — read off the SAME `ops.getIssue(callerKey)` payload already fetched for type/project inference (Jira hydrates each outward `Implements` stub's `summary` alongside its `status`, confirmed live against a real caller-with-children payload), so this costs no extra Jira call and no JQL search. On a match, nothing is created — the result carries the existing worker's `key`, `created: false`, and a `duplicateReason` naming the match, never a throw (a throw here would reproduce the exact uninterpretable-outcome shape this ticket exists to kill).

### Fixed
- Nothing was broken in the sense of a wrong outcome (see this ticket's own investigation: the reported "half-success" duplicate has a completed Confluence doc, meaning `new_worker` returned normally — there was no error for the caller to misread). The defect was that the return, and two tool descriptions, made a claim ("an agent is now running") the code was never able to back up, on every call, 100% of the time.

### Limitations, stated deliberately rather than left implied
- **No bypass for the idempotency check in this increment.** A caller that genuinely wants a second worker with an identical summary must differentiate the summary — there is no flag to force a second ticket.
- **The idempotency check applies to the ISSUE-caller path only.** The PROJECT-caller path (`newProjectWorker`) does not get it: the free read it relies on (a single `getIssue` call that already embeds every child's summary) only exists because the caller is an issue with `issuelinks`; a Jira PROJECT is not an issue and has no equivalent free read — finding a project's own existing Epics by summary would need a new JQL search, which is exactly the added Jira round trip this ticket rules out for the issue-caller path. Adding it anyway would be a materially different, costlier feature, not a symmetric extension of the free one.
- **The board surface is deliberately unchanged** — no new Jira status, no new label, no change to `src/labels/`. A ticket whose spawn failed stays In Progress on purpose: moving it out would remove it from `ACTIVE_STATUSES`, and the daemon would stop retrying the spawn, stranding it permanently — trading a legibility problem for a worse one. The honest surface (the `agent:*` label, and now `check_worker`) already existed; what was missing was only that callers weren't told to use it.
