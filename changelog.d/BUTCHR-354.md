### Fixed
- **`/dashboard` now reaches its own `{checked: false, declinedAt}` state when the issue poll rejects upstream of `syncLabels` (BUTCHR-354).** `runResourceLoop`'s fetch stage (`src/daemon/loop.ts`) runs `search()` → `reconcileNow()` → `related()` → `syncLabels()` in order with no enclosing try/catch — a rejection from any of the first three steps aborts the poll before `syncLabels` (and therefore `/dashboard`'s own poll-fed check, `agentStatusesFeedingDashboard`) ever runs. Before this fix, that meant the dashboard snapshot simply froze at whatever it last held — `checked: true`, an aging `confirmedAt`, no `declinedAt`, and no coverage decline — with no way for a reader of `/dashboard` alone to tell "current" from "the daemon silently stopped checking, some unknown time ago." Measured live against the unmodified tree via a search()-rejection falsifier: the snapshot stayed `checked: true` indefinitely while `/health`'s own `pollLoop` component correctly went stale past `config.pollStaleMs`.
- `createDashboardFeed` (`src/agents/dashboard.ts`) gains `beginPoll()`/`declineUpstream()`: `beginPoll()` resets a tick-scoped flag at the very start of each fetch tick (wired from the issue tier's own `search` dep, `src/daemon/index.ts`); `declineUpstream()` flips the snapshot to `{checked: false, declinedAt}` with rows carried forward byte-identical, exactly like the existing decline path — but is a no-op whenever this same tick's own `poll()` already ran, so the pre-existing `agent.list()`-rejection decline path (BUTCHR-308) is never double-counted. Wired from the issue loop's `onError` (`src/daemon/index.ts`), which `@brooswit/sundry`'s `watch()` already calls whenever the fetch stage rejects for any reason — no change to the poll's own control flow, and the project loop (which does not feed `/dashboard`) is untouched.
- A single rejected poll declines `/dashboard` immediately rather than waiting out `config.pollStaleMs` — waiting would just reproduce, for this surface, the same blind window `/health`'s `pollLoop` staleness already has, which this fix exists to close. This is the same immediate-decline behavior the existing `agent.list()` decline path already has, not a new risk.
- No response shape change: this reuses the existing `DashboardResponse` `{checked: false, declinedAt, rows, admission}` vocabulary a reader (`src/web/dashboard-page.ts`) already handles from the pre-existing decline path.
