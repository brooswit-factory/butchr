### Fixed
- **A respawn in an already-reported pane (model/effort change, crash-loop restart, ordinary relaunch) now reports its NEW session id to herdr too, closing a gap PR #678's review found in FACTORY-714's startup-only sweep (FACTORY-720/FACTORY-713/FACTORY-704).** `reportPersistedAgentSessions` (FACTORY-714) reports a pane's persisted Claude session id to herdr only once, at daemon startup. Without this, a later respawn in that same pane persisted a NEW session id on disk while herdr kept whatever the earlier sweep told it — so the next herdr restart would confidently `claude --resume` a finished conversation instead of the live one, worse than the bug FACTORY-714 set out to fix. `HerdrHerd.spawn()` (`src/agents/herd.ts`) now also calls `herdr.pane.reportAgentSession` immediately after persisting a freshly-discovered session id, reusing the exact call the startup sweep already makes (factored into `reportAgentSession()`, `src/agents/report-agent-sessions.ts`) with the same swallow-and-log discipline — a failed report never fails the spawn, which has already succeeded. Neither call site sends a `seq`: read directly against the installed herdr's own source, a source nothing has ever attached a `seq` to is always treated as "newer than the last" on a plain re-report, so a seq-less report from either call site plainly overwrites the previous value; sending one from only one call site would instead permanently lock out future seq-less reports from the other.
