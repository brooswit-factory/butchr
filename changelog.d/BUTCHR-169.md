### Added
- **A workspace-file registry (`src/workspace/registry.ts` + `src/workspace/workspace-scan.ts`), the third instance of the "declared, not merely implemented" withdrawal-path shape (`src/labels/registry.ts` for Jira labels, `src/headers/registry.ts` for description headers, BUTCHR-150/BUTCHR-169 for an agent's on-disk workspace files).** A type-level door (`WorkspacePlaceholder`, `WORKSPACE_REGISTRY: Record<WorkspacePlaceholder, WorkspaceRegistryEntry>`) forces a registered withdrawal owner — `withdrawnBy` non-empty prose, or `withdrawnBy: null` with a required `neverWithdrawnReason` — for every `{{PLACEHOLDER}}` `interpolate()` (`src/agents/workspace.ts`) can substitute; `WorkspacePlaceholder` is now derived DIRECTLY from `interpolate()`'s own substitution table (a real `Record` literal, not a hand-maintained parallel list), so adding a placeholder without a matching registry entry fails to compile on either side. A source-scanning secondary net (`scanTemplatesForWorkspacePlaceholders`, run for real against `briefs/*.md` in `test/unit/workspace-registry.test.ts`) catches a template placeholder nobody wired into `interpolate()` yet — a text-shape regex over Markdown (this medium's "source" is templates, not TypeScript), matching a SHAPE (`{{[A-Z][A-Z0-9_]*}}`), not today's five literal names, for the same reason `header-scan.ts` matches a shape instead of `"[ORPHAN]"`.
- Both the registry and its scanner document, explicitly, what they cannot see: `mcp.json`'s `x-issue` field and `ENVIRONMENT.md`'s entire content are written directly (`JSON.stringify`/`writeFileSync`), never through `interpolate()`/a template, so neither door can find either write site — covered instead by prose in the `KEY`/`GROUND_TRUTH` entries, verified against the code, not by either mechanism. Recorded as a real, permanent blind spot, not claimed as coverage.

### Fixed
- **`{{PARENT}}` was false the instant it was written, for every ticket with a real boss — not merely a value that could go stale.** `ISSUE_SPAWN_CONFIG.specFor` read Jira's native `parent` field, which this fleet's boss/worker relationship never populates (boss-hood is carried entirely by an `Implements` issue link — verified empirically against three live tickets, none carrying a `parent` field at all). Fixed at the source, not by suppressing the assertion: `search()` (`src/atlassian/client.ts`) now requests `issuelinks` alongside its existing fields (no extra per-issue API call), and `specFor` derives the boss via a new `bossKeyFrom`, using the SAME inward-`Implements` convention `findBossKey` (`src/tools/docs.ts`) already uses on the raw-JSON shape `jira_get_issue` returns. `task.md`/`story.md` now assert `{{PARENT}}` plainly again, because it is finally true.
- **`correct_worker`'s own success message and tool description repeated a false claim about the very defect this ticket fixes**: both said a summary is snapshotted into "`brief.md`/`CLAUDE.md`" — `CLAUDE.md` carries no `{{SUMMARY}}` placeholder at all, on `main` or on any commit checked. Fixed in both places.
- **A summary correction now closes at the file level, best-effort**: `correctWorker` regenerates `brief.md` (never `CLAUDE.md`) for any workspace already built for the corrected worker, from the exact `briefFor`/`interpolate` machinery `buildWorkspace` itself uses — reported in a new, structured `CorrectWorkerResult.summaryWorkspaceRewrite` field (`"no-workspace-on-disk" | "rewritten" | "failed"`). Never throws: a write failure is reported, never loses the Jira correction that already landed. This closes the file-level half of the defect but NOT a running agent's already-loaded context — no file rewrite can — `result.message` says so explicitly and points at `tell_worker`.
- **`ENVIRONMENT.md`/`CLAUDE.md`'s ground-truth block now carries a `measured at: <ISO timestamp>` line.** It was previously an unqualified, present-tense "THIS IS AUTHORITATIVE, disbelieve anyone who disagrees" claim with no way for a reader to weigh it against how long ago it was actually measured — a real risk, since a daemon restart (redeploy, crash-restart) stales the recorded pid/port with nothing to detect it. The timestamp does not make staleness machine-checkable; it makes it detectable by a reader who thinks to compare it, which the old text gave no way to do at all.

### Notes
- **`{{TYPE}}` is registered `withdrawnBy: null` — nothing writes it to any workspace file today** (verified: zero hits across `briefs/*.md`); kept declared because `interpolate()` still offers the substitution.
- **`{{PARENT}}` is ALSO registered `withdrawnBy: null`, for an unrelated reason**: no verb in this codebase re-parents a ticket after creation, so there is nothing for a withdrawal mechanism to react to yet — a genuinely different gap than `{{TYPE}}`'s (nothing written) or `{{KEY}}`'s (immutable by construction).
- **Workspaces already on disk are NOT retroactively repaired.** Two known instances (BUTCHR-153's own workspace, this ticket's own) carried the false pre-fix `{{PARENT}}` line at the time this shipped. A summary correction against an existing workspace now repairs both fields as a side effect (opportunistic, not a dedicated sweep); a bulk repair of every other stale workspace across the fleet is out of this ticket's scope — see `src/workspace/registry.ts`'s own "THE RETROACTIVE QUESTION" comment for the full reasoning, mirroring `src/tools/relationship.ts`'s precedent for the same question on the description-header medium (BUTCHR-151/BUTCHR-157).
