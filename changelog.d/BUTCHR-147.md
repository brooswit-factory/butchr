### Added
- **A rejecting `herd.spawn`/`herd.stop`/mid-respawn `herd.spawn` no longer aborts the whole reconcile poll — and the isolated failure is now audible on that resource's own channel (BUTCHR-147).** Before this change, `reconcileNow`'s `Promise.all(plan.spawn.map(...))` rejected on the FIRST rejecting spawn, propagating out of `reconcileNow` before `stop` or `respawn` ever ran — so one resource whose `workspace.create`/`agent.start` failed (a genuine, observed failure mode: `HerdrHerd.spawn` throws when `workspace.create` returns no root pane) silently aborted every OTHER resource's stop and respawn for the fleet, plus that poll's label sync and success heartbeat, and misdirected the resulting `/health` alarm at "the daemon is dead" rather than at the one resource actually responsible.
- Each `herd.spawn` call, each `herd.stop` call, and each half of a respawn (`herd.stop` then `herd.spawn`) now catches its own rejection independently — one bad resource can no longer affect any other resource's spawn/stop/respawn this same poll. `herd.staleIssues()`/`herd.runningIssues()` are deliberately left unwrapped: a rejection there means the poll has no valid snapshot to reconcile against at all and must still fail the poll.
- **`/health`'s poll-loop component no longer degrades on an isolated per-resource failure — a deliberate reversal of the old (accidental) behaviour.** `onPollSuccess` now fires whenever the poll loop itself completed, regardless of an isolated spawn/stop/respawn failure; the per-resource fact belongs on that resource's own channel, not smeared across the daemon's own liveness signal.
- New `src/agents/reconcile-failure.ts`, reusing crash-loop.ts's/frozen-asleep.ts's own mechanism (`RateCap`/`findMarked`/`HOUR_MS`, `speakOnOwnChannel`/`createOwnChannelComments`) rather than inventing a second one: `reconcileNow`'s new optional `checkReconcileFailure` hook is called once per poll, after every isolated attempt, with the set of failures that poll produced. Two failures of the same resource within a rolling 15-minute window post one observational, rate-capped, dedupe-by-adoption `[butchr:reconcile]` complaint carrying the actual rejection message — the one thing BUTCHR-141's own `[butchr:crashloop]` complaint (a pure count, with no visibility into any individual rejection) cannot say; a single one-poll blip that recovers on its own never posts. Wired into BOTH the issue and project loops (`src/daemon/index.ts`), each with its own tracker instance, same as `checkCrashLoop`.
- `RespawnGuard`'s contract is unchanged: a respawn whose spawn half fails leaves the resource stopped and not running, so it can never again satisfy the guard's own `stale ∩ desired ∩ running` condition until freshly spawned — it falls into the ordinary `spawn` list next poll instead, unaffected by the guard window. `onRespawn` (the `[butchr:respawn]` Jira notice) is not called when a respawn's herd-level half fails.
