### Fixed
- **`correct_worker` no longer leaves a misleading `[correction]` archive when the replace fails (BUTCHR-128/BUTCHR-130).** An oversized `description` (over Jira Cloud's fixed 32767-character limit on rich-text fields — not configurable in Cloud, and not the same thing as the `jira.text.field.character.limit` advanced setting, which is a Server/Data Center mechanism that doesn't exist on Cloud) or `summary` (over Jira Cloud's separate fixed 255-character system-field limit) is now refused BEFORE the archive comment is posted — the worker is left byte-for-byte untouched and the error states the actual size and the limit, so the caller knows how much to cut. This is a cheap, no-Jira-read check ordered alongside the verb's existing self-key/neither-field/empty-`why` refusals.
- **When the replace fails for any other reason, the archive is now self-correcting.** `correct_worker` posts a best-effort follow-up comment, tagged with the new exported `CORRECTION_REJECTED_MARKER` (`[correction-rejected]`), marking the just-written `[correction]` archive as recording a write that was REJECTED — so a reader six weeks later with only the comment thread can tell a superseded-and-replaced archive apart from a superseded-and-NOT-replaced one. The annotation is genuinely best-effort: if posting it fails too, the ORIGINAL edit error still surfaces unchanged, never masked or replaced.
- The archive-before-replace ordering is unchanged, as is the caller-facing error text for a failed edit — this fixes the durable record on the ticket, not the in-session error, which was already correct.
