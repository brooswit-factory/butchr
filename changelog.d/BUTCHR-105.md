### Fixed
- **`advanceProjectWatermark` no longer risks destroying a project's `butchr` property on a transient read failure (BUTCHR-105).** It read the property fail-open (`.catch(() => undefined) ?? {}`) and used whatever it got as the base of `setProjectProperty`'s full-value replace — so a read that failed for any reason (rate limit, timeout, a permission change) looked identical to a genuine 404, and a successful write on top of that empty base would silently wipe `rootDoc`, `space`, `repos`, `archiveProject` and `scaffolded`. `rootDoc` is not reconstructible from anything else in the system. The function now reads via `AtlassianOps.getProjectPropertyOrNull`, whose contract already draws the needed distinction: a genuine not-found resolves `null` (a safe empty base), while any other rejection propagates and the write is never reached. This was latent in production — the account this write path runs as currently lacks the Jira permission to write project properties at all, so every write already 403s before the fail-open base could do harm — but becomes live the moment that permission is granted, which is a deliberate later step of BUTCHR-115.
- **`speakOnOwnChannel`'s self-wake watermark write no longer fails silently.** It already caught its own failure so a bookkeeping error could never fail an otherwise-successful `report_to_boss`/`ask_boss` — that behavior is kept, deliberately (an escalation from a blocked agent must not fail on this). What changes: the failure is now logged (`console.error` by default, an optional `log` param for callers/tests), because while the write above was 403ing in production, a project nudged itself on its own comments every five minutes with no signal anywhere saying why.
