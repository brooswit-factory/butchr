### Added
- **Provider capability declaration + a comments capability, proven on `jira-work-item` (FACTORY-23, implementing FACTORY-20).** `supports(ref, capability)`/`capabilitiesOf(ref)` (`src/resources/capabilities.ts`) let calling code ask which of `query`/`read`/`snapshot`/`comments`/`links`/`createTask` a resource's provider actually supports today, across all eight resource providers (`jira-work-item`, `jira-project`, `jira-idea`, `confluence-page`, `github-issue`, `zendesk-ticket`, `filesystem`, `webpage`) — additive only, no existing query/read/links code was rewritten. Invoking an unsupported capability throws the typed, programmatically detectable `UnsupportedCapabilityError` (carrying `provider`/`capability`), never a silent no-op or a generic `Error`.
- **`readComments`/`addComment` (`src/resources/comments.ts`), a canonical `Comment` shape, implemented for `jira-work-item` only**, reusing `AtlassianClient`'s existing native comment methods (`allComments`/`addComment`) with no duplicate Jira comment logic — oldest-first, paged and capped by the existing `allComments` behaviour. Every other provider (including `jira-idea` and `zendesk-ticket`, which already have their own working comment code, and `jira-project`, which has no native "project comment" concept at all) declares `comments` unsupported through the same mechanism; wiring them in is a follow-on story (FACTORY-21).
- See `docs/provider-capabilities.md` for the full 8×6 inventory (actual status per provider × capability, with code pointers) and every deviation from the original handoff design this story's contact with the real codebase forced.
