### Fixed
- **`test/unit/merge-check-guard.test.ts` now covers `briefs/project.md`, which it had never built, read, or asserted against (BUTCHR-149).** The guard's brief channel was a literal four-element issue-type array (`["Epic", "Story", "Task", "Bug"]`); the project tier is a separate, non-issue caller (`buildWorkspace({ issuetype: "project" })`), so it was silently absent from both the guard's coverage and its `EXCLUSIONS` list — indistinguishable from "covered" until someone checked. This already caused a real miss: while delivering BUTCHR-135's correction to the stale-approval protocol text, `briefs/project.md` was the one channel that did not receive the sha-transcription caveat that `briefs/story.md` and `briefs/epic.md` received in the same change, and the full (then-green) suite could not have caught it.
- `src/agents/workspace.ts` now exports `knownBriefTypes()`, the keys of `briefFor()`'s own type→template table. The guard's `briefChannels()` derives its issue-type list from this export (plus one hardcoded `"Bug"`, standing in for any type nobody explicitly mapped) instead of hand-copying a parallel list — the same shape of drift that let `briefs/project.md` go uncovered when the `project` entry was added to `briefFor()`'s table but not to the guard's own list.
- The project tier never merges a PR of its own, so it correctly stays out of `MERGE_INSTRUCTING_BRIEFS` (which asserts the author-side stale-approval check: `reviews[].commit.oid`, last-decisive-review ordering, the base-merge caveat). Instead, a new, narrower assertion checks the reviewer-side instruction `briefs/project.md` actually carries: the `[review] APPROVED|CHANGES_REQUESTED <pr-url> @ <sha>` line format it sends down to an epic, and the caveat that the sha must be pasted verbatim from `gh pr view --json headRefOid`, never retyped by hand.
- Mutation-verified: deleting the transcription caveat sentence from `briefs/project.md` turns the new assertion red; restoring it turns the suite green again.
