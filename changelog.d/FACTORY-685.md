### Fixed
- **v0.28.0 first-run template hotfix (FACTORY-685, implementing FACTORY-684/681, agentsafety F1, audits #49/#50) — eight items in one PR:**
  1. The first-run seed (`src/rules/seed-first-run.ts`) now writes `ui-first-rule` with `execution: "swarm"` instead of `"singleton"` — the shape its `brief: "@builtin:task"` (per-ticket, `jira_get_issue`/`ask_boss`/merge-its-own-PR) is actually written for. A `singleton` + `@builtin:task` pairing handed a fresh-install user's first enabled agent a brief it structurally could not follow.
  2. `src/rules/rules-write.ts`'s `writeRuleEnabled`/`planRuleWrite` now refuse (409) ANY enable of a `swarm` rule without `confirm: true` ("enabling this rule will staff up to N tickets; resend with confirm"), independent of the existing 25-ticket scope ceiling and `BUTCHR_MAX_AGENTS` cap (both kept, unchanged, as an additional gate). The plan response keeps `requiresConfirm`/`scope` and adds `confirmReason` (`"unmeasurable-scope"` / `"scope-ceiling"` / `"swarm-enable"` / `"stop-restart"`) naming which gate fired — deliberately NOT a rename to `confirmRequired`/`reason`, since `requiresConfirm` already ships to the dashboard.
  3. The dashboard (`FirstRuleSetup.tsx`, the rules table's toggle via `RulesRoute.tsx`/`RuleToggleConfirmDialog.tsx`) now shows an explicit confirm dialog on ANY swarm enable — "This will staff up to N tickets: `<first 10 keys>`" — sent only after the user confirms, by trusting the server's own `requiresConfirm`/`confirmReason` rather than re-deriving the condition client-side.
  4. (L1) `seedFirstRunRules` no longer seeds into a rules directory that already holds OTHER state (e.g. `session-definitions/`, `secrets/`) but no `rules.json` and no `.bak-*` — a new `"config-dir-not-empty"` outcome logs a warning and raises a non-deduped ops alert instead.
  5. (L2) `createRulesFileExclusive` (`src/rules/write-rules.ts`) no longer `chmod`s an EXISTING rules directory in either direction — a pre-existing `0755` dir is no longer silently narrowed to `0700`, and a pre-existing `0500` dir is no longer widened to `0700` (that write now correctly fails closed instead). A pre-existing dir already wider than `0700` surfaces a `dirPermissionsWarning` the daemon logs.
  6. (L3) The entire `seedFirstRunRules` body — not just the write — is now wrapped in one `try`, so a directory sitting at the rules path, an unreadable file, or any other `io` failure (`ENOTDIR`/`EACCES`) reports `"seed-failed"` instead of throwing out of the daemon's own startup.
  7. Stale "singleton"/UI-editable-brief wording fixed across `seed-first-run.ts`, `README.md`, and `changelog.d/FACTORY-669.md`.
  8. (N4) The scope-measurement cache (`createScopeCache`) is now keyed by rule id PLUS a hash of the query text (previously id alone — a widened query within the 10s TTL answered with the STALE scope), and is cleared on every write/reload (`src/daemon/index.ts`'s `rulesWriteDeps.reload`, `reloadRulesNow`, and the `SIGHUP` handler all call its new `clear()`).
