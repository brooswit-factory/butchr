### Added
- **`get_doc` accepts an optional caller-controllable `offset`/`limit` range read, so a document too large for one MCP result can be read in full across as many calls as it takes — including the largest document on this surface, a project's root doc.** Both are in CHARACTERS (JS string `.length`, i.e. UTF-16 code units — the same unit every `size`/`slice`/`offset` figure uses). `offset` defaults to 0; `limit` defaults to a conservative `DEFAULT_GET_DOC_LIMIT_CHARS = 20000` (a guess about the calling harness's own result-size cap, not a server maximum — an explicit `limit` is honoured verbatim, however large). `offset`/`limit` shape violations (non-integer, negative offset, non-positive limit) and `offset` past the document's own size are refusals, not silent clamps.
- **The hit arm now carries three states instead of one, discriminated by a new `complete` field, with `version` and `size: { chars, bytes }` added to every hit.** `complete: true` is additive-only over the old shape — every field an existing caller reads is present and unchanged, and `body` is still the whole document. `complete: false` (the new state, `{ found, complete: false, id, url, title, version, size, slice: { offset, chars, bytes }, next?: { offset }, chunk, warning }`) is a bounded window: **`body` is present if and only if `complete` is true — a partial's content lives under a different field (`chunk`), never `body`.** This is safety-critical, not cosmetic: `set_doc` is a full-body replace, and the taught workflow is "call `get_doc`, edit the body you got back, write the whole thing" — a partial that populated `body` would let a caller unaware of pagination write a truncated body back and permanently destroy the rest of the document in a corpus where nothing is ever archived. With `body` structurally absent on a partial, that same caller gets `undefined` and fails loudly instead. A caller knows it is finished paging when `next` is absent (never by checking `complete`, which stays `false` on every slice of a partial read including the last one); concatenating every `chunk` in offset order, from 0 until `next` is absent, reproduces the stored body exactly. The bound never splits a UTF-16 surrogate pair — the boundary nudges rather than emitting lone surrogates, and `slice.chars` reports the actual (possibly nudged) length rather than echoing the requested `limit`.
- **Both `get_doc` dispatch branches — an issue's own doc and a project's root doc — implement the identical three-arm contract**, pinned by a full arm/refusal test matrix (not-found, fits-entirely, empty-body, does-not-fit with an explicit `"body" in result === false` assertion, exact-concatenation round trip using content where chars/bytes diverge, astral-character boundary nudging in both directions, explicit-limit-honoured-verbatim, offset-at-the-end, and every refusal) mirrored for both branches. The bound lives in the tool-facing layer (`getDoc`/`getProjectDoc`), not in the shared page-resolution helpers those internal, non-tool code paths also call using only the page id.
- `get_doc`'s tool description is rewritten to document the new parameters, the three-arm shape and how to tell them apart, the `body`-present-iff-`complete` safety rule and why, and that pagination finishes when `next` is absent.
- **Live-checked against real Confluence, using the branch's own code (not the MCP surface, which does not run an unmerged branch):** the `BUTCHR` project's root doc (57,791 real characters, genuinely over the measured oversize bracket's low end) was paged end-to-end at the production default (`limit: 20000`) in 3 calls; every serialised result stayed at or under 20,673 characters — well clear of the bracket — and the concatenation of every chunk matched an independent unbounded read exactly. A scan of the 100 most-recently-updated Story/Epic/Task tickets plus every other product project's root doc found no ticket doc currently large enough to exercise the partial arm at scale (closest: 54,819 characters) — stated here as a non-result for the issue branch specifically, not claimed as demonstrated; the issue branch's partial-arm correctness rests on the unit tests instead.
