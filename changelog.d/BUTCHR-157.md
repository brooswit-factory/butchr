### Added
- **A description-header registry (`src/headers/registry.ts` + `src/headers/header-scan.ts`), the same "declared, not merely implemented" shape `src/labels/registry.ts` already holds Jira labels to (BUTCHR-133/BUTCHR-143), extended for the first time to a second medium (BUTCHR-150/BUTCHR-151).** A type-level door (`DescriptionHeaderKind`, `HEADER_REGISTRY: Record<DescriptionHeaderKind, HeaderRegistryEntry>`) forces a registered withdrawal owner — `withdrawnBy` non-empty prose, or `withdrawnBy: null` with a required `neverWithdrawnReason` — for every header kind the codebase bakes into a ticket description; a source-scanning secondary net (`scanDirForHeaderTagLiterals`, run for real against `src/` in `test/unit/header-registry.test.ts`) catches a header block built entirely outside that type. The scanner matches the SHAPE of a header opening line (a bracketed, all-caps tag — `/^\[[A-Z][A-Z0-9_]*\]/`), not today's literal `"[ORPHAN]"` text, specifically so a future header with a different tag is still caught without anyone touching this scanner — the identical trap `label-scan.ts` already documents for `agent:*`/`pr:*` labels built by concatenation, deliberately not repeated here.

### Fixed
- **`adopt_worker` (both `adoptWorker` and `adoptProjectWorker`) now retires the `[ORPHAN]` description header — baked into a ticket by `file_where_it_belongs` — in the SAME call that already withdraws the `butchr:orphan` label, for BOTH dispositions, not gated on the `alreadyAdopted` idempotence check.** Before this: `adopt_worker` made every sentence of the header false (*"this ticket has no boss... nobody owns it"*) while withdrawing the label right next to it — one fact, two media, one withdrawn by machine, one left lying, forever, with nothing able to detect it. Measured live: BUTCHR-144 carried exactly this header after adoption and had to be repaired **by hand** with `correct_worker`, because no machine path existed. That hand-repair is now unnecessary going forward.
- The header is retired **surgically**: the stale `[ORPHAN] ... nobody owns it` block is replaced with a truthful `[ADOPTED]` successor line naming the new boss (never blanked — the `[unwritten]` Confluence doc-title marker is the model this follows: a solved medium replaces the stale assertion with a true one, it does not delete it), and everything below the header is preserved untouched. The retired header's exact text is archived first, under its own `[header-withdrawn]` marker (deliberately distinct from `correct_worker`'s `[correction]` — this fires automatically on every orphan adoption as a declared consequence of gaining a boss, not a human judgment call that the old text was wrong).
- **Refuses to guess, on purpose, in three cases** — a header absent (the common case: silent no-op, zero extra Jira calls), hand-edited (opening line present, closing line missing or altered), or appearing more than once — reporting why via `AdoptWorkerResult.orphanHeaderNotWithdrawn` rather than corrupting the description. A failure at the write itself (the archive comment, or the rewrite) is reported the same way and **never blocks or corrupts the rest of the adoption** — the ordering/partial-state discipline `adopt_worker`'s own doc comment already holds every other secondary concern to.
- **"Byte for byte" is honoured at the granularity this codebase's one description-replace primitive (`AtlassianOps.correctText`) actually offers**: it always re-wraps whatever plain text it's given as a single ADF paragraph — a pre-existing property of `correctText` itself, not something this change introduces, and the same collapse every `correct_worker` call has always produced. The flattened plain text below the header is preserved character-for-character; a freshly-filed orphan (the case this fix acts on) round-trips with zero loss, since `file_where_it_belongs` itself already builds the whole description as one plain string wrapped in exactly one ADF paragraph.
- **Tickets adopted before this fix are NOT retroactively repaired**, decided explicitly rather than left to be discovered later: the one concretely known instance (BUTCHR-144) is already hand-repaired, there is no reliable, label-based way to find any others (the label side already cleared, which is why the header alone stays stale), and rewriting an unbounded, unowned set of other tickets' descriptions from inside one Task's scope is a wide-blast-radius action this ticket does not take unilaterally. See `src/tools/relationship.ts`'s "THE RETROACTIVE QUESTION" comment for the full reasoning.
