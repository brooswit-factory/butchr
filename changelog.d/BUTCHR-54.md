### Added
- **A running daemon now reports the build it is actually RUNNING — sha, version, start time, pid, unit and journalctl command — and `scripts/audit-alias-calls.ts` prints it per daemon it discovers (BUTCHR-54).** Previously nothing outside a butchr daemon could say which build it was running; the only ways to guess were indirect (a behavioural side effect, an endpoint's shape changing, or reading `/proc/<pid>/cwd`'s checkout HEAD — which answers "what does the filesystem say NOW", not "what did this process load at start"). `/health` gains a `build` field, a SIBLING of `components[]` (never an entry inside it — `ok` is a liveness AND, and a daemon not knowing its own sha is not thereby unhealthy): `{ sha, shaProvenance, shaDirty, shaUnknownReason, version, startedAt, pid, unit, journalctl }`. Captured exactly ONCE, at this process's first import of `src/agents/build-identity.ts` (module singletons are cached by the runtime) — never re-read per request, which is the exact live-read mistake this ticket exists to close.
- **The design decision, in writing:** two launch paths, both must be truthful. `bun run src/daemon/index.ts` (`start`) runs from source with no build step, so nothing can be baked in — it reads `git rev-parse HEAD` (and `git status --porcelain` for a dirty flag) ONCE at process start, from `src/agents/build-identity.ts`'s OWN resolved file location (`import.meta.url`, never `process.cwd()` — a systemd unit's `WorkingDirectory=` can point anywhere; `git` itself then searches upward for `.git`, so this is correct from any nesting depth). `bun run build` (`scripts/build/build.ts`, replacing the old one-line `bun build` CLI invocation) is a real build step, and the published npm package ships only `dist/` (`package.json`'s `files`) — no `.git` anywhere near an installed daemon — so this bakes the sha (and dirty flag) into the bundle via `Bun.build`'s `define`, matching the literal `process.env.BUTCHR_BUILD_SHA`/`BUTCHR_BUILD_DIRTY` member-expressions `resolveSha`'s caller uses on purpose (an indirect `env.X` property read would never be matched by `define` — verified against the real bundler, not assumed). A baked value always wins when present (the stronger claim — frozen before the process started); the from-source git read only runs when nothing was baked, so a bundled daemon never pays for a git spawn it doesn't need.
- **Provenance rides along, not just the sha.** `shaProvenance` ("baked" vs. "git-at-start") and `shaDirty` let an operator tell a build-time guarantee apart from a live-at-start read of a possibly-uncommitted tree — two genuinely different-strength claims. `version` comes from a real `import … from "../../package.json"` resolved relative to the importing file (correctly inlined by the bundler for the dist path, correctly resolved live for the from-source path — no cwd-dependent read either way). "unknown" is a first-class, explicit answer, never a guess: an empty baked sha falls through to the from-source git read, which also correctly fails (no `.git` near an npm install) and ends in `sha: null` with a stated `shaUnknownReason` — never a fabricated default.
- **The consumer keeps the two axes separate.** `scripts/audit-alias-calls.ts` already reported per-daemon journal readability; it now also reports build identity (sha/version/uptime/pid) per daemon, from the SAME `/health` probe it already made for liveness (no second, divergent round trip) — via `decideBuildIdentity`. The two are independent: a daemon can be journal-readable and build-unknown, or the reverse, and neither masks the other in the printed report. THE CASE THAT IS LIVE TODAY (deploy-on-merge is off for this epic, so merging this ships no restart): every daemon already running on a host predates this field entirely, and now renders as an explicit `build: unknown — this daemon does not report a build identity; it predates the field, or is running an older build` line — never a blank column, never silently omitted, and never folded into the existing journal-readability verdict (`computeVerdict`'s CONDITION_MET/NOT_MET/INCONCLUSIVE logic is unchanged; build identity is additive display only).
