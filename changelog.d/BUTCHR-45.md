### Fixed
- **An `ANSWER` directive sent as the entire comment body now parses even with the identity tag `jira_add_comment`/`tell_worker` prepend.** `parseDirective` (`src/agents/escalate.ts`) previously matched `ANSWER ` only at the very start of a trimmed line, so the terse, system-recommended reply `ANSWER 2 abc12345` — the form the escalation comment itself asks for — arrived as a single line reading `[KEY] ANSWER 2 abc12345`, never matched, and was silently dropped: the comment posted successfully and the blocked agent stayed blocked, with no error anywhere (BUTCHR-44). The parser now strips a tag-SHAPED prefix (`[A-Z]+-\d+`, matching how Jira issue keys look — never a hardcoded key, since the parser has no way to know the caller's) before matching, and applies the pre-existing `[butchr:blocked]` self-comment guard to both the raw and the tag-stripped text. The escalation comment's own instruction text is updated to say a leading identity tag is expected and handled. Fixed in the parser only — `jira_add_comment` and `tell_worker`'s tagging behavior, and every other marker/directive in the codebase, are unchanged (checked: `[butchr:respawn]`, `[review]`, `[ask]`, and the other blocked-dialog/parked-ticket markers are never matched against a tagged comment today, so none shared this exposure).
