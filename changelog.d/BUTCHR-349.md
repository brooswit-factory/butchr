### Fixed
- **The daemon's log sink now flattens non-string `console.error` arguments too, closing the gap its own doc comment claimed away (BUTCHR-349).** `installLogSink` (`src/daemon/log-sink.ts`) previously flattened raw newlines only in string arguments, on the stated theory that "only a STRING can carry a raw newline into a line this daemon's own journal readers parse" — false for an `Error`: `console.error(err)` renders its message/stack with raw newlines intact and, before this fix, passed it straight through to the original writer, letting a second physical `journalctl` line masquerade as a genuine `[tools2]`/`[tools]` record. When every `console.error` argument is a string, behavior is unchanged; when any argument is not a string, the whole argument list is now rendered with `util.format(...args)` (the same primitive the original writer already uses to combine/format arguments) and the single resulting string is flattened before it reaches the writer. `log-sink.test.ts`'s old "a non-string argument passes through unmodified" test — which pinned the gap as intended behaviour — is replaced with one driving a multi-line `Error` through the real sink to a real `Console` bound to a real stream, asserting no physical line parses as an outcome record.
- Documents a stated, un-fixed limit next to `installLogSink`: the runtime's own printer for an uncaught exception or unhandled rejection writes to `stderr` directly, bypassing this wrap, so a crash's own message can still forge a physical line — a reader should treat journal lines near a crash/restart as unverified until corroborated elsewhere.
