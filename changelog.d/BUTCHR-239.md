### Fixed
- **`get_doc_comments` now returns plain text instead of raw storage-format XHTML (BUTCHR-239).** `AtlassianOps.getPageComments` correctly returns raw storage-format XHTML (`bodyFormat: "storage"`), but the handler handed that straight back with no unwrapping — so a peer message's `[butchr:peer from=... to=... intent=...]` marker actually arrived as `<p>[butchr:peer ...` and any `&`/`<`/`>` in the text came back entity-escaped (e.g. `<->` as `&lt;-&gt;`). Measured live: 0 of 19 rows on BUTCHR's own root doc began with a bare `[`; all 19 began with `<p>`. Fixed by applying the SAME `unwrapStorageParagraph` the write side's wrapping (`tell_peer`/`speakOnOwnChannel`) already has as its exact inverse (src/tools/speak.ts) — no second unwrapper. The tool description now states the representation explicitly; every other claim in it (NEWEST-COMMENT-ORDER NOT GUARANTEED, the BUTCHR-198/BUTCHR-202 numeric-id-sort warning) is unchanged.
- The prior test fixture (`docCommentsRig({ "1": [{ id: "10", body: "hello from a reviewer", ... }] })`) handed back plain text, so it could not distinguish a reader that unwraps from one that doesn't — this exact defect had already passed two reviews for that reason. New tests build their fixtures from what the real writer (`escapeStorageText` + the `<p>...</p>` shape) actually produces, covering: a `tell_peer`-shaped body reading back with a bare `[butchr:peer ` prefix and literal (not entity-escaped) `<->`; round-trip identity between `escapeStorageText`/`unwrapStorageParagraph`; a non-`<p>`-wrapped (human) comment passing through sensibly; `id`/`author` arriving intact with `author` absent (never a placeholder) when unreadable; and exactly-once unwrapping (a body whose ORIGINAL plain text itself contains an entity-looking literal like `&gt;` must survive unchanged — unwrapping twice would silently rewrite it to `>`). Mutation-tested: with `unwrapStorageParagraph` removed from the handler, `a tell_peer-shaped body reads back so body.startsWith('[butchr:peer ') is true and '<->' is literal, not entity-escaped` and `id and author still arrive intact, and author is still absent (not a placeholder) when the source has none` both fail by name; with the handler applying `unwrapStorageParagraph` TWICE, `exactly-once unwrap: a body whose ORIGINAL plain text itself contains an entity-looking literal ('&gt;') survives the round trip unchanged` fails by name, alone. Restoring the single-unwrap fix turns all three green again.
- **Placement is deliberate, not incidental: the unwrap lives ONLY in `get_doc_comments`' own handler (defs.ts), never in the shared `getPageComments` op or `atlassian-real.ts`.** `createOwnChannelComments` (src/tools/speak.ts) already maps its own caller's rows through this same `unwrapStorageParagraph` — putting the inverse in the shared op as well would double-unwrap that path and silently corrupt a caller's literal (verified: a stored `<p>the arrow renders as &amp;gt; in storage</p>` correctly single-unwraps to `the arrow renders as &gt; in storage`, but a second unwrap turns it into `the arrow renders as > in storage` with no error on either side).
