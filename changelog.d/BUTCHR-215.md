### Added
- **New `tell_peer(peer, text, intent)` verb: a PROJECT caller can now send a message to a named peer project (BUTCHR-185/BUTCHR-215).** The write half of "two projects can talk sideways" — `list_peers` (BUTCHR-184/BUTCHR-188) is the enumeration half. Posts ONE footer comment on `peer`'s root doc, prefixed `[butchr:peer from=<caller> to=<peer> intent=<intent>] ` — authored by the tool, unconditionally, so no caller input (including text that itself starts with `[butchr:peer …]`, or leading whitespace/newlines) can suppress or displace it. `intent` is required, exactly one of `request`/`accept`/`decline`/`notice` — no default, no fifth value; `decline` additionally requires `text` to state a real reason (refused when empty, whitespace-only, or a placeholder like "n/a"/"tbd"/"no"). Refuses an ISSUE caller, a self-send, and a `peer` that is not an eligible peer (unknown key, not live, not led by this credential, or missing a readable `butchr` property) — naming the peers that DO exist, from the same `resolveEligibleProjects` resolver `list_peers` uses (never a second eligibility rule, never the staffing allowlist). The peer's root doc is resolved fresh at send time, never a page id cached from an earlier `list_peers` call. Advances no `wake.comment` watermark, for either side — this verb intentionally does not reuse `speakOnOwnChannel` (which advances the CALLER's own watermark), since doing so for the recipient would mark this very comment already-seen before the recipient ever wakes on it. Posts a comment — that is all it does and all it claims: delivery is durable (the comment is never lost) but the WAKE it can trigger is best-effort, because Confluence footer-comment ids are not monotonic with creation time and the project wake path's MAX-id watermark comparison can silently miss a comment whose id lands below the recipient's current max (BUTCHR-195, not this verb's to fix).
