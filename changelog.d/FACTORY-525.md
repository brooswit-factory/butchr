### Fixed
- **The `[resume] KEY failed` journal line, and the respawn comment built from it, now carry the reason a relaunch failed instead of nothing at all (FACTORY-525).** Observed live during the manager switch: `unity-manager`'s pinned rule failed a `resumeInPlace()` relaunch, and the only trace was `[resume] jira-project:unity-manager:GK failed` followed by a respawn notice reading "session lost: resume failed (the relaunched session did not stay alive — see the pane for details)" — nothing said WHY.
- `HerdrHerd.resumeInPlaceExclusive` (`src/agents/herd.ts`) now records a reason at every `"failed"` return point: the herdr error's own message when the relaunch attempt itself was rejected (`agent_name_taken` or any other `agent.start` failure against an already-confirmed-empty pane), or the literal `"no exit status captured"` when herdr accepted the launch and Claude simply didn't stay up with nothing thrown — herdr exposes no exit code for a pane's process, so that string is the honest ceiling, not a gap. The `[resume]` log line now appends `— <reason>` for a `"failed"` outcome, same "free text last" placement `[spawn]`'s own tag already uses.
- The reason is also readable through a new optional `Herd.lastResumeFailureDetail(issue)` accessor — read-once, mirroring `resumeInPlace()`'s own outcome — which `reconcileNow` (`src/daemon/loop.ts`) now reads to build its respawn comment, so an operator reading either the journal or the ticket sees the same reason. `scopedHerd` forwards it explicitly, the same way `providerOf` already is, so production's real reconcile path actually reaches it rather than silently dropping it the way FACTORY-426 found `resumeInPlace` itself once was. A fake `Herd` that implements `resumeInPlace` but not this new optional accessor degrades to the same explicit `"no exit status captured"` fallback rather than a silent "see the pane for details".
- The stop-then-fresh-spawn fallback itself is unchanged: only the reason text describing why it fired changed.
