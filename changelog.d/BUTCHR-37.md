### Added
- **`file_where_it_belongs` — the successor to `jira_create_issue`'s `implements: "none"` deliberate-orphan escape (BUTCHR-37, per the settled glossary — https://wroosbit.atlassian.net/wiki/spaces/BUTCHR/pages/12484678).** Files a ticket that is explicitly NOT the caller's — genuine out-of-scope work a brief tells an agent to file outside its own epic — and, unlike the alias it succeeds, cannot be called without saying where the work belongs: filing a ticket outside your own scope was always only half the job; this makes stating the other half a REQUIRED `destination` argument instead of a convention nothing enforces. `destination` is either an existing EPIC KEY the work belongs under, or a short prose reason a brand-new epic is needed — both legitimate, neither a fallback for the other. An empty/whitespace destination, a known placeholder ("n/a", "tbd", "unknown", "none", "?", "-", "idk", and near-misses after normalizing case/whitespace/trailing punctuation), a Jira-key destination that doesn't exist, or one that exists but isn't an Epic (naming what it actually is), and prose too thin to be a real reason are all refused with a message that teaches: what's wrong, what a good destination looks like, both accepted shapes, and why it's asked at all — worded so an agent mid-task, slightly guilty about scope, doesn't read the refusal as an obstacle to route around.
- **The destination is recorded on the created ticket itself, not only in a comment.** It lands as a header block baked into the ticket's own description in the SAME create call, alongside a new `butchr:orphan` label — a one-line JQL filter away from "show me every undirected ticket" — so a human opening the orphan cold six weeks later reads it in the description, not comment #7. The ticket is filed To Do, staffed by role exactly as the alias staffs it today, and takes NO disposition parameter (an argued omission: a disposition answers "what happens to MY worker", and nobody can answer that for a ticket that by definition isn't the caller's) — it waits for a future boss to `adopt_worker` it. Never carries the shelved-exemption label: the parked-ticket detector only ever walks tickets reachable by an Implements link, and this ticket has none, so that label would mean nothing here.
- **A notice is pushed to where a person actually is, using only tools humans already use — a Jira comment on a ticket a human already watches, never a new triage page** (a standing "every undirected ticket" page was considered and rejected: it's pull, not push, and its whole premise — that someone was told to go look — is exactly the property that failed on 2026-08-30, when three stories were orphaned by the very epic created to stop orphaning). Case A (destination is an epic key): the notice comments on that epic, reaching its agent (which can `adopt_worker` the ticket) and its human watchers via Jira's own notifications. Case B (destination is a "needs a new epic" reason): there's no epic to comment on and this daemon has no configured human/root key, so the notice walks UP the CALLER's own Implements chain to the topmost ticket (an Epic, by construction) and comments there — the same terminal the parked-ticket detector already escalates to. **Case B creates NO link.** The comment says where the filer thinks the work belongs; it does not make it so — quietly re-parenting an orphan onto whatever it lands near would be exactly the suppression this escape exists to prevent.
- Write order: create (destination header + `butchr:orphan` already baked in) first and irreversible, then a best-effort notice, then `ensureDoc` (unchanged behavior — a bossless ticket already bottoms out under the project root doc). Unlike `new_worker`, there is no "worst survivable state" to roll back from — this ticket never gets a boss link at all — so a throw after creation always means the ticket itself needs no cleanup; the error names exactly which of the notice/doc failed and how to complete it by hand.
- `jira_create_issue` is otherwise unchanged this release — `implements: "none"` still works exactly as it did — but its description no longer claims to be the ONLY way to file a deliberate orphan, since that became false the moment this verb shipped; it now points to `file_where_it_belongs` as the preferred route.
- Named `file_for_another_boss` during design; renamed to `file_where_it_belongs` before shipping because the old name asserted there IS another boss, which is false in the "needs a new epic" case — one of the verb's two legitimate destinations.
