### Fixed
- **A project's own `tell_worker` comment to one of its In-Review epics no longer wakes that project on the next poll (BUTCHR-292/BUTCHR-328) — the epic axis's own version of the self-wake HAZARD 1 already closed for the comment axis.** `projectVerdict`'s epic axis treats a comment observed on an In-Review epic as active until that project's own watermark has recorded the id as seen; `tell_worker` — the ONLY way a project speaks down to one of its own epics, carrying the `[review] APPROVED/CHANGES_REQUESTED` line, an `ANSWER`, a correction, or a ratification — wrote no watermark at all before this change, so the review hop woke its own writer every time. `tellWorker` (`src/tools/relationship.ts`) now advances the caller's own `wake.epicsSeen[workerKey]` set to include the comment id it just posted, immediately after `ops.addComment` succeeds, reusing `assertOwnWorker`'s own fetch for the epic's current status (no added Jira call).
- **The write is a PARTIAL, per-key UNION, never `check_in`'s complete-observation key-set REPLACE.** `advanceProjectWatermark` (`src/resources/project.ts`) gains a new, explicit `patch.epicsPartial` field, structurally distinct from `patch.epics`: for each key present, its ids are unioned into whatever is already stored for that key (creating the key if absent), and every OTHER stored epic key is left byte-for-byte untouched — never inferred from the patch's shape or size. Routing this write through `patch.epics` instead would have wiped every other In-Review epic's seen set on every suppression write (fixing one self-wake by manufacturing many); pinned by a test that proves the two patch shapes actually behave differently (a mutation check, not just an assertion that the correct shape works).
- **The suppression write only fires when the target epic reads "In Review" right now.** `projectVerdict` treats an epic key absent from the stored map as "never acted on this review episode" — the signal a fresh entry into review needs to stay observable, restored on re-entry by `check_in`'s own key-set replace. Creating that key is a real, stated behaviour change (the project genuinely just acted on the epic while it was in review), but seeding it for an epic that is NOT currently In Review would instead consume a FUTURE episode's fresh-entry signal before that episode begins — the same hazard with worse consequences, so `tell_worker` to an epic outside review still posts its comment unconditionally; only the watermark write is gated on status.
- **The suppression keys on nothing but write identity — never the comment's author, never a content marker.** The daemon and every tier post under the same Atlassian account (`author` is genuinely absent when unreadable), and a `[review]`/`[butchr:...]`-shaped prefix is reader-facing only; a comment written by anyone else on the same epic still wakes the project exactly as before — pinned by a dedicated test that fails if the suppression widens.
- **Fail-open, reusing (not duplicating) the existing DEFECT 1b in-process pending-watermark fallback (PR #280 / BUTCHR-214-226).** A rejected watermark write never fails the `tell_worker` call that already landed a real comment. The fallback (`pendingWatermarkFallback`, `src/resources/project.ts`) and its read-side merge (`mergePendingFallback`) are extended to also carry a per-epic seen-ids map, merged by the same per-key union discipline — the map's own doc comment previously stated it deliberately never touched `epicsSeen`; it now does, for both writers that touch that axis.
- **The issue tier is unaffected — confirmed by reading its own mechanism, not assumed.** An issue caller's `tell_worker` (e.g. an Epic telling its own Story) never reaches this write at all: the issue tier uses a separate, pre-existing in-memory per-key newest-comment cursor (`src/resources/issue.ts`), fail-open, reset on restart, never the project property. Pinned by a test asserting zero project-watermark calls from an issue caller even when the comment carries an id and the target reads "In Review".
- **Out of scope, stated rather than silently widened:** the comment and root-doc-version axes (closed by PR #280); the per-epic READER's pagination (BUTCHR-256's, unchanged — this PR owns only the WRITE side, marking the project's own comment seen); comment ordering and the stored fields' meaning (BUTCHR-195/199/227); reader-visible peer/boss marking (BUTCHR-183's); the issue tier's own cursor (confirmed unaffected, not modified).
