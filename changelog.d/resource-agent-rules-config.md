### BREAKING

- **Resource-agent rules replace the issue-type and project tiers.** The daemon no longer staffs every assigned In Progress/In Review ticket by issue type, and no longer runs project agents or the project poll loop. It staffs exactly what enabled rules match: one agent per (rule, matched Jira ticket), stopped when the rule's query stops returning the ticket. There is no compatibility mode and no second loop.
- **Rules come from a config file outside the repo:** `BUTCHR_RULES_FILE`, else `$XDG_CONFIG_HOME/butchr/rules.json`, else `~/.config/butchr/rules.json`. A file whose `rules` array is empty (or all disabled) staffs nothing. When no file exists there are zero rules and nothing is staffed (announced at startup; nothing is written) — there are no built-in default rules or templates. A malformed file stops the daemon at startup with every problem listed.
- **New agent identity and workspace layout.** Agents are keyed `jira-work:<ruleId>:<ISSUE>` and work in `<workspace root>/jira-work/<ruleId>/<ISSUE>`. Legacy `<workspace root>/<ISSUE>` workspaces and their agents are never stopped, adopted, or rewritten (including by `correct_worker`'s summary rewrite). The reaper can still close a leftover herdr workspace at a legacy path once no agent is running there; the directory on disk is kept.
- **MCP identity gains `x-butchr-agent`.** `x-issue` still names the ticket for every tool; rule agents also send their agent key, which scopes channel pushes and own-write echo suppression to the one agent, so two agents on one ticket hear each other's writes.
- **`stand_down` and `check_in` no longer affect staffing.** Both tools still run, but declare nothing; `stand_down` now answers `asleep: false` with a note instead of claiming a sleep and pane release that never happen. Per-agent sleep under rules is not implemented yet.

### Added

- Rule queries read every page of Jira results (`nextPageToken`). A query matching more than 1000 issues, or a response that cannot prove it is complete, fails the whole poll instead of reading the missing tickets as having left the query and stopping their agents.

- Rule schema: `id`, `enabled`, `resourceProvider` (`jira-work`), `query`, `brief`, ranked `agentPreferences` (`harness` claude/codex/agy, optional `model`/`effort` — the first preference naming a harness sets its model and effort), and `relationships` (`childRule`, `inwardConnectionRules`) that reference other rules by id.
- **Rule relationships route changes to listening rule agents (read-only).** An agent under rule `R` on ticket `B` is notified when a ticket `W` changes if some enabled rule `C` matching `W` is `R`'s `childRule` and Jira already has `W` implementing `B` (an `Implements` link), or `C` is listed in `R`'s `inwardConnectionRules` and Jira already has `W` and `B` joined by a `Relates` link. Links are read from either ticket. A worker never hears its boss and nothing routes down. `Relates` is symmetric in Jira, so the configuration alone sets direction: `C`'s agents do not hear `R`'s ticket unless `C` lists `R` too. A child rule over `Relates`, an inward rule over `Implements`, `Blocks` or other links, reversed `Implements` links, and tickets no rule matches route nothing. A listener hears one change once however many rules or links connect the ticket, and an agent's own write still reaches its listeners. Butchr does not create or edit links.
- **`github-issue` rules.** A rule may name `resourceProvider: "github-issue"` with a GitHub issue search query (select issue types with `type:Bug`, `type:Feature`, `type:Task`). Each match is keyed `github-issue:<ruleId>:<owner/repo#number>` (owner and repo lowercased) and would work in `<workspace root>/github-issue/<ruleId>/<owner%2Frepo%23number>`. Searches are read-only, reuse `GITHUB_TOKEN_FILE`, and stay inside `BUTCHR_GITHUB_ORGS` (or `repo:` qualifiers within those orgs); every search adds `is:issue` and drops pull requests. Queries asking for pull requests, naming `org:`/`user:`/`owner:`, or using `AND`/`OR`/`NOT` or parentheses stop the daemon at startup, as do relationships on a `github-issue` rule and relationships between rules of different providers. They are staffed by a second rule loop (polling once a minute) only when `GITHUB_TOKEN_FILE` and `BUTCHR_GITHUB_ORGS` are set and every enabled `github-issue` rule's query stays inside those orgs; otherwise none of them runs, nothing is spawned for one, and the daemon says why at startup while Jira rules run as usual. The two loops share the host admission cap and never stop each other's agents. A `github-issue` agent identifies to MCP with `x-butchr-agent` alone (no `x-issue`; a connection sending both is refused) and gets two tools that act only on its own issue: `github_get_issue` (title, body, issue type, state, labels, every comment) and `github_add_comment` (tagged `[butchr <rule>]`). Both re-read the issue first and refuse a pull request, an issue that moved to another repo, or an owner outside the configured orgs. Jira and Confluence tools refuse `github-issue` agents, and the GitHub tools refuse every other caller. It is nudged when its issue's state, comments, title, body, labels or type change, but not about its own comment. `GITHUB_TOKEN_FILE`'s token needs permission to comment on those repos. Not wired for GitHub agents yet: labels, stall/parked/abandoned detection, respawn and crash-loop notices, session-limit recovery, blocked-dialog escalation, and dashboard ticket details. `jira-work` staffing never touches a `github-issue` agent.
- **`jira-idea` rules, and ideas are never work.** A rule may name `resourceProvider: "jira-idea"` with JQL. It staffs only issues Jira proves are Product Discovery ideas — issue type `Idea` in a project whose type is `product_discovery` — one agent per (rule, idea), keyed `jira-idea:<ruleId>:<KEY>` in `<workspace root>/jira-idea/<ruleId>/<KEY>`. **`jira-work` rules now skip those ideas, plus any issue of type `Idea` whose project type is not `product_discovery` or cannot be read, and any other issue in a `product_discovery` project**, however broad their JQL. Neither kind of rule staffs those half-proven issues, and each skip is logged once. Jira searches now request each issue's `project` so the project type can be read. `jira-idea` rules share the Jira client but run in their own loop (every 15 seconds, only while an enabled `jira-idea` rule exists), with their own admission bucket under the host cap. That loop gets none of the work loop's label sync, stall/parked/abandoned detection, or respawn and crash-loop comments. Loops never stop each other's agents. A `jira-idea` agent identifies to MCP with `x-butchr-agent` alone (a connection that also sends `x-issue` is refused). It gets `jira_idea_get` (summary, description, status, labels, every comment) and `jira_idea_add_comment` (tagged `[butchr <rule>]`). Both act only on its own idea and re-read it first, refusing a moved key or anything no longer proven to be an idea. Jira work, Confluence and GitHub tools refuse idea agents, and the idea tools refuse every other caller. It is nudged, naming `jira_idea_get`, when its idea's status, labels, comments or summary change, but not about its own comment. A `childRule` on a `jira-idea` rule, or a relationship to one from another rule, stops the daemon at startup. JPD-specific fields (Impact, Effort, Goals, Insights, delivery progress) and idea↔work links are not read or written yet; see `docs/jira-idea.md` for what needs live proof first.
- **Ideas hear the GitHub issues they link to (read-only).** A `jira-idea` rule's `inwardConnectionRules` may now name `github-issue` rules, and only those. An idea agent is nudged when a GitHub issue changes (state, comments, title, body, labels or type) if its idea has a Jira remote issue link to that issue's `https://github.com/<owner>/<repo>/issues/<n>` URL and a rule its rule names currently matches the issue. A link to a pull request or any other URL, an issue matched only by rules it does not name, an inactive idea, a link being added or removed, and a change only to `updated` send nothing. The nudge names the issue and the reason, never GitHub text. Nothing routes from an idea to a GitHub agent. The idea loop reads each listening idea's remote links (`GET /rest/api/3/issue/{key}/remotelink`) every poll, but only while such a rule matches at least one issue. It reuses the GitHub loop's latest matches rather than searching GitHub again, so without GitHub staffing ideas hear nothing (warned at startup). A failed link read keeps that idea's last read and is logged once. Idea agents get `jira_idea_github_issues`, which lists their own idea's linked GitHub issues (ref, URL, link title and relationship) from Jira alone. Butchr creates no links, issues or ideas.
- **Agents can link an existing GitHub issue to an existing idea, on request.** A `github-issue` agent calls `github_link_jira_idea` with an idea key, or a `jira-idea` agent calls `jira_idea_link_github_issue` with a `https://github.com/<owner>/<repo>/issues/<n>` URL. The link is allowed only when a `jira-idea` rule currently matching the idea lists, in `inwardConnectionRules`, a `github-issue` rule currently matching the issue, and the caller's own rule is one of the two. Both resources are re-read first: the issue must still be an issue (not a pull request) inside `BUTCHR_GITHUB_ORGS` and not transferred, and the idea must still be a proven, unmoved idea. Pull request URLs, Jira URLs, GitHub refs in place of keys, and callers of the wrong provider are refused before anything is read. The link is a Jira remote issue link people can see on the idea (`POST /rest/api/3/issue/{key}/remotelink`, relationship "GitHub issue", titled `<owner>/<repo>#<n>: <title>`), with a fixed `globalId` per issue so Jira's create-or-update keeps retries and races to one link. If the idea already links the issue, by any link, nothing is written. A link removed in Jira is re-added only by another call. The tools exist only while both GitHub and idea rules are staffed. The Jira account needs Link issues permission on the discovery project. Nothing is written to GitHub, and no issue or idea is created or linked automatically.
