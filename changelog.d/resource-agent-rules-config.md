### BREAKING

- **Resource-agent rules replace the issue-type and project tiers.** The daemon no longer staffs every assigned In Progress/In Review ticket by issue type, and no longer runs project agents or the project poll loop. It staffs exactly what enabled rules match: one agent per (rule, matched Jira ticket), stopped when the rule's query stops returning the ticket. There is no compatibility mode and no second loop.
- **Rules come from a config file outside the repo:** `BUTCHR_RULES_FILE`, else `$XDG_CONFIG_HOME/butchr/rules.json`, else `~/.config/butchr/rules.json`. A file whose `rules` array is empty (or all disabled) staffs nothing. When no file exists at the default path there are zero rules and nothing is staffed (announced at startup; nothing is written). A `BUTCHR_RULES_FILE` that does not exist stops the daemon at startup instead of reading as zero rules and stopping every rule agent — there are no built-in default rules or templates. A malformed file stops the daemon at startup with every problem listed.
- **New agent identity and workspace layout.** Agents are keyed `jira-work:<ruleId>:<ISSUE>` and work in `<workspace root>/jira-work/<ruleId>/<ISSUE>`. Legacy `<workspace root>/<ISSUE>` workspaces and their agents are never stopped, adopted, or rewritten (including by `correct_worker`'s summary rewrite). **The daemon refuses to start while any agent is still running in a legacy workspace**, listing each one and its pane: no loop would manage it, yet it would count against `BUTCHR_MAX_AGENTS`. Stop those agents yourself, then start the daemon; the startup check only lists agents and never stops one or touches a directory. It also refuses to start when herdr's agent list cannot be read. The reaper can still close a leftover herdr workspace at a legacy path once no agent is running there; the directory on disk is kept.
- **MCP identity gains `x-butchr-agent`.** `x-issue` still names the ticket for every tool; rule agents also send their agent key, which scopes channel pushes and own-write echo suppression to the one agent, so two agents on one ticket hear each other's writes.
- **`stand_down` and `check_in` no longer affect staffing.** Both tools still run, but declare nothing; `stand_down` now answers `asleep: false` with a note instead of claiming a sleep and pane release that never happen. Per-agent sleep under rules is not implemented yet.

- **The daemon's HTTP server (MCP, `/health`, dashboard) now listens on `127.0.0.1` only.** It previously bound every interface (Bun listens on `*` when no hostname is given), exposing the write-capable MCP tools to the network. Local clients dialing `http://localhost:<port>` or `http://127.0.0.1:<port>` are unaffected; anything reaching the daemon from another host, or via `[::1]`, is refused. There is no setting to widen it.

### Added

- Rule queries read every page of Jira results (`nextPageToken`). A query matching more than 1000 issues, or a response that cannot prove it is complete, fails the whole poll instead of reading the missing tickets as having left the query and stopping their agents.

- Rule schema: `id`, `enabled`, `resourceProvider` (`jira-work`), `query`, `brief`, ranked `agentPreferences` (`harness` claude/codex/agy, optional `model`/`effort` — the first preference naming a harness sets its model and effort), and `relationships` (`childRule`, `inwardConnectionRules`) that reference other rules by id.
- **Rule relationships route changes to listening rule agents (read-only).** An agent under rule `R` on ticket `B` is notified when a ticket `W` changes if some enabled rule `C` matching `W` is `R`'s `childRule` and Jira already has `W` implementing `B` (an `Implements` link), or `C` is listed in `R`'s `inwardConnectionRules` and Jira already has `W` and `B` joined by a `Relates` link. Links are read from either ticket. A worker never hears its boss and nothing routes down. `Relates` is symmetric in Jira, so the configuration alone sets direction: `C`'s agents do not hear `R`'s ticket unless `C` lists `R` too. A child rule over `Relates`, an inward rule over `Implements`, `Blocks` or other links, reversed `Implements` links, and tickets no rule matches route nothing. A listener hears one change once however many rules or links connect the ticket, and an agent's own write still reaches its listeners. Butchr does not create or edit links.
- **`github-issue` rules.** A rule may name `resourceProvider: "github-issue"` with a GitHub issue search query (select issue types with `type:Bug`, `type:Feature`, `type:Task`). Each match is keyed `github-issue:<ruleId>:<owner/repo#number>` (owner and repo lowercased) and would work in `<workspace root>/github-issue/<ruleId>/<owner%2Frepo%23number>`. Searches are read-only, reuse `GITHUB_TOKEN_FILE`, and stay inside `BUTCHR_GITHUB_ORGS` (or `repo:` qualifiers within those orgs); every search adds `is:issue` and drops pull requests. Queries asking for pull requests, naming `org:`/`user:`/`owner:`, or using `AND`/`OR`/`NOT` or parentheses stop the daemon at startup, as do relationships on a `github-issue` rule and relationships between rules of different providers. They are staffed by a second rule loop (polling once a minute) only when `GITHUB_TOKEN_FILE` and `BUTCHR_GITHUB_ORGS` are set and every enabled `github-issue` rule's query stays inside those orgs; otherwise none of them runs, nothing is searched or spawned for one, any `github-issue` agent left from an earlier run is stopped, and the daemon says why at startup while Jira rules run as usual. The two loops share the host admission cap and never stop each other's agents. A `github-issue` agent identifies to MCP with `x-butchr-agent` alone (no `x-issue`; a connection sending both is refused) and gets two tools that act only on its own issue: `github_get_issue` (title, body, issue type, state, labels, every comment) and `github_add_comment` (tagged `[butchr <rule>]`). Both re-read the issue first and refuse a pull request, an issue that moved to another repo, or an owner outside the configured orgs. Jira and Confluence tools refuse `github-issue` agents, and the GitHub tools refuse every other caller. It is nudged when its issue's state, comments, title, body, labels or type change, but not about its own comment. `GITHUB_TOKEN_FILE`'s token needs permission to comment on those repos. "Only its own issue" limits the tools, not the agent: agents run shell commands as the daemon's user, can read `GITHUB_TOKEN_FILE`, and can call GitHub directly on anything that token reaches. Not wired for GitHub agents yet: labels, stall/parked/abandoned detection, respawn and crash-loop notices, session-limit recovery, blocked-dialog escalation, and dashboard ticket details. `jira-work` staffing never touches a `github-issue` agent.
- **`jira-idea` rules, and ideas are never work.** A rule may name `resourceProvider: "jira-idea"` with JQL. It staffs only issues Jira proves are Product Discovery ideas — issue type `Idea` in a project whose type is `product_discovery` — one agent per (rule, idea), keyed `jira-idea:<ruleId>:<KEY>` in `<workspace root>/jira-idea/<ruleId>/<KEY>`. **`jira-work` rules now skip those ideas, plus any issue of type `Idea` whose project type is not `product_discovery` or cannot be read, and any other issue in a `product_discovery` project**, however broad their JQL. Neither kind of rule staffs those half-proven issues, and each skip is logged once. Jira searches now request each issue's `project` so the project type can be read. `jira-idea` rules share the Jira client but run in their own loop (every 15 seconds; with no enabled `jira-idea` rule it searches nothing and only stops `jira-idea` agents left from an earlier run), with their own admission bucket under the host cap. That loop gets none of the work loop's label sync, stall/parked/abandoned detection, or respawn and crash-loop comments. Loops never stop each other's agents. A `jira-idea` agent identifies to MCP with `x-butchr-agent` alone (a connection that also sends `x-issue` is refused). It gets `jira_idea_get` (summary, description, status, labels, every comment) and `jira_idea_add_comment` (tagged `[butchr <rule>]`). Both act only on its own idea and re-read it first, refusing a moved key or anything no longer proven to be an idea. Jira work, Confluence and GitHub tools refuse idea agents, and the idea tools refuse every other caller (a tool limit only: agents can read the daemon's Jira credentials). It is nudged, naming `jira_idea_get`, when its idea's status, labels, comments or summary change, but not about its own comment. A `childRule` on a `jira-idea` rule, or a relationship to one from another rule, stops the daemon at startup. JPD-specific fields (Impact, Effort, Goals, Insights, delivery progress) and idea↔work links are not read or written yet; see `docs/jira-idea.md` for what needs live proof first.
- **Ideas hear the GitHub issues they link to (read-only).** A `jira-idea` rule's `inwardConnectionRules` may now name `github-issue` rules, and only those. An idea agent is nudged when a GitHub issue changes (state, comments, title, body, labels or type) if its idea has a Jira remote issue link to that issue's `https://github.com/<owner>/<repo>/issues/<n>` URL and a rule its rule names currently matches the issue. A link to a pull request or any other URL, an issue matched only by rules it does not name, an inactive idea, a link being added or removed, and a change only to `updated` send nothing. The nudge names the issue and the reason, never GitHub text. Nothing routes from an idea to a GitHub agent. The idea loop reads each listening idea's remote links (`GET /rest/api/3/issue/{key}/remotelink`) every poll, but only while such a rule matches at least one issue. It reuses the GitHub loop's latest matches rather than searching GitHub again, so without GitHub staffing ideas hear nothing (warned at startup). A failed link read keeps that idea's last read and is logged once. Idea agents get `jira_idea_github_issues`, which lists their own idea's linked GitHub issues (ref, URL, link title and relationship) from Jira alone. Butchr creates no links, issues or ideas.
- **Agents can link an existing GitHub issue to an existing idea, on request.** A `github-issue` agent calls `github_link_jira_idea` with an idea key, or a `jira-idea` agent calls `jira_idea_link_github_issue` with a `https://github.com/<owner>/<repo>/issues/<n>` URL. The link is allowed only when a `jira-idea` rule currently matching the idea lists, in `inwardConnectionRules`, a `github-issue` rule currently matching the issue, and the caller's own rule is one of the two. Both resources are re-read first: the issue must still be an issue (not a pull request) inside `BUTCHR_GITHUB_ORGS` and not transferred, and the idea must still be a proven, unmoved idea. Pull request URLs, Jira URLs, GitHub refs in place of keys, and callers of the wrong provider are refused before anything is read. The link is a Jira remote issue link people can see on the idea (`POST /rest/api/3/issue/{key}/remotelink`, relationship "GitHub issue", titled `<owner>/<repo>#<n>: <title>`), with a fixed `globalId` per issue so Jira's create-or-update keeps retries and races to one link. If the idea already links the issue, by any link, nothing is written. A link removed in Jira is re-added only by another call. The tools exist only while both GitHub and idea rules are staffed. The Jira account needs Link issues permission on the discovery project. Nothing is written to GitHub, and no issue or idea is created or linked automatically.
- **`zendesk-ticket` rules: read Zendesk tickets and add internal notes through tools that cannot post public replies. Off unless explicitly acknowledged.** A rule may name `resourceProvider: "zendesk-ticket"` with Zendesk search syntax. Each match is keyed `zendesk-ticket:<ruleId>:<subdomain>#<id>` in `<workspace root>/zendesk-ticket/<ruleId>/<subdomain>%23<id>`. Auth is a Zendesk OAuth access token only, read from `ZENDESK_OAUTH_TOKEN_FILE` and sent as a Bearer token to `https://<ZENDESK_SUBDOMAIN>.zendesk.com` with redirects refused. The file must be a regular file with no group or other permissions, owned by the daemon's user or root. Email/API-token auth is not supported, and setting `ZENDESK_EMAIL` or `ZENDESK_API_TOKEN` disables Zendesk staffing. Zendesk staffing also requires `BUTCHR_ZENDESK_ACCEPT_SHELL_CREDENTIAL_RISK=agents-can-read-the-zendesk-token` (exactly), checked before the token file is read. Without it, without both settings, or when any check fails, no `zendesk-ticket` rule runs: nothing is searched or spawned, leftover `zendesk-ticket` agents are stopped, and startup and `/health` say why, while other rules run as usual. The token file is read only when an enabled `zendesk-ticket` rule exists. Every search adds `type:ticket` and reads every page. A query naming `type:` or using `AND`/`OR`/`NOT` or parentheses, and relationships on or to a `zendesk-ticket` rule, stop the daemon at startup. Matching over 1000 tickets fails the poll. The rules run in their own loop, polling once a minute, with their own admission bucket under the host cap and none of the Jira detectors. A `zendesk-ticket` agent identifies with `x-butchr-agent` alone and gets two tools that act only on its own ticket. `zendesk_get_ticket` returns the subject, description, status, priority, type, tags and every comment, marked public or internal. `zendesk_add_internal_note` re-reads the ticket, refuses closed tickets and other subdomains, and sends exactly `{"comment":{"body":…,"public":false}}` tagged `[butchr <rule>]`. It errors if Zendesk's audit records the comment as public. No tool, argument or client method can post a public reply or change anything else on a ticket. **This is not a security boundary:** agents run shell commands as the daemon's OS user, so one can read the token file (the owner-only mode protects it from other users, not from agents) and call Zendesk directly, public replies included. The acknowledgement variable exists so nobody enables Zendesk believing otherwise; the effective limit is the Zendesk account's own role and OAuth scopes. Jira, Confluence, GitHub and idea tools refuse `zendesk-ticket` agents, and the Zendesk tools refuse everyone else. Agents are nudged when status, subject, priority, type or tags change, or when a new comment arrives, but not about their own note. Nudges carry no ticket text. See `docs/zendesk-ticket.md` for the dedicated least-privilege agent account, OAuth client and token-file setup, and what still needs live verification.
- **`/health` reports `github-issue`, `jira-idea` and `zendesk-ticket` loop health** in a new `resourceLoops` array: per type, whether its rules run (and why not), `state`/`lastSuccessAt`/`staleForMs` from completed polls, `consecutiveFailures`, and the last poll error. Stale after three missed polls (or `BUTCHR_POLL_STALE_MS`, if longer), logged like the other health components. It never changes `ok` or the 503 status, which still reflect only the Jira work loop.
- **A rule's `brief` can name a shipped brief with `@builtin:<type>`** (`epic`, `story`, `task`, `bug`, `project`; case-insensitive) instead of inline text. A new `bug` brief ships for bug rules. An unknown type fails the rules file at load rather than silently falling back to the default brief. Every rule brief, `@builtin` or inline and for every provider, is interpolated for the agent's resource when its workspace is built, so `{{KEY}}`, `{{PARENT}}` and the other placeholders never reach an agent raw.
- **A missing rules file no longer stops a running fleet.** If the rules file is missing at startup while rule agents are still running, the daemon names them and refuses to start instead of reading zero rules and stopping every one on the first poll. A missing file with no rule agents running still means zero rules, as before; a present file without a rule still retires that rule's agents.

### Fixed

- **Rule loops no longer start more agents than `BUTCHR_MAX_AGENTS` between them.** Each loop's admission read the same herdr agent list, which does not show an agent until its spawn finishes, so the work, `github-issue`, `jira-idea` and `zendesk-ticket` loops could each take the whole remaining budget in one round. Admission now runs one loop at a time and counts an admitted agent as occupied until its spawn finishes: from then on the agent list shows it, or it never started and holds nothing, so a spawn left waiting on provider quota and a loop whose search keeps failing no longer keep other loops' agents out. A respawn keeps its agent's place from its stop until the replacement finishes, so another loop cannot take that place in between. A single loop admits as before. The `[admission2]` line shows `in-flight=<n>` when other loops' admissions are being counted.
- **Herdr agent names no longer collide, grow without bound, or exceed Herdr's limit.** The display name Butchr passes to `herdr agent start` is now `butchr-` followed by the first 24 hex characters of the SHA-256 of the exact agent key: always 31 characters, lowercase `[a-z0-9-]` (Herdr rejects names over 32 characters as `invalid_agent_name`). Any key, however long or unusual, including uppercase Jira keys such as `jira-work:live-jira-work:BUTCHR-364`, gets a name Herdr accepts, one key always gets the same name, and distinct keys (including ones differing only in case) get different names. The name no longer shows the ticket. Names are for display only: agents are still identified by their workspace directory, which is unchanged.
