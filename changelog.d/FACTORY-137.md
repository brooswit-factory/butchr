### Added
- **Catamorbius push mode wired into linked-eventing (FACTORY-137, implementing story FACTORY-22, task 2/2).** A daemon-level `CatamorbiusPushController` (`src/catamorbius/push-controller.ts`) owns the ONE Catamorbius SSE client connection (built on FACTORY-134's client/config/mapping) and turns its events into dirty-hint/resync signals for `src/jira-watch/linked-eventing.ts`'s existing polling pipeline. A (target, owner) pair is COVERED only when it maps to a Catamorbius watch key, its provider is explicitly enabled (`CATAMORBIUS_PROVIDERS`, default empty — inert until an operator asserts webhooks are actually flowing), and the connection is live (or reconnecting within a grace window). A covered, clean target is skipped entirely (no fetch) until it goes dirty, its TTL expires (`CATAMORBIUS_TTL_MS`, default 10 minutes, with optional per-provider overrides), or a resync is forced; every other target keeps polling completely unchanged. `runTick`'s own existing coalescer/rate-cap/notify path is reused byte-for-byte — a consumer of a `LinkedChangeEvent` cannot tell which mechanism produced it, and every one of `runTick`'s existing tests passes unmodified.
- A new on-demand pass (`LinkedEventingState.runDirtyPass`, debounced via `CATAMORBIUS_DEBOUNCE_MS`, default 2s) delivers a dirty change within roughly one debounce window instead of waiting for the next scheduled 15s/60s tick, reusing the triggering tick's own already-discovered items — no fresh Jira search, remote-links call, or managed-link listing. `runTick` and `runDirtyPass` are serialized against each other so they can never double-diff the same baselines.
- Disconnects degrade gracefully: covered targets stay covered while reconnecting within `CATAMORBIUS_GRACE_MS` (default 60s), then fall back to full polling until the client is live again, at which point (or on the client's own resync-required signal) every covered target is force-refreshed once. A change found only by that forced refresh is delivered as the exact same event polling would have produced, with one rate-limited WARNING and a counter (`stats().streamMissed`) — never a difference in the event itself.
- `loadCatamorbiusFullConfig` (`src/catamorbius/push-config.ts`) wraps FACTORY-134's `loadCatamorbiusConfig` without modifying it: an unreadable token file now disables push mode with one WARNING and falls back to polling (rather than crashing daemon startup, which is what the unwrapped loader still does); every other malformed value (URL, a numeric knob, an unknown `CATAMORBIUS_PROVIDERS` entry) still fails startup loudly, unchanged.
- `stats()` counters split across the two levels that actually own the state: the push controller (`notificationsReceived`/`unmapped`/`deduped`/`degrades`/`resyncs`, connection-wide) and each `LinkedEventingState` instance (`dirtyMarks`/`onDemandPasses`/`ttlRefreshes`/`streamMissed`, per instance — baselines are per instance, so dirty/TTL state is too).
- See `docs/catamorbius-push.md` for the full architecture, the D1-D9 decisions and their reasoning, config defaults, and the operator RUNBOOK to enable this (with its rollback and the "healthy connection does not prove events are flowing" caveat); `docs/resource-links.md` now points at it instead of reading as "polling is the only mode".
- `scripts/verify-catamorbius-push-e2e.ts` (AC5): an opt-in end-to-end proof — real client + real `CatamorbiusPushController` + a real `LinkedEventingState` with fake fetchers, driven against a scratch Catamorbius gateway this script starts and stops itself. Skips cleanly when `CATAMORBIUS_SCRATCH_DIR` is unset, so it is never part of `bun run check`. See `docs/catamorbius-push.md`'s "AC5: end-to-end evidence gathered for task 2" for the transcript from a real run.

### Fixed
- Review round 1 (PR #790): `isCoveringNow()` no longer grants reconnect-grace coverage before the client has been live at least once this process — the real client's own `scheduleReconnect` sets `reconnecting` unconditionally, including right after the very first connection attempt ever fails, so without this gate an unreachable-at-startup gateway would still silently suppress polling for already-seeded targets (D2(3)/D5's own "before the first live connection... uncovered immediately, no grace").
- The push controller's `onEvent` handler is now isolated against a throwing consumer/mapping bug (the client's own listener dispatch otherwise swallows it with zero trace): a new `stats().handlerErrors` counter plus a WARNING log, with each registered consumer's `markDirty` call isolated individually so one bad consumer never costs every other consumer the same event.
- Added the differential AC1/C2 test (identical before/after state through today's polling-only `runTick` and through push mode, asserting deep-equal `deps.notify` payloads via two independent instances, not a hand-copied literal) and the T10 concurrency test (a regular tick and an on-demand pass held concurrently via controllable promises, over the same real change, producing exactly one notification).

### Fixed (review round 2)
- `LinkedEventingState.runDirtyPass`'s batched Jira fetch no longer treats a `jira-project` owner's project MEMBER target as "already fetched" using the regular tick's now-stale cached member snapshot (`memberFetchedByKey`, carried over via `lastPassContext`). That dedup is correct for an actual regular tick (the member search just ran fresh, same tick) but was wrongly applied to an on-demand pass too, which never reruns member discovery (D3) — so a member that went dirty between regular project ticks would be silently diffed against stale data, found "unchanged," and have its dirty mark cleared with nothing delivered until the next regular tick happened to run. Fixed by gating that dedup on `!restrict` (a genuine regular tick); an on-demand pass now always re-fetches a dirty/resync-pending member through the same ordinary batched `key in (...)` call every other target already goes through — no new discovery call is added. New regression test proves the bug (fails red against the pre-fix code, passes green with the fix): discover a project member via a regular tick, change its authoritative status with no further regular tick, mark it dirty, call `runDirtyPass`, and assert a fresh fetch plus exactly one notification.
