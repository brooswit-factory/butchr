bump: minor

### Added
- **A tier-identity collision — the caller of `new_worker`/`adopt_worker` and the accountId about to be assigned to the child resolving to the SAME Atlassian account — is now surfaced at staffing time instead of four steps later at `gh pr review --approve` (BUTCHR-103/BUTCHR-110).** RECORD, never refuse (BUTCHR-103's decision): a refusal here would deadlock the fleet, since changing a `BUTCHR_ASSIGNEE_*` value is out of scope for every agent that could hit this, and refusing to adopt an orphan just recreates the orphan problem `adopt_worker` exists to solve. The call always succeeds; the collision is instead made LOUD in three places, uniformly across issue callers AND project callers: a new `identityCollision` field on `new_worker`'s/`adopt_worker`'s result (`src/tools/relationship.ts`), an `IDENTITY COLLISION:` audit line on the daemon's existing tool-audit path (`src/tools/defs.ts`, same line-writing path the existing `REFUSED: no assignee` lines use), and a comment on the worker's own ticket, tagged with the caller's identity like every other agent comment. Every message names both role variables involved (or, for a PROJECT caller — which has no role variable on its own side — `ATLASSIAN_EMAIL`/this daemon's own Atlassian credential), both tiers by name, the specific hop that will not work in words, and the shared accountId (truncated to match the startup banner's own format).
- **The caller's accountId is read from the caller's OWN ticket** (or, for a PROJECT caller, from `ops.getMyself()` — the same call BUTCHR-67's discovery lead-filter already uses), never from the role variable governing the caller's tier: those can differ on a hand-assigned ticket, and the observed value is what actually decides whether GitHub will refuse the review. `new_worker`'s issue-caller path already fetched the caller's own ticket for type/project inference, so the check costs no extra Jira call there; `adopt_worker`'s issue-caller path did not previously fetch the caller's ticket at all and now does — one extra read, paid as the price of the check.
- **Fail-safe, never fail-silent**: if the trace comment fails to post, the staffing call still succeeds and the returned `identityCollision` text says so, and why — never a bare `.catch(() => {})` masking the failure.
- **`adopt_worker`'s idempotent re-adoption path**: `identityCollision` is still computed and returned on every call (a fact about current state, cheap to state), but the ticket comment is only (re-)posted the call that actually does adoption work (`!alreadyAdopted`) — a fully idempotent re-adoption already does no other write, and reposting an identical comment on every subsequent no-op check would spam the ticket with duplicates carrying no new information.
- **Daemon startup now reports role-map collisions among this daemon's own SET `BUTCHR_ASSIGNEE_*` variables**, extending `describeConfig`'s existing pure, tested rendering function (`src/config/config.ts`) rather than adding a second reporting path — pairwise across `story`/`task`/`epic`; two UNSET roles are never a collision (unset keeps its own, unchanged wording). **The report always carries an honesty clause, collision or none**: it states plainly that the comparison is over LOCALLY CONFIGURED role variables only, that a tier staffed by a *different* daemon has no local variable here to compare against, that a clean report is therefore NOT evidence every review hop on this Epic's fleet is sound, and that `new_worker`/`adopt_worker`'s own staffing-time check is what actually catches what this cannot — measured necessary by BUTCHR-100 (2026-09-02): a daemon with only `story`/`task` set, genuinely different, reports clean under a naive pairwise comparison even while a live Epic staffed by a *different* daemon collapses onto that same task account, because this daemon has no local epic role to compare it against at all. The project↔epic hop is deliberately never checked at boot (the caller's side is this daemon's Atlassian credential, not knowable without a Jira call, and config rendering stays pure and synchronous) — stated, not silently omitted.

### Fixed
- **`.env.example`'s `BUTCHR_ASSIGNEE_EPIC` guidance stated only one pairwise constraint** (must differ from this daemon's project-lead identity) **and was silent on the one that actually broke in production**: an Epic can adopt a Story or a Task *directly* via `adopt_worker`, so the epic account must also differ from `BUTCHR_ASSIGNEE_STORY`/`BUTCHR_ASSIGNEE_TASK`. Worse, its own commented-out suggested value was *identical* to the `BUTCHR_ASSIGNEE_TASK` value two lines above it — instantiating the exact collision the block was warning about. The full constraint set is now stated, and no colliding example value is suggested.
