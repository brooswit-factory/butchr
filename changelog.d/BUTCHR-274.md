### Added
- **`docs/deploy-delivery-mechanism.md` records, by measurement and controlled experiment, how a commit on `main` actually reaches a running daemon (BUTCHR-274/BUTCHR-301).** The answer: there is **no in-process deploy path at all** — at `88cfde11`, every git call site in `src/` is a read (`rev-parse`, `rev-list`, `status`), `systemctl` and `--ff-only` appear nowhere in the repository, and both `Bun.spawn` sites are terminal pane-attach. Delivery is done entirely by **one external sweep** that pulls and restarts **in the same second**, per daemon in sequence (13 paired events, the other account always first, +1s to +16s, ordering never reversed). That sweep ran hourly at `:43` on 2026-09-01, continued irregularly through 2026-09-02 21:51:25, then stopped; its **invoker is not in this repository and was not visible from the measuring account** (every place searched is enumerated in the doc, including the two that were permission-denied). Latency from merge to execution is therefore **"until a person acts", unbounded by construction** — worst gap actually observed, **seven days with no restart at all**.
- **A measurement trap that invalidates a common way of reading this evidence, and which produced one of this question's four retractions: a pull that finds nothing new changes no ref, so it writes NO reflog entry — yet it still restarts the daemon.** The `main` reflog therefore *systematically under-counts* deploy-sweep runs; restarts, not reflog entries, are the sound detector. The 2026-09-01 23:43:42 sweep is visible only as a restart.

### Fixed
- **Documented, with its falsifier, that a comment in `src/agents/build-currency.ts` is wrong about where `FETCH_HEAD` lives — measured at git 2.43.0.** The comment above `resolveGitCommonDir` claims `FETCH_HEAD` was "measured living under `--git-common-dir`, NOT the per-worktree `--git-dir`", so that a fetch in one worktree updates it for all. A controlled experiment (throwaway clone, never a live tree) shows the opposite: a fetch inside a **linked worktree** advances the **shared** `refs/remotes/origin/main` but writes **only** `.git/worktrees/<name>/FETCH_HEAD`, never creating the common-dir file. `lastFetchedAt()` stats the common-dir path, so it observes **only main-worktree fetches** while most fetching in this fleet happens in linked worktrees — making the clone look like it fetched longer ago than it did. **The code is deliberately left unchanged:** correcting the comment without correcting `lastFetchedAt()` would leave prose that is right above behaviour that is wrong, which is strictly more misleading; the signal and its consumers belong to BUTCHR-163.
- **Both long-open ref anomalies are now reproduced rather than hypothesised, and one of them is the false-CURRENT direction.** Anomaly (a) (`origin/main` advances, top-level `FETCH_HEAD` does not) needs nothing exotic — any fetch in any linked worktree produces it. Anomaly (b) (a fetch leaves `origin/main` behind commits that already exist) has **two** demonstrated mechanisms: `git fetch origin <sha>` — the shape of an ordinary PR review fetch — and `git fetch <url> <branch>`; both write `FETCH_HEAD` and bring the objects in while leaving the tracking ref untouched. Because (b) makes `FETCH_HEAD` freshness and `origin/main` trustworthiness independent, **a freshness gate that infers the latter from the former can print a false CURRENT.** Which mechanism produced the specific historical observation is **permanently undeterminable**: `FETCH_HEAD` is overwritten on every fetch, so only the latest survives — a field read of all 3824 current lines on the studied checkout found exactly one source URL and no sha-or-tag line at all.
