### Added
- **Abandoned-worker detector: an open worker whose `Implements` boss reached Done now escalates instead of sitting silently forever (BUTCHR-200/BUTCHR-192).** A boss can tell a worker "merge it, then I'll close you out", have the worker merge, and then reach Done itself without ever discharging that worker — this already happened in production (BUTCHR-127 told BUTCHR-159 exactly that, then closed leaving it open; discharged by hand 2h15m later, only because a person happened to remember). The link stays intact, so `adopt_worker`'s orphan machinery correctly refuses to touch it (that refusal is unchanged and correct); the boss will never call `finish_worker` on it, never answer it, never `start_worker` it again. This exists **because the guard that prevents the state is structurally bypassable**: `jira_transition` (`src/tools/defs.ts`) is a live, unguarded verb — a bare passthrough to `ops.transition(key, status)` with no ownership, status, or downward check; its "deprecated" status is a string in its own description, not an enforced refusal. Any agent, or a human editing status by hand in the Jira UI, can move a boss to Done over an open worker without going near the guarded relationship verbs. A sibling ticket (BUTCHR-193) adds refusals to the three closing verbs, but those bind only from the moment they deploy and do nothing about `jira_transition` itself.
- **The predicate (`src/agents/abandoned.ts`'s `abandonedCandidates`) is pure and total over one poll's already-fetched `issues` snapshot — zero extra Jira calls, and no `related` walk at all**, unlike `parked.ts`. `parked.ts`'s trick (resolving the boss's status out of the active `issues` set) doesn't work here: a Done boss is never in that set by construction, and `related` (the Implements-outward walk off it) holds workers, never bosses. Instead, `parseIssueLinks` (`src/atlassian/client.ts`) now carries the OTHER end's `status` on a flattened `IssueLink` (`status?: string`, `src/atlassian/types.ts`, populated only when the payload carries it — `undefined` means UNKNOWN, never inferred as Done or not-Done) — strictly additive, verified against every existing consumer of `IssueLink`/`parseIssueLinks` (`parked.ts`, `jira-watch/routes.ts`'s `watchedKeys`, `resources/issue.ts`'s boss-key lookup — all read only `type`/`otherEnd`/`key`) and against the full test suite. MEASURED live (BUTCHR-192, against the exact endpoint and field projection `AtlassianClient#search` uses, `GET /rest/api/3/search/jql?fields=summary,status,issuetype,assignee,parent,updated,labels,issuelinks`): Jira hydrates `status` on both `inwardIssue` and `outwardIssue` stubs; `labels` is never present on either, even when the far end demonstrably carries one. So a worker already in the poll's own snapshot now carries its boss's status on its own inward `Implements` stub, at no additional cost.
- **The escalation target is flipped from `parked.ts`'s, and deliberately so**: `parked.ts`'s boss is live by definition, so posting on the boss's own ticket reaches a running agent — the cheapest likely-to-be-read channel. Here the boss is Done by definition (dead, no running agent), while the WORKER is the live party (it is, by construction, one of `issues` — In Progress or In Review, staffed by this daemon's own credential). Stage 1/2 therefore post on the WORKER's own ticket; only stage 3 walks up the Implements chain, to the boss's own boss (a "grandboss", resolved via the one extra Jira call in the whole feature — `atlassian.links(boss)`, only reached once two prior stages went unaddressed), or, when there is none, back on the boss itself (which, having no inward Implements link of its own, is by construction an Epic — a human's own ticket). Same staged/rate-capped/deduped shape as `parked.ts` otherwise: `RateCap`/`findMarked`/`HOUR_MS` from `src/agents/escalation-helper.ts`, a per-(worker, boss)-pair in-memory floor that can only ever delay a signal (never fabricate one, and starts fresh across a daemon restart or after a candidate stops qualifying), and dedupe/adoption against the target's own comment history so a restart adopts its own prior escalation instead of re-posting it. Comments are read through the tier-aware `createOwnChannelComments` (`src/tools/speak.ts`) — unlike `parked.ts`, which still uses a raw `atlassian.comments` call because it predates that fix; not corrected there, deliberately, to keep this PR isolated.
- New marker `[butchr:abandoned]`, distinct from `[butchr:parked]` and every other detector's marker on purpose — a shared marker would make a future "show me every X" grep silently wrong (the same reasoning `ORPHAN_LABEL`'s own doc comment, `src/tools/relationship.ts`, already gives for keeping that label distinct from `EXEMPT_LABEL`).
- **`butchr:shelved` deliberately does NOT exempt here — the opposite of `parked.ts`'s decision.** A shelved worker can only be reactivated by its own boss calling `start_worker` (verified: `assertOwnWorker` refuses any caller that is not the worker's own Implements-linked boss) — so a worker left shelved under a Done boss can never be reactivated by anyone, ever. It is not less abandoned than an unshelved one; it is more so. This is not in tension with the sibling closing-door guard (BUTCHR-193/BUTCHR-191), which deliberately lets a boss `shelve_worker` an open worker and then close over it (refusing that too would reproduce the BUTCHR-92 circle — a worker the boss can neither finish nor shelve, with no exit at all): the design both tickets converge on is *enforce where there is an exit, make audible where there is not* — this detector is the audible half.
- **Known limitation, documented rather than silently accepted, and the ARCHETYPE of this failure family, not its low-value remainder: a To Do worker under a Done boss is invisible to this detector** (`ISSUE_JQL` never returns a To Do issue), to `parked.ts` (which requires the boss to be In Progress), and to the orphan machinery (the link is intact). "Inert" is why this is worse, not better — nothing is burning, so nothing complains, so it stays silent forever; BUTCHR-13 exists because four stories were stranded exactly that way. Not covered here (no widening of `ISSUE_JQL`, shared by every consumer of the poll; no dead configuration stubbed for it, matching `parked.ts`'s own precedent for an out-of-scope adjacent state) — the concrete cost of covering it is reported separately. Same second limitation as `parked.ts`: a worker staffed by a different credential is invisible to this daemon.
- **Steady-state volume should not be assumed to stay at the measured day-one population of zero** (37 open BUTCHR candidates scanned, complete set, zero abandoned workers found): the sibling closing-door guard's own refusal message recommends `shelve_worker` as a discharge path, and every agent that follows that advice and then closes is inflow this detector did not create and cannot control, at a rate no measurement available today predicts. `BUTCHR_ABANDONED_MINUTES` (default 30 — three times `parked.ts`'s 10, deliberately not short: unlike a To Do child under a live boss, a boss closing moments before discharging its last worker is a real ordering race, not a fault, but 30 minutes still surfaces the state roughly 4-5x faster than the one historical instance this detector exists for) and the rate cap (3/hour per target, matching `parked.ts`'s own — not because steady-state volume is expected to match, but because no measurement available today justifies inventing a different number) are both sized with this in mind rather than tuned for the zero.
- **Wired ON by default** into the issue-tier poll loop (`src/daemon/index.ts`, `src/daemon/loop.ts`'s `LoopDeps.checkAbandoned`/`GenericLoopDeps.checkAbandoned`, called from the poll's observe function — never `watch()`'s `onChange` — for the same reason `checkParked` is, see that field's own doc comment) — the mirror image of the project loop's deliberate opt-in-default-off precedent (which exists because every eligible target there verdicted "active" on a first poll): this detector's measured first-poll count is zero, so an ON default cannot spam anything on day one. Never throws — every failure caught and logged (belt-and-suspenders, same as `checkParked`), so a Jira hiccup here can never take the poll loop down.
- New `BUTCHR_ABANDONED_MINUTES` env knob (default 30, optional), added to `Config`/`ConfigEnv`, validated in `loadConfig`, printed by `describeConfig`.

### Deploy impact
A pull plus a `systemctl --user restart butchr.service` (or equivalent) is the entire deploy — no separate build step. `BUTCHR_ABANDONED_MINUTES` is optional (defaults to 30); nothing breaks if it's left unset. Across the restart, the detector's in-memory floor and stage state for any worker already mid-escalation is lost and starts fresh on the next poll — this can only ever DELAY that worker's next escalation stage, never fabricate one, and dedupe against the target's own comment history means a still-abandoned worker does not get a duplicate stage-1 comment once the fresh floor catches back up. Already-running agents are entirely unaffected — this feature only ever reads the poll's own `issues` snapshot and writes Jira comments; it never touches the herd/reconcile path. Nothing is ever auto-repaired, re-parented, re-linked, or auto-closed — every action this detector's comments name is a human or boss action.
