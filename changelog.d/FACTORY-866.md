### Fixed
- **butchr's own `[butchr:*]` bookkeeping comments no longer defeat Jira daemon-label-only (`agent:*`/`pr:*`) notify suppression (FACTORY-864/FACTORY-865/FACTORY-866).** The notify comment cursor built by `src/resources/issue.ts`'s `createIssueEventRules` and the parent/child linked-change path's `!commentChanged && isDaemonLabelOnlyDiff(...)` gate in `src/jira-watch/linked-eventing.ts` are now both computed from `src/jira-watch/diff.ts`'s new `excludeBookkeepingComments`, which drops any comment matching `DAEMON_CHATTER_PREFIX` (`src/agents/stalled.ts`) UNLESS its marker is in the new `WAKE_MARKERS` allowlist (`[butchr:blocked]`, `[butchr:respawn]`, `[butchr:stall]`, `[butchr:unresponsive]`). Previously, any `[butchr:*]` chatter comment — e.g. `[butchr:parked]`, `[butchr:reconcile]`, `[butchr:crashloop]` — moved the cursor just as a real comment would, so the next routine `agent:working`/`agent:idle` label flip on that ticket (which happens every agent turn) was delivered as a wake wrongly attributed to the comment, even though a pure label-only diff is supposed to be suppressed. No new Jira I/O: the filter runs over comment data the suppression stack already fetches.
- The cross-daemon arm's fail-open "no recorded comment baseline -> do not suppress" branch now suppresses instead: a daemon-label-only diff can never itself be a reason to wake anyone, regardless of whether a baseline happens to be known yet. A failed comments fetch still never installs or advances a cursor value nothing was actually observed.
- No change to `pr:*` transition delivery, the `undetermined`/fallback delivery path, or any non-Jira provider (GitHub issue label changes keep firing unconditionally; Zendesk and filesystem have no label dimension) — scope is pinned by a dedicated test asserting `SyncDeps` (`src/labels/sync.ts`) is a Jira-only label writer and that the GitHub label-change path still delivers.
