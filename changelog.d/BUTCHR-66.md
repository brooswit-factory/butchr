### Added
- **Sleep as a third `Activation<T>` verdict (`src/resources/types.ts`).** `Activation<T>.isActive(resource): boolean` is replaced by `Activation<T>.verdictFor(resource): ActivationVerdict`, where `ActivationVerdict = "active" | "asleep" | "inactive"`. `"asleep"` means legitimately at rest: never spawn, never stop, never respawn, never alarm — an absent agent is healthy, and a present one (just woken, mid-work) is healthy too and is left alone to finish and exit by itself. This is a widening of the existing member's verdict, not a fifth `ResourceType<T>` member — `ResourceType<T>` still declares exactly four members.
- **The reconciler now takes an `atRest` set (`planReconcile`'s new `atRest` parameter, `src/reconcile/plan.ts`; threaded through `ReconcileOptions.atRest` and the new `atRestFrom` helper, `src/daemon/loop.ts`).** `spawn`/`respawn` already exclude an asleep resource automatically (neither is ever in `desired`); `stop = running − desired` did not, and is the one real change — an asleep resource that is still running (the window between a woken agent advancing its own watermark and actually exiting) must never be stopped. `atRest` defaults to empty, so every existing caller (none of which has ever had an asleep-capable resource type) is unaffected.

### Changed
- `desiredFrom` (`src/daemon/loop.ts`) now checks `resourceType.activation.verdictFor(item) === "active"` instead of the removed boolean `isActive`.

No behaviour change for the issue tier: `ISSUE_ACTIVATION` (`src/resources/issue.ts`) now returns `"active"`/`"inactive"` only — `verdictFor` maps the unchanged, unforked `isActive(status)`/`ACTIVE_STATUSES` predicate (`src/reconcile/plan.ts`) directly, so it is structurally unable to return `"asleep"` for any input (see `test/unit/sleep.test.ts`'s structural proof). Every existing test passes unedited except `test/unit/resource-type-second-instance.test.ts` (BUTCHR-64/69's `Widget` fixture), which required a mechanical `isActive: () => true` → `verdictFor: () => "active"` rename to keep type-checking against the widened interface — the same unconditional verdict, not a behaviour change; disclosed on the PR and the ticket rather than absorbed silently.

**Bump-level reasoning:** `minor`, per `CHANGELOG.md`'s own definitions — "a change to an existing feature that breaks just that feature." `Activation<T>.isActive` is a public interface member of an exported type, and this PR changes its name and return type, which is a breaking change to that one seam, requiring every implementer (the issue tier, and any test fixture) to update. `major` doesn't fit: nothing about the surrounding `ResourceType<T>`/reconciler/loop machinery requires reimplementation — `desiredFrom`'s own exported signature is unchanged, and the issue tier's runtime behaviour is provably identical. `patch` doesn't fit either: this is not a fix, and it does require a (small, mechanical) consumer code change.
