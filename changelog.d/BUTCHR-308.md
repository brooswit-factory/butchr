### Fixed
- **The "could not check" decision behind `/dashboard` is now unit-tested against the real function, not just inferred from route-level fixtures (BUTCHR-308).** Before this ticket, the whole-response `agent.list()` outcome — carry the prior rows forward on decline, stamp a fresh `confirmedAt`/`declinedAt`, never launder a decline into `checked: true` — was decided inline inside `src/daemon/index.ts`'s `agentStatuses` provider, a module no unit test in this repo imports. Two mutations that destroy that exact behaviour (discarding the prior rows on decline; reporting `checked: true` on a decline) passed the full 2104-test suite unnoticed. `createDashboardFeed` (`src/agents/dashboard.ts`) moves the decision itself into a small, directly-testable feed object (`poll(list)` / `snapshot()`); `src/daemon/index.ts` is now wiring only — it still owns the one `agent.list()` fetch and the `coverage.recordChecked`/`recordDeclined` calls next to it, but the snapshot shape itself is decided in, and tested against, `src/agents/dashboard.ts`.
- **A `checked: true` `/dashboard` response now carries its own response-level `confirmedAt`.** With rows, each row's own `confirmedAt` already ages and tells the truth; a genuinely empty fleet (`rows: []`) had nothing to carry a time at all, so "checked: this daemon runs nothing" was indistinguishable from the same response served hours stale — this story's founding distinction (BUTCHR-116) leaking through the one shape with no row to carry it. The per-row `confirmedAt` is unchanged and still required on every row (BUTCHR-269's AC-3); this is additive. The declined shape is unchanged — it already carries its own `declinedAt`.
