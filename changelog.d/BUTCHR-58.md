### Fixed
- **`butchr:shelved` now means CURRENTLY shelved instead of EVER shelved: `start_worker`, `finish_worker`, and `adopt_worker(..., "start")` withdraw the exemption they no longer justify, instead of leaving it on the ticket forever (BUTCHR-50).** `shelve_worker` sets the label; until now, nothing ever cleared it, so a worker shelved once and later reactivated stayed permanently exempt from the parked-ticket detector (`src/agents/parked.ts`) — and if it was ever parked again, the detector was silently blind to it, exactly for the population most likely to be forgotten a second time. Measured on the live board before this fix: four Done tickets (BUTCHR-28/-29/-30/-31) still carried a `butchr:shelved` declaration that had already been reversed. The label was always meant to be a STATE, not a history: set when the decision is made, cleared when the decision is reversed.
- `startWorker` and `finishWorker` now clear the label first, then transition — ordering is the design decision, not an implementation detail: transitioning first and then failing the label removal would leave a live ticket *silently* carrying a stale exemption (the exact blindness this fixes); clearing first and then failing the transition instead leaves a To Do, assigned, unexempt child under a live boss, which the parked detector reports *loudly*. A partial failure must never be silently wrong when it can instead be loudly right. Both verbs reuse `assertOwnWorker`'s existing issue fetch (now returned instead of discarded) to decide whether a removal call is even needed — a ticket that was never shelved costs exactly what it cost before this fix, zero extra Jira calls.
- `adoptWorker` with `disposition: "start"` clears the label too, whenever the adopted ticket carries it — including when the call is otherwise a fully idempotent no-op (already linked, assigned, and In Progress), since a stale label surviving that path reproduces the identical bug through a second door. `disposition: "shelve"` is unchanged — it still sets the label additively.
- New `AtlassianOps.removeLabels(key, labels)`, the read-modify-write inverse of the existing `addLabels` (Jira's `editIssue` has no subtractive label endpoint). Removing a label the issue doesn't carry is a no-op, not an error.
- A label set **by hand** (never through `shelve_worker`) is still never cleared automatically by anything — that stays the responsibility of whoever set it. Only the relationship-tool verbs that reverse a `shelve_worker` decision withdraw the declaration it made; the daemon's own poll/sweep label machinery (`src/labels/plan.ts`, `src/labels/sweep.ts`) still never touches this label at all, in either direction.

### Deploy impact
A pull plus a `systemctl --user restart butchr.service` (or equivalent) is the entire deploy — no schema or config change. Deploy-on-merge is not enabled for this epic (BUTCHR-52), so the running fleet keeps the old (label-never-cleared) behavior until an operator restarts it; this PR does not depend on that restart to be reviewable. The four pre-existing residue tickets (BUTCHR-28/-29/-30/-31) are not touched by this fix — they are Done, so the detector cannot fire on them today, and any one of them that is ever reopened and reactivated through `start_worker` is healed automatically by this change.
