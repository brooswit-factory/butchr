### Added
- **A second, herdr-independent blocked-detector closes the class of freeze that cost all five epic agents ~12 hours on 2026-08-30 (BUTCHR-5/BUTCHR-16).** Claude Code showed an effort-recommendation dialog ("We recommend Opus 5 at medium effort" / "Switch ... to medium effort" vs "Keep high") that herdr classified every affected pane `idle`/`done` for the entire freeze — `blockedNow` never returned them, so `watchPrompts`/`parsePrompt`/the escalation stack never ran at all; teaching the parser the shape would not have helped, since it was never invoked. `src/agents/idle-dialog.ts` now tracks, per pane, how long its herdr status has read idle/done continuously (mirroring `stalled.ts`'s `StalledTracker`) and, once that clears a new `BUTCHR_IDLE_DIALOG_MINUTES` bound (default 2 — short by design: escalating a dialog we could have answered costs one notification, failing to escalate one we cannot costs hours × agent count), reads the pane and checks whether its text parses as a real dialog (`parsePrompt`, unmodified, so the KAN-756 anti-false-positive gates — footer immediately after the last option, exactly one cursor, a bounded question tail — apply here too). A pane that matches is folded into the SAME poll's blocked set fed to the existing `watchBlocked`/`watchPrompts`/escalator pipeline (`blockedNow` itself stays pure and untouched), so auto-answer, fingerprint debounce, once-per-fingerprint escalation, the 3-per-hour rate cap, and the 15-minute follow-up all apply identically — no second escalation path. Pane text is read only for panes that already clear the cheap idle-duration precondition; a normal 5s status poll costs nothing extra.
- **A settings-recommendation dialog is answered by PRESERVING the current setting, chosen by content, never by position (BUTCHR-16).** `chooseStartupAnswer` (`src/agents/prompt.ts`) gates on a question containing "recommend" (placed after the existing option-content rules, since "recommended" also appears as ordinary option text on the unrelated resume-from-summary dialog) and scans every option for keep/no-change/stay/leave-as-is wording — the same "exactly one hit or null" discipline `freeTextOption` already uses: zero matches or more than one plausible match returns null and lets the dialog escalate rather than guessing. A regression test with the options listed in the OPPOSITE order proves the same option is still chosen. The fleet's default effort level is unchanged by this ticket (still HIGH) — this only stops the fleet's effort from being silently changed by whichever order a future dialog happens to list its options in.
- **Every escalation now durably captures the full, unredacted pane text to `BUTCHR_CAPTURE_DIR`** (`<ISSUE>-escalation-<compact-UTC-timestamp>.txt`, same store as the session-limit watcher's own captures, BUTCHR-12 — each recognises only its own filename shape, so neither evicts the other's files, and each is capped at 50 files, oldest evicted first) **and the Jira comment references that path, never the raw text.** The fixture for the effort-recommendation dialog itself is already gone — nothing survived the ~12-hour freeze but an operator's hand transcription, and `herdr pane read` returned unrelated shallow scrollback by the time anyone went looking ~14 hours later. `escalationComment` keeps building the Jira-visible text ONLY from the (redacted) question and options; the capture path is not secret-shaped and needs no redaction of its own.
- `test/fixtures/pane-cap-effort-recommendation.txt`: a RECONSTRUCTED fixture for the effort-recommendation dialog, with a header stating plainly which parts are the operator's real transcription (question wording, option text) and which are guessed (cursor position, footer line, absence of other chrome) — see the file's own header and the PR description for the full accounting.

### Fixed
- **A dialog quoted anywhere in scrollback, with its cursor and footer still intact, no longer parses as live on the new idle path (PR #104 review, round 1).** `parsePrompt`'s existing gates verify the dialog block itself but say nothing about what follows it — safe for herdr's own `blocked` classification (the dialog IS the live composer state by construction) but not once an idle pane reaches the same parser: an agent that `cat`s a dialog-shaped fixture, narrates about it, and goes idle produces a pane whose scrollback carries a well-formed dialog followed by the agent's own prose and then the pane's genuinely-live composer chrome. Without this fix a reproduced pane sent a real Down+Enter into a working agent's composer.
- **The trailing-region check itself failed toward SILENCE (PR #104 review, round 2): any shape not on its allowlist — a boxed dialog's closing border, a footer split across two lines, a non-bypass status line, a scroll hint, all real possibilities the ticket itself named as unknown — was dropped outright, which is a real dialog hitting DoD 1's exact failure mode.** `src/agents/idle-dialog.ts` (still not `prompt.ts` — the parser stays correct and unmodified for its original caller) now classifies the region after a dialog's footer three ways instead of a binary: `"live"` (nothing, or the recognized terminal chrome — auto-answer or escalate as before), `"stale"` (a Claude Code turn bullet or a tool-result continuation marker anywhere after the footer — the round-1 signature — dropped entirely), or `"unknown"` (anything else — treated as blocked and escalated, but the pane is flagged so `daemon/index.ts`'s `onPrompt` refuses to auto-answer it regardless of what `chooseStartupAnswer` would otherwise say). The two hazards are asymmetric by OUTCOME, not by detection: a wrong auto-answer sends a real keystroke, a wrong escalation costs one already-deduped, already-rate-capped Jira comment carrying the captured pane text — exactly the mechanism for promoting a real recurring unknown shape to `"live"` with actual ground truth instead of a guessed allowlist.
