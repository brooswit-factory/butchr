### Fixed
- **`parsePrompt`/`parseUnnumbered` anchor a dialog's `question` to the dialog's own opening frame, so scrollback chatter above it can no longer displace the question or move the escalation fingerprint (FACTORY-481, implements FACTORY-378).** Both parsers used to build `question` from a plain `.slice(-QUESTION_TAIL)` (last 6 non-blank, non-footer, non-rule lines) tail over EVERY line preceding the option block — arbitrary prior pane content, notably butchr's own notification chatter interleaved above a dialog, could and did displace the real question. Since `fingerprint()` (`src/agents/escalate.ts`) hashes `question + options`, a drifting question meant a drifting fingerprint, and the `ANSWER <n> <fingerprint>` protocol correctly refuses a stale fingerprint — so the escalation became permanently unanswerable. Measured live on FACTORY-327 (comments 26314/26328/26332): three `[butchr:blocked]` escalations of the SAME weekly-limit dialog within ~90 seconds, three different fingerprints (`9af0ab76`/`d0f4ab9f`/`137f7381`).
- Fixed by anchoring `question` to start fresh immediately after the dialog's own opening horizontal rule line (`─+`), rather than accumulating from wherever the preceding scrollback happens to end. Every one of the 84 real captures in this daemon's own `.captures/` corpus carries exactly this rule directly above the dialog's own content, with arbitrary agent/tool/notification chatter above it and nothing but the dialog below — confirmed by grepping the full corpus, not assumed. `QUESTION_TAIL`'s tail-bound is kept as a fallback for the (synthetic-only, never observed in a real capture) case of a dialog with no rule line, so no existing behavior regresses.
- `fingerprint` itself is UNCHANGED — still `question + options`. Anchoring `question` to the frame is what makes it invariant per-episode; no downstream change was needed, and the `ANSWER <n> <fingerprint>` protocol still correctly refuses a genuinely stale fingerprint (the dialog's own content changing, e.g. a new option list) since that still changes `question`/`options` for real.
- Disclosure: `escalationComment` already calls `redact()` over `question`/`options` before posting, so credential-SHAPED content (`KEY=value`, bearer tokens, DB URLs, etc.) was never posted un-redacted even before this fix. What this fix closes is narrower but real: arbitrary NON-secret-shaped pane prose (command text, file paths, unrelated ticket prose) that happened to fall within the old 6-line tail window could reach a project-readable escalation comment as the "question" — never any more than 6 lines' worth, and never anything past a dialog's own rule line once one is present, which is every real capture measured.
- Both `parsePrompt`'s numbered-menu branch and `parseUnnumbered` (the un-numbered/trust-dialog shape) got the identical fix — the ticket's own suspicion that `parseUnnumbered` "likely has the same defect" was correct.
