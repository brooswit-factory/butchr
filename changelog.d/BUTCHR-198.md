### Changed
- **`get_doc_comments`'s tool-surface description no longer tells you to sort its results by numeric comment id (BUTCHR-198/BUTCHR-202).** This description is returned live to every project-tier agent over MCP, and it previously advised callers to "sort by `id` numerically yourself, the way `newestCommentId` does, if you need newest-first". **That advice is withdrawn: it does not work.** Confluence footer-comment ids are NOT monotonic with creation time — measured independently on two different project root docs (on one, id `17334328` was created at `14:58:06.003Z` and id `17104948` 24s LATER at `14:58:30.387Z`, an id lower by 229,380; replaying ten real footer comments in creation order against a max-id watermark, 6 of 10 would never have been surfaced). **There is currently no reliable way to recover newest-first order from this verb's output**, and the description now says so. If you wrote logic that followed the old advice, it inherited the defect at the level of method — re-derive rather than assume. The raw data is re-derivable at any time with `get_doc_comments()`.

### Fixed
- **A false factual assertion about the world, recorded as verified, corrected in six sites across five files (BUTCHR-198/BUTCHR-202).** `newestCommentId`'s doc comment (`src/resources/project.ts`) asserted that Confluence footer-comment ids are "monotonically increasing platform-wide, confirmed live". That was false, and it was the stated reason the surrounding code is shaped as it is — **a wrong premise recorded as verified is worse than an unexamined one, because it defeats the next person who checks by looking as though someone already did.** Corrected at the origin; at `src/tools/speak.ts`, which inherited it as a post-condition that does not hold (its callers, `escalation-loop.ts`'s dedupe among them, read that output as newest-first — now documented as known-wrong, with the caller-side consequence filed as BUTCHR-205); at the `get_doc_comments` description above; at `check_in`'s epics-in-review loop (`src/tools/defs.ts`), which called its Jira reader "always correct" for the purpose; at `src/resources/issue.ts`, which credited "a monotonically-growing newest-comment id" for safety that actually rests on id distinctness plus the reader's explicitly-requested `orderBy=-created`; and in the pending `changelog.d/BUTCHR-171.md` fragment, which restated the same guarantee and would otherwise have carried it into the released changelog. **Documentation only — no behaviour changed anywhere.** The ordering defect itself is deliberately downstream (BUTCHR-195).
- **The inbound "is there something new" rule is now stated rather than inferred, and it is THREE surfaces, not two tiers (BUTCHR-198).** (1) The Confluence root-doc watermark: max-id reduce over an unsorted read — premise MEASURED FALSE. (2) `check_in`'s epics-in-review watermark: the same max-id reduce over a Jira read that *does* request `orderBy=-created`, but the reduce discards input order entirely and re-derives "newest" from id magnitude, so the requested sort protects it not at all — its correctness rests on Jira comment-id monotonicity, which is **UNMEASURED**, neither established nor refuted. (3) The issue tier that carries `[review]` lines and `ANSWER` replies: no max anywhere, equality only against `comments[0]` of an explicitly `-created` read — ordering REQUESTED rather than merely observed, though it was not possible to confirm from Atlassian's published reference that the parameter is a guaranteed contract rather than best-effort. **In every case the loss is in what is OBSERVED, not in the comparison** — the comparison is `!==` and is sound, so changing the operator would fix nothing. Wake trigger and watermark write are one function over one read, so the blast radius is not split.
