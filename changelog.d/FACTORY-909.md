### Added
- **A Jira native `parent` (Epic-link) relationship is now treated as an equivalent boss relationship to an `Implements` link (FACTORY-909), closing the FACTORY-908 orphan bug: a Story/Task filed under its Epic/Story via Jira's native parent field ALONE (no `Implements` link) is no longer an orphan, and its Epic/Story boss can `start_worker`/`check_worker`/`finish_worker`/`shelve_worker`/`prioritize_worker`/`correct_worker`/`tell_worker` it, and `finish_without_a_boss` correctly refuses it self-closing.** `resolveBoss` (`src/tools/docs.ts`) is the single, pure, I/O-free resolver `assertOwnWorker` and `finishWithoutABoss` (`src/tools/relationship.ts`) now share: `Implements` wins whenever both an `Implements` link and a native parent exist and disagree (logged as `[relationship] Implements/parent disagreement child=<k> implements=<boss> parent=<p> — Implements wins`), and a native parent is only honoured when its tier is one this fleet recognises as an equivalent boss relationship — a Story's parent must be an Epic, a Task's parent must be a Story (`isEligibleParentTier`).
- **`[butchr:missing-implements]` fallback warning**, for the one case (A) cannot cover: a native parent exists but is not an eligible tier for the child. `assertOwnWorker` posts exactly ONE comment on the child (idempotent — gated on the label, no re-post), naming the parent and the exact `jira_link_issues` call to add the missing `Implements` link, sets the new `butchr:missing-implements` label (registered in `src/labels/registry.ts`, verb-owned, deliberately never withdrawn), and logs `[relationship] missing Implements link child=<k> parent=<p>`.
- **The boss-side closing guard (`finish_worker` / `finish_without_a_boss` / `submit_to_boss`) now also sees parent-only children.** `findWorkers`'s Implements-only view cannot see a child linked only by Jira's native parent field — fixing only the child side would have turned a loud "no boss" refusal into a silent premature `Done` past the second-identity rule. The shared `openWorkers` guard now also pays one `ops.search(parent = "<key>" AND issuetype in (Story, Task) AND status != Done)` per call (a deliberate, documented cost increase — see that function's own doc comment) so a live, non-Done, parent-only child still blocks its boss from closing. `findWorkers` itself, `new_worker`'s duplicate-child idempotency check, and `stand_down`'s watch set remain Implements-only — a named, deliberately-scoped-out gap, not an oversight.
- Corrected a now-falsified claim in `src/workspace/registry.ts`'s `PARENT` registry entry: it asserted Jira's native `parent` field is "EMPIRICALLY ALWAYS NULL" for every issue in this project. That was true when written (BUTCHR-169) but is false today — `parent` is populated on dozens of live FACTORY issues — so a correction note was appended rather than leaving two sources of truth disagree. This does not reopen BUTCHR-169's own fix (`SpawnSpec.parent` still derives from the `Implements`-link read, never from `issue.parent` directly).
- Table-driven tests (`test/unit/docs.test.ts`, `test/unit/relationship.test.ts`) cover: Implements-only (unchanged), parent-only (now recognised), both agreeing, both disagreeing (Implements wins + logged), neither (orphan, unchanged), Task under Story, Story under Epic, a non-eligible parent tier (refused + warning fires), the warning comment posted exactly once per ticket, and the boss-side guard refusing a close while a live parent-only child is open.
