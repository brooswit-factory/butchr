### Fixed
- **`correct_worker` can no longer leave a ticket permanently uncorrectable once its description grows large (BUTCHR-145/BUTCHR-140/BUTCHR-130).** Its archive-before-replace safety already refused to edit without first preserving the superseded text as a `[correction]` comment — correctly — but once `why + header + old description` exceeded Jira's ~32767-character comment cap, that archive could never post, and no other verb can shrink a description, so the ticket deadlocked. Live, measured case: BUTCHR-139.
- When the archive body exceeds the cap, it is now split into a numbered, chained sequence of comments (`[correction] (part i of N) ...`) instead of failing. The concatenation of the parts reproduces the superseded text exactly, including through UTF-16 surrogate pairs (astral-plane characters are never split mid-pair). Every part stays greppable via the existing `[correction]` marker. An ordinary under-cap correction is completely unchanged: exactly one comment, same body, same wording.
- A chain that fails partway through now leaves a self-evidently incomplete record rather than reintroducing the archive-integrity defect this same fix closes: a best-effort follow-up comment, tagged with the new exported `CORRECTION_CHAIN_INCOMPLETE_MARKER` (`[correction-incomplete]`), states exactly how many parts were needed and how many posted before the caller ever sees the description replaced. A broken chain fails closed — the description/summary are never edited — same as today's single-comment archive failure.
- A successful correction now warns in its result message when the just-written description is within 3000 characters of Jira's description limit, since the next correction on that ticket will likely need its own archive chained. Worded for the world this fix creates: the next correction will still succeed, never "will fail."
- Established live (not inherited) which payload Jira's comment cap is measured against: plain-text character count, not UTF-8 bytes and not the serialized ADF payload — the same measure the existing incoming-description size pre-check (BUTCHR-128) already uses, now confirmed correct rather than assumed.
- BUTCHR-128's incoming-size pre-checks and its `[correction-rejected]` annotation for a replace that fails after a successful archive are unchanged; their tests pass unmodified.
