### Added
- **Rules reload without a daemon restart (FACTORY-657, FACTORY-643 slice 1, GitHub issue #616).** The daemon's loaded rules now live behind a `RulesHolder` (`src/rules/rules.ts`) that every rule-consuming codepath reads through per poll instead of a startup-captured snapshot. Sending the daemon `SIGHUP` re-reads the rules file (`src/rules/reload.ts`'s `reloadRules`, the exact same `loadRules`/`parseRules` validation `butchr rules check` dry-runs) and swaps the holder's contents in place; an invalid file (bad JSON, a schema violation) leaves the running rules untouched and logs the problem(s) once, with the daemon still up. A **missing** file is only accepted as a valid "zero rules" reload when the holder is already empty — over a non-empty holder it is refused (keeping the running rules) rather than wiping every rule, since a vanished/moved/bad-mount file is far more likely an accident than an operator's deliberate "disable everything" (a **present** file that parses to zero rules IS accepted either way, and logged loudly). A successful reload logs `butchr: rules reloaded from <path>: N enabled (ids)` plus which ids were added/removed/changed. A rule removed or disabled by a reload does not kill its agent(s) mid-ticket — the existing reconcile/reap path ends them on a later poll, exactly as a restart's first poll already does today. `reloadRules(holder)` and `getRules()` are also exposed on the daemon's web-app deps (`src/web/view.ts`'s `ViewDeps.reloadRulesNow`/`getRules`, not wired to any route in this slice) for FACTORY-663's in-process web write path and FACTORY-660's rules previewer to use directly — no HTTP endpoint or CLI subcommand added in this slice, per this ticket's own scope correction. README's "Applying a change" and "First run" sections now describe `SIGHUP` instead of "there is no reload path", including which provider activations still need a restart and the missing-vs-present-empty-file distinction.
