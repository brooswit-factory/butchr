### Fixed
- **Every boss-facing priority surface now says, in plain text, that priority does not affect admission order.** `prioritize_worker`, `new_worker`'s `priority` parameter, `file_where_it_belongs`'s `priority` parameter, `jira_create_issue`'s priority sentence, and `jira_set_priority` all previously implied (or at least never denied) that raising a ticket's priority would change what gets staffed first — true before BUTCHR-284's admission controller, false since, and nothing said so. Each now states the mechanism plainly: "priority is not read by admission or reconcile, so it does not change which ticket is staffed first" — a deliberate policy state (BUTCHR-299/BUTCHR-304 own whether that should ever change), not a bug. `briefs/story.md`, `briefs/epic.md` and `briefs/project.md`'s own "revise priority as reality shifts" guidance gets the same sentence, since it implied an effect on staffing; `briefs/task.md`'s mention (who sets priority, not its effect) is unchanged. Pinned by a new test in `test/unit/admission.test.ts` that fails if priority ever becomes an input to `orderByWait`/`admit()`'s ordering, plus a lightweight backstop in `test/unit/tools.test.ts` asserting the sentence is present on all five tool surfaces.
