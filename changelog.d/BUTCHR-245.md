### Added
- **A per-poll reaper reclaims a herdr workspace whose agent exited on its own — a Claude session-limit refusal, a crash, a manual `/exit` — instead of leaking it forever (BUTCHR-245).** `HerdrHerd`'s only route from an issue key to a pane was `agent.list()` (`byIssue()`, `src/agents/herd.ts`); the moment an agent vanished from that list, `stop()` on its issue became a silent successful no-op, `reconcileNow`'s BUTCHR-147 failure handling never saw anything, and the workspace/pane stayed open, unreachable by anything butchr remembered. Measured live: 24 of this daemon's own 49 workspaces were agentless (71% was the reviewer's own herd's figure — this host runs a second, independent butchr daemon under a different Unix user, invisible to this one).
- New `src/agents/reap.ts`: `strandedCandidates()` — a pure ownership+agentless join over one poll's `workspace.list()`/`pane.list()`/`agent.list()` snapshots, no herdr I/O of its own. Ownership is proven by two facts that must agree, never by the label alone: a workspace is butchr's iff its label `L` pairs with a pane, in that same workspace, whose `cwd` is exactly `join(workspaceRoot(), L)` — `buildWorkspace()`'s own convention. A label alone is free text a human can type, and a project-tier label is a bare project key that collides with anything.
- `HerdrHerd.strandedCandidates()`/`HerdrHerd.closeStranded()` (`src/agents/herd.ts`): the herdr-I/O half. `closeStranded()` is the decisive safety layer — it calls `pane.processInfo` for every one of a candidate's panes and closes the workspace only if every call succeeded and none reported a `claude` process in its foreground (reusing `isClaude()`, already in this file for `staleIssues()`). A thrown call, a missing `process_info`, or an empty `foreground_processes` are all UNKNOWN, never dead — same unknown-≠-stale discipline `staleIssues()` already applies — and a single live pane vetoes the whole workspace. This is what makes the guard safe against an agent that is alive but absent from `agent.list()` (herdr's registry lost it across a restart, but the process is still there): `agent.list()` can't see it, `processInfo` can.
- `ReapGuard` (`src/agents/reap.ts`): an across-poll grace period — a workspace must be observed agentless-and-owned on at least two consecutive polls of a given tracker AND for at least 60 seconds of wall clock before it's eligible, both conditions together (a short poll interval must not collapse the window). This covers the seconds between `workspace.create` returning and `agent.start` registering the agent, during which a perfectly healthy spawn-in-progress looks exactly like a stranded slot. An id absent from any later poll's candidate set (gained an agent, or the workspace disappeared) loses its accumulated observations entirely.
- `createReaper()` (`src/agents/reap.ts`): the per-poll orchestration — gathers candidates, grace-filters them, verifies+closes each capped at 10/poll, and is fully fault-isolated: a gather failure or one candidate's close rejecting degrades to "reclaimed nothing this poll," never fails the poll or blocks any other candidate. Logs one greppable `[reap] reclaimed workspace <id> (<label>)` line per reclaim plus a per-poll summary count — deliberately no Jira comment; a reclaim is routine housekeeping, and a fleet-wide reclaim burst posting dozens of comments at once would bury the channel.
- Wired into `reconcileNow` (`src/daemon/loop.ts`) as new optional `ReconcileOptions.checkReap`, called once per poll before the spawn loop — same shape/optionality as `checkCrashLoop`/`checkReconcileFailure` — and threaded into both the issue and project loops (`src/daemon/index.ts`), each with its own `Reaper`/`ReapGuard` instance, sharing the one live `HerdrHerd`. Running before the spawn loop lets a slot freed this poll serve this poll's own spawns; the grace period, not this ordering, is what actually protects an in-flight spawn.
- Scoped to the WORKSPACE, never the issue key: a duplicate label (one live workspace, one stranded) is exactly the case an issue-keyed check would get wrong, since the key itself is still in `agent.list()`. The reaper asks "does *this workspace* contain a live agent," never "is this key running," so the live one always survives.
