### Added
- **A shared mechanism, `src/media/blind-spot.ts`, turns each of three source-literal scanners' "WHAT THIS CANNOT SEE" prose sections into an enumerable, type-checked, runtime-verified list (BUTCHR-222/BUTCHR-224).** `HEADER_BLIND_SPOTS` (`src/headers/header-scan.ts`), `LABEL_BLIND_SPOTS` (`src/labels/label-scan.ts`), and `WORKSPACE_BLIND_SPOTS` (`src/workspace/workspace-scan.ts`) replace the module-header bullet lists those three files used to carry — 14 entries total, 12 backed by an executable witness and 2 (`workspace`'s `nonTemplateWriteSites` and `mergedNotDeployed`) carrying a written `noWitnessReason` instead, because they name gaps no source-reading check can construct an input for.
- **Every witnessed entry pairs a silence assertion with a positive control, and the pairing is enforced structurally, not by convention.** `witnessBlindSpot(id, { silence, positiveControl })` runs both halves before recording `id` as executed — `BlindSpotWitnessCheck` requires both fields, so a later author cannot write an unpaired "the detector stays quiet here" assertion by forgetting the other half. The positive control (a near-miss variant of the same input that IS detected) is what proves the silence came from the specific claimed property and not from the detector simply being dead on that fixture.
- **Two independent doors close two independent gaps.** A type-level discriminated union (`BlindSpotWitnessField`) makes `witness: null` require a written `noWitnessReason` — the omission fails to compile, not merely go unreviewed — mirroring the door `DetectorField` (`src/media/registry.ts`) already uses for `withdrawnBy`. That door cannot see a `witness: "some-id"` naming a test nobody wrote, because the string alone compiles whether or not anything executes under that id; `assertBlindSpotCoverage`, called at the end of each of the three registry test files (`test/unit/header-registry.test.ts`, `test/unit/labels-registry.test.ts`, `test/unit/workspace-registry.test.ts`) after that file's own `witnessBlindSpot` calls, closes that second gap by comparing every declared witness id against the ids actually recorded at runtime and failing on any that never ran.
- **What was true before this ticket: those blind-spot claims were prose only** — a `WHAT THIS CANNOT SEE` bullet was satisfiable by writing a sentence and running nothing, with no mechanism able to tell a true claim from a stale or simply wrong one.
- **What this does NOT claim, read before citing this fragment as "blind spots are now verified" — it is not that: promoting a prose bullet into a value-level entry does not make the list COMPLETE.** Nothing added here checks that every prose bullet a detector's module header once carried became an entry, and nothing checks that a detector has no blind spot its author never noticed — that residual layer stays self-declaring; this mechanism narrows what a *declared* claim can get away with, it does not audit the declaration itself. What it actually buys: every DECLARED blind spot stops being a sentence and becomes a measurement — closing one of those holes (making a scanner see something it claimed it couldn't) turns the suite red instead of leaving a stale comment sitting uncontradicted.
- **A narrower, related gap, found in BUTCHR-224's own review round 1 and not closed here either:** the runtime coverage door (`assertBlindSpotCoverage`) is opt-in per list, wired by a call each caller must remember to add — nothing detects that call's own absence or deletion. Measured, not argued: deleting the coverage call from `test/unit/labels-registry.test.ts` at commit `3b118dbe` left `LABEL_BLIND_SPOTS` and its four declared witness ids untouched and `bun test test/unit test/load` fully green (one fewer test, no failure). Deliberately left unguarded rather than adding a fourth check that could itself be deleted with nothing catching that.
