### Fixed
- **A managed-session agent that kept dying and being spawned again produced no audible signal at all — nothing in the journal recorded why the previous pane went away (FACTORY-47).** `startManagedSessionsLoop` (`src/daemon/session-definitions-loop.ts`) had no `checkCrashLoop` seam, unlike the ordinary rule-agent loop, which has wired `createCrashLoopDetector` (BUTCHR-141) since that ticket landed. A managed session whose agent process crashes right after spawning (a startup crash, an MCP config that fails to load, a session-limit refusal that never clears, ...) is genuinely gone from `herd.runningIssues()` on the very next poll, so it is reported as an ordinary `spawn`, never a `respawn` — there is no "stale" agent for `staleIssues()`/`onRespawn` to name, and nothing else in this loop watches for the same id being spawned over and over. Fixed by threading `checkCrashLoop` through `ManagedSessionsLoopDeps` into `runResourceLoop`, and wiring a dedicated `createCrashLoopDetector` instance for managed sessions (`src/daemon/index.ts`) that logs directly instead of posting a Jira comment — a managed-session id is a filesystem path, never a ticket, so (unlike the rule-agent instance's `isQueryLevelAgent` branch) this one unconditionally bypasses Jira. A managed session repeatedly spawned within the rolling crash-loop window now gets a `WARNING: [crashloop]`-style journal line naming the id and the count, exactly like an ordinary rule agent already does.
