### Fixed
- **`finish_without_a_boss`'s branch (b) is now credential-invariant: the same Epic in the same project gets the same verdict on every daemon (BUTCHR-92/BUTCHR-333).** Branch (b) (BUTCHR-326) previously answered "does my project have a boss" by calling `resolveEligibleProjects`, which filters `GET /project/search?status=live` down to projects LED BY THE CALLING CREDENTIAL before ever reading the `butchr` property — so the verdict silently depended on which daemon's account handled the call. Demonstrated live: same Epic, same project carrying the property, varying only the project's lead — lead = caller's credential → refused; lead = another account → transitioned to Done, no refusal. Because the project tier and the epic tier normally run under *different* credentials, this likely made the whole BUTCHR-326 gate a no-op exactly where the six-epic self-close defect it was built to close actually lived — the existing unit tests couldn't catch it, since their fake world always set the project lead to the caller's own `getMyself()`.
- Branch (b) now reads the caller's own project's `butchr` root-doc property directly — `readProjectTierProperty(ops, projectKey)`, a new export on `src/resources/project.ts` — with no `getMyself`, no project search, no lead filter, and no allowlist. Nothing about the calling credential enters the verdict. This is also cheaper: one property read for one project, instead of `getMyself` + a project search + N property reads.
- The `?.rootDoc?.id` test that used to live inline in `resolveEligibleProjects` is now this one exported helper, and `resolveEligibleProjects` calls it too — one place knows that shape, not two. `PROPERTY_KEY` stays module-private: the helper owns the whole property read rather than exporting the key for a second call site to reuse.
- **Renamed the concept branch (b) tests, everywhere it's described, away from "eligible."** In this codebase "eligible" already means "live AND led by this credential AND carries the property" (`resolveEligibleProjects`'s own, still-correct meaning for its own callers — `loadProjects`, `list_peers`, `tell_peer`, unchanged by this PR). Branch (b)'s rule is only the last conjunct, so calling it "eligibility" pointed a reader at the wrong resolver and the wrong conclusion. It's now described as carrying a project-tier root doc / having a project tier — in `src/tools/relationship.ts`'s doc comment, `src/tools/defs.ts`'s `finish_without_a_boss` description, and `briefs/epic.md`.
- **Fails closed exactly as before, same message shape**: a clean not-found (no `butchr` property) means no project tier, so branch (b) does not fire and the caller falls through; any other read failure refuses with the same distinct "could not determine whether … has a boss" message, now naming the direct property read instead of the eligibility search.
- **A named, intended consequence, not a new gap**: a project can carry the property while no running daemon's credential leads it. An Epic there is still refused by branch (b) and waits, visibly, In Review, with nobody yet able to call `finish_worker` on it — BUTCHR-189's "make audible where there is no exit." Do not read this as a reason to add a staffing check here.
- **`briefs/epic.md`'s closing step no longer teaches `finish_without_a_boss` as the safe default.** It previously said reaching for `finish_without_a_boss` "first when unsure is safe, never wrong" — backwards: when the boss check can't find a boss for *any* reason (this defect, or a future gap), `finish_without_a_boss` closes the epic silently, with no review at all — the exact failure this whole story exists to prevent. `submit_to_boss` is now stated as the default closing step and the answer when unsure; its worst case, waiting visibly In Review, is named as the deliberate safe failure, not a hazard. `finish_without_a_boss` is now scoped to an epic that *knows* its project has no project tier. The claim that `submit_to_boss` is "the event that wakes your project" is also qualified: it wakes a project tier that is actually staffed (`loadProjects`'s batched JQL search runs on the project's own daemon, whose credential does lead its own projects), but a property-carrying project with no daemon leading it wakes nobody — both now stated, neither overclaimed.
