### Fixed
- **`agent.start` was firing on a pane `workspace.create` had just returned, before herdr considered it an "available shell" (BUTCHR-268).** The spawn path (`HerdrHerd.spawn()`, `src/agents/herd.ts`) called `workspace.create` then `agent.start` on the returned root pane back-to-back, with no gap. Measured directly against a live herdr via `HerdrClient` (`scripts/repro-pane-busy.ts`, 8 trials/gap, repeated — a single-sample sweep passed at gap=0 and is exactly the trap this ticket's own history warns about): at gap=0ms `agent.start` rejected with `agent_pane_busy` on **4/8** trials on this branch's own commit (the ticket that filed this measured 6/8 on a separate run); at gap≥50ms it was 0/8 every time. Concurrency was measured and ruled out as the driver (flat ~60% across a 3x change in simultaneous create+start pairs) — this fix does not touch the reconcile loop's spawn fan-out.
- **Fleet-level "before", journal-measured, two windows (see Limitations for why two).** 2026-09-10 00:00–11:34 (servyboi, `butchr.service`, build 467c36e8, unmodified): 42 `agent_pane_busy` rejections out of 74 logged spawn/respawn attempts (57%), 26 distinct tickets, 3 `[reconcile]` complaints and 1 `[crashloop]` complaint — the crashloop one (BUTCHR-279) confirmed self-healed within ~2 minutes of posting. That window spans a host reboot (~11:12), two daemon restarts (~11:14, ~11:27:45) and a whole-fleet capacity park (~11:24), so it is not one clean population — see Limitations. A second, narrower window taken entirely inside the current daemon generation (11:27:45–11:46, pid 21200, no restart inside it): 16 `agent_pane_busy` rejections across 12 distinct tickets, 3 more `[reconcile]` complaints, 2 more `[crashloop]` complaints (BUTCHR-279 again, and BUTCHR-275). The only poll in this window that logged its own desired-set size is the first (9/9), so this window has no attempt denominator and no rate should be derived from it — a successful spawn writes no journal line, so failures cannot be compared against successes here. Reported as a set and a count, not a ratio; the 74-attempt window above is the one with a denominator. This window opens with the daemon's own `[crashloop]` WARNING that the "entire desired set (9/9) is in plan.spawn this poll", i.e. herdr momentarily reported nothing running right after the restart. That is the exact condition the parent epic separately measured on a different herd: spawns firing for tickets that already had a live agent running elsewhere, all rejected by `agent_pane_busy` — which in that scenario is accidentally the only thing standing between the daemon and a duplicate agent (tracked as BUTCHR-282, shelved, not this ticket's to fix).
- **Fix: wait before every `agent.start` attempt, and retry ONLY `agent_pane_busy`, bounded.** `HerdrHerd` now waits `PANE_READY_WAIT_MS` (200ms) before each attempt — including the first — and retries up to `PANE_BUSY_MAX_RETRIES` (4) additional times when, and only when, the rejection carries `HerdrError`'s `agent_pane_busy` code; any other `agent.start` rejection (including a herdr transport outage, where `agent.list`/`pane.read` fail with `socket error` and every tracked pane reads `pane_not_found`) still reaches `spawn()`'s own catch on the first attempt unchanged, so it can't become a hot loop, and the pane it just created still gets closed (BUTCHR-111's leak-safety guarantee — covered by a dedicated test). Worst case this adds `PANE_READY_WAIT_MS * (1 + PANE_BUSY_MAX_RETRIES)` = 1000ms to a failing spawn, negligible next to `KICKOFF_VERIFY_MS`'s existing multi-second wait, against a failure that used to cost a whole poll cycle. Re-measured with the fix's own logic (`scripts/repro-pane-busy.ts fixed`, same live herdr, gap=0, the worst case the table above found): **0/16** `agent_pane_busy` rejections reached the caller — but see Limitations: that number is from throwaway harness workspaces with no possibility of an already-live agent, so it says "the retry works," not "the retry is a net win during a duplicate-spawn window."
- **Harness hygiene.** `scripts/repro-pane-busy.ts` (new, manual/operator-only — its own `main()` is never exercised by `bun run check`, which only proves it parses and its imports resolve; see `scripts/load/inventory.ts`'s `RUNS_ON_IMPORT`, same treatment as `verify-workspace-ground-truth.ts`/`reap-dry-run.ts`) sweeps its own leftover workspaces by label (`repro-268`/`err-check`/`repro` prefixes) at the START of every run, not only in a `finally` — a mid-run kill (e.g. a herdr-server restart) never reaches a `finally`, and this fleet's journal shows that restart-and-respawn pattern happening. Every sweep candidate is verified against a fresh `agent.list()` before being closed, and the ownership predicate is scoped to this harness's own label prefixes only — it never touches BUTCHR-111's reaper or its cwd-based ownership check. This run's own census on this herd found zero residue before and after.

### Limitations, stated deliberately rather than left implied
- **Not a guarantee, a bounded improvement.** The rate table's own 1/8 outlier at gap=1200ms means no fixed wait makes this impossible, only unlikely; a spawn can still exhaust the retry budget and fail. That failure still closes its pane and surfaces exactly as before — this fix narrows the window, it does not remove it.
- **The 0/16 "after" figure does not account for the duplicate-agent-spawn scenario, and this fix likely widens it slightly.** When the daemon (incorrectly) fires a spawn for a ticket that already has a live agent elsewhere — observed live in the 11:27:45 window above, right after a daemon restart — the new pane races the exact same readiness window this ticket fixes. Before this change, that race already let such a duplicate through on roughly the same ~40–60% of attempts the rate table shows for a first try; `agent_pane_busy` only ever blocked it the rest of the time, as an accidental side effect of the same bug this PR fixes, never as a designed guard. This fix's retry pushes a bounded (200ms × up to 5 attempts = 1000ms) window of *additional* attempts at getting the same pane ready, which raises the odds that an incorrectly-fired duplicate spawn eventually succeeds too. It does not create the duplicate-spawn condition and does not remove `agent_pane_busy`'s accidental, partial cover for it — a real guard (excluding a spawn target that already has a live agent) is filed separately as BUTCHR-282 and is deliberately not built here, per the parent epic. If the epic's own measurement says otherwise once this ships, that measurement wins over this reasoning.
- **No true fleet-level "after" in this fragment.** The "after" measurement above replays the fix's own retry logic against live herdr directly (`scripts/repro-pane-busy.ts fixed`), not the deployed daemon — merged is not deployed, and the running build's actual fleet-wide busy/complaint rate after this ships should be re-measured against the journal once it is, inside a single clean daemon generation.
- **`[reconcile]`/`[crashloop]` complaint thresholds and text are unchanged** — out of scope for this ticket by design; if complaints still fire post-deploy on healthy startups, that is a detector-calibration question, not this fix's.
