### Added
- **Parked-ticket detector: a staffed child left in To Do under a live boss now escalates instead of sitting silently forever (BUTCHR-24/BUTCHR-23).** A boss agent (epic or story) that files a child, assigns it, and never moves it out of To Do leaves that child unstaffed — no agent is ever spawned for a To Do ticket — so the boss waits on events from an agent that does not exist. This has already happened in production (BUTCHR-13 parked all four of an epic's stories). Detection (`src/agents/parked.ts`) runs every poll, entirely over data the loop already fetches (`issues`, the active set, and `related`, the Implements-outward children of the active set) — zero extra Jira calls on a normal poll. A ticket is PARKED when it has an assignee, an Implements link to a boss, that boss is "In Progress", the ticket itself is "To Do", and it has held that state continuously (from the daemon's own first observation — a conservative floor, same reasoning as `StalledTracker`) for at least `BUTCHR_PARKED_MINUTES` (default 10).
- Escalation is three stages, all through the daemon's single existing `addComment` seam: **stage 1** posts once on the boss's own ticket at the threshold; **stage 2** posts one follow-up on the boss's ticket if it's still parked one more interval later; **stage 3**, one more interval after that, escalates to the *boss's own boss* (resolved via one `atlassian.links(bossKey)` call — the only extra Jira call in the whole feature, and it only fires once a boss has ignored two prior comments). Each stage dedupes against the boss ticket's own comment history (marker + stable fingerprint + stage tag), so a daemon restart adopts its own prior escalation instead of re-posting it, and a per-boss rate cap (3/hour, mirroring `escalation-loop.ts`) keeps a detector bug from spamming a ticket unboundedly.
- **The "boss never acts" answer**: this fleet's Implements chain is task → story → epic, and epics are the human's own tickets (`docs/agent-model.md`) — so walking one link up from a story reaches the epic, and walking up from an epic reaches nothing. A boss with no inward Implements link (already at the top, or unlinked) is therefore a human-owned ticket by construction: stage 3 re-posts on that boss's own ticket and emits a `WARNING: [parked] ...` log line, so a `journalctl | grep WARNING` surfaces it. There is no separate human channel and none is needed.
- New `BUTCHR_PARKED_MINUTES` env knob (default 10, optional), added to `Config`/`ConfigEnv`, validated in `loadConfig`, printed by `describeConfig`, and documented in `.env.example`. Ten minutes matches `BUTCHR_STALLED_MINUTES`'s default — both measure a comparable "this should have happened by now and didn't" interval, far outside any legitimate mid-decomposition window (a boss filing and activating a child normally does both within one agent turn) while still catching a genuinely parked ticket in minutes rather than a working day.
- New exemption label `butchr:parked-ok`: a ticket carrying it is never reported parked, at any stage — for a deliberately-parked backlog item under a live boss (the one real false positive; KAN-839 is the live example). It is **read-only for the daemon** — never added or removed by butchr — with a guarding comment in `src/labels/plan.ts` and a pinned test (`isDaemonLabel("butchr:parked-ok") === false`) so it can never be folded into the daemon-owned label namespace and silently stripped by `sweepStaleAgentLabels`. Documented in the escalation comment itself, `.env.example`, `docs/agent-model.md`, and one sentence each in `briefs/epic.md`/`briefs/story.md`.
- The generic dedupe (marker + fingerprint scan) and per-key hourly rate cap are factored into a new, dependency-free `src/agents/escalation-helper.ts`, written so the existing blocked-dialog escalator (`src/agents/escalation-loop.ts`) can later move onto the same primitives without a behaviour change. Not wired into `escalation-loop.ts` yet: PR #108 (BUTCHR-5) was open against that exact file when this was written, and refactoring it here would have conflicted with an in-flight review — the consolidation is deferred to a follow-up once #108 lands.
- **Scope, deliberately narrow: To Do only.** A different stale state — e.g. a task left In Review after its story approved and merged its PR (BUTCHR-18) — is a legitimately long-lived state in general (a reviewer may be mid-task or asleep), so the same short-threshold rule would fire constantly on healthy work. That needs PR state from `PrTracker` (`src/labels/pr.ts`), a different threshold, and its own ticket — not built here, and not stubbed out as dead configuration.

### Deploy impact
A pull plus a `systemctl --user restart butchr.service` (or equivalent) is the entire deploy — no separate build step. `BUTCHR_PARKED_MINUTES` is optional (defaults to 10); nothing breaks if it's left unset. Across the restart, the detector's in-memory floor and stage state for any ticket already mid-escalation is lost and starts fresh on the next poll — this can only ever DELAY that ticket's next escalation stage, never fabricate one, and stage-1 dedupe against the ticket's own comment history means a still-parked child does not get a duplicate stage-1 comment once the fresh floor catches back up. Already-running agents are entirely unaffected — this feature only ever reads `issues`/`related` and writes Jira comments; it never touches the herd/reconcile path.
