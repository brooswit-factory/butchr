### Added
- **Validated, atomic, backed-up `rules.json` writes, as a library (FACTORY-658, FACTORY-643 slice 2, GitHub issue #616).** `src/rules/write-rules.ts`'s `writeRulesFile` is the one function every rules-file writer (the web write path, FACTORY-663) goes through: validates the whole resulting file through the same entry point the daemon's own startup uses before touching disk (a bad edit writes nothing, no temp file left behind), then — holding an in-process plus cross-process (`O_EXCL` lock file with pid/staleness detection) write lock across the whole read-validate-backup-rename span, so concurrent writers never interleave — backs up the current file to `rules.json.bak-<UTC timestamp>` (unique even across two writes in the same second; fsynced; pruned to the newest 20), then writes atomically — a unique `O_EXCL`+`O_NOFOLLOW` temp file in the same directory, fsync, rename, directory fsync — preserving the file's existing mode. An optional `opts.ifMatch` (sha256 etag) refuses a write whose expected prior content is stale, for optimistic concurrency; `rulesEtag` reads the current etag for a GET handler. `restoreBackup` restores a previous backup through that exact same validated/atomic/locked path, byte-identical to the backup's own bytes, for a web UI "Undo". `setRuleEnabled` is a pure text-level editor that flips one rule's `enabled` field and leaves every other rule and byte of formatting untouched. No CLI or HTTP route in this slice — `butchr rules check` is unaffected.
