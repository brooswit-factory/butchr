### Added
- **`docs/rules.example.json`: the canonical example rules file every deploy provisions its rules file from (BUTCHR-400, story BUTCHR-399).** One `jira-work` rule per ticket-worker role — `epics`, `stories`, `tasks`, `bugs`, `subtasks` — each `assignee = currentUser()` plus an `issuetype` clause plus `status IN ("In Progress", "In Review")`, as a sensible default rather than an enforced floor: an operator who wants a rule to also match `To Do` (or any other status) is free to write that query. This replaces the `statusCategory != Done` shape observed in the live rule files that prompted this story: that shape also matches `To Do`, so a `To Do` ticket took a capacity slot and a move *into* `To Do` woke its agent instead of stopping it. `test/unit/rules-example.test.ts` loads the file through the real `loadRules`/`parseRules` loader (not a hand-copied fixture) so a future schema change that the example no longer satisfies fails there, and asserts every rule in it keeps the `In Progress`/`In Review` shape and never matches `statusCategory`.

### Changed
- **README gets a new "Rules file" section** stating the `In Progress`/`In Review` convention, pointing provisioning at `docs/rules.example.json`, and correcting how a rules-file edit is actually applied: the file is read once at startup (no reload path) so an edit needs a daemon restart, but a restart does **not** stop every worker — each reconcile poll (including the first one after a restart) diffs rule matches against herdr's own live agent list, so a resident agent whose ticket still matches its rule is left running untouched; only agents whose tickets no longer match any enabled rule are stopped. Verified against `src/reconcile/plan.ts` and `src/daemon/loop.ts` before writing this, per the owner's live-restart measurement on BUTCHR-399 (residency 16 → 13, only `To Do` tickets dropped).
- The same section resolves, rather than repeats, a location discrepancy: the code's own default (`src/rules/rules.ts`'s `rulesPath()`) is `BUTCHR_RULES_FILE`, else `$XDG_CONFIG_HOME/butchr/rules.json`, else `~/.config/butchr/rules.json` — this repository has no `butchr-new`/`resource-rules.json` branch anywhere, so a live daemon reading from such a path is running an explicit `BUTCHR_RULES_FILE` override this repository cannot see, not a second coded default.

### Known gaps
- **Capacity naming is not in `docs/rules.example.json`, and it never needs to be added there (corrected by BUTCHR-401).** This fragment originally said the example and README should "adopt the field once BUTCHR-392 lands" — the owner has since clarified that framing was wrong: the default capacity role is `worker`, so a ticket-worker rule takes no capacity flag at all, ever. Only an always-on agent is flagged `sentinel`. See `changelog.d/BUTCHR-401.md` for the README correction. BUTCHR-392 has since merged: the field is `role: "worker" | "sentinel"` (`src/rules/rules.ts`), default `"worker"` — named exactly in the README as of BUTCHR-414.
- **This fragment originally also shipped a log-only startup warning for a `jira-work` rule with no `status` clause (corrected by BUTCHR-414).** The owner reversed the underlying requirement — a status-less or `To Do`-inclusive `jira-work` query is a choice Butchr never gates, prevents, or warns about — so that warning (and its test) never shipped to a release and has been removed outright; it never existed in any tagged version.
