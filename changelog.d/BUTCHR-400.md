### Added
- **`docs/rules.example.json`: the canonical example rules file every deploy provisions its rules file from (BUTCHR-400, story BUTCHR-399).** One `jira-work` rule per ticket-worker role — `epics`, `stories`, `tasks`, `bugs`, `subtasks` — each `assignee = currentUser()` plus an `issuetype` clause plus `status IN ("In Progress", "In Review")`. This replaces the `statusCategory != Done` shape observed in the live rule files that prompted this story: that shape also matches `To Do`, so a `To Do` ticket took a capacity slot and a move *into* `To Do` woke its agent instead of stopping it. `test/unit/rules-example.test.ts` loads the file through the real `loadRules`/`parseRules` loader (not a hand-copied fixture) so a future schema change that the example no longer satisfies fails there, and asserts every rule in it keeps the `In Progress`/`In Review` shape and never matches `statusCategory`.
- **An optional, log-only startup warning for a `jira-work` rule with no `status` clause at all** (`src/rules/status-clause-warning.ts`, wired into `src/daemon/index.ts` right after rules load). Detection is deliberately conservative — any occurrence of the word `status`, so `statusCategory != Done` still counts as "has a status clause" for this check, even though it is the shape this ticket steers deploys away from; the check only flags a query that considered status *not at all*. This is informational only: it never refuses startup, drops a rule, or rewrites a query, per the consolidation spec's requirement that Jira status stay fully query-configurable with no fixed status rules baked into `jira-work` staffing.

### Changed
- **README gets a new "Rules file" section** stating the `In Progress`/`In Review` convention, pointing provisioning at `docs/rules.example.json`, and correcting how a rules-file edit is actually applied: the file is read once at startup (no reload path) so an edit needs a daemon restart, but a restart does **not** stop every worker — each reconcile poll (including the first one after a restart) diffs rule matches against herdr's own live agent list, so a resident agent whose ticket still matches its rule is left running untouched; only agents whose tickets no longer match any enabled rule are stopped. Verified against `src/reconcile/plan.ts` and `src/daemon/loop.ts` before writing this, per the owner's live-restart measurement on BUTCHR-399 (residency 16 → 13, only `To Do` tickets dropped).
- The same section resolves, rather than repeats, a location discrepancy: the code's own default (`src/rules/rules.ts`'s `rulesPath()`) is `BUTCHR_RULES_FILE`, else `$XDG_CONFIG_HOME/butchr/rules.json`, else `~/.config/butchr/rules.json` — this repository has no `butchr-new`/`resource-rules.json` branch anywhere, so a live daemon reading from such a path is running an explicit `BUTCHR_RULES_FILE` override this repository cannot see, not a second coded default.

### Known gaps
- **Capacity naming (`workers`/`sentinels`) is not yet in `docs/rules.example.json`.** BUTCHR-392, which is expected to add that field to `Rule` (`src/rules/rules.ts`), had not merged into `main`/`BUTCHR-399` as of this branch. The example and README note this and say to adopt the field once BUTCHR-392 lands, rather than inventing it ahead of the schema.
