### Fixed
- **A managed session launched with a non-default `permissionMode` (e.g. `"auto"`) respawn-looped forever, and one launched with `strictMcpConfig: true` could silently run without `--strict-mcp-config` after a herdr restart, because `staleIssues()`'s reconstructed "expected" argv never carried either field (FACTORY-43).** `staleIssues()` (`src/agents/herd.ts`) rebuilds the `SpawnSpec` it expects a running managed-session agent to have been launched with from scratch, since it holds no reference to the original spawn's spec — it already did this correctly for `mcpServers`/`externalMcpServers` by persisting them non-secretly at build time (`.butchr-mcp-servers.json`/`.butchr-external-mcp.json`, `buildWorkspace`) and reading them back (`workspaceMcpServers`/`workspaceExternalMcp`), but `permissionMode`/`strictMcpConfig` were never part of that persist-and-read-back set. Since Drovr's `buildAgentStartParams` always emits `--permission-mode <mode>` (defaulting to `bypassPermissions` when unset), a managed session actually launched with `permissionMode: "auto"` (`specForSessionDefinition`, `src/rules/session-definition-type.ts`) was compared against an expectation that silently assumed `bypassPermissions`, and every poll killed and respawned the agent. Fixed by extending the exact same persist-at-build/read-back-at-check shape to `.butchr-permission-mode.json`/`.butchr-strict-mcp-config.json` (`workspacePermissionMode`/`workspaceStrictMcpConfig`, `src/agents/workspace.ts`), so `staleIssues()`'s expected argv is now built from the SAME data the real launch used, not a second, independently-recomputed guess. Regression tests cover both directions for both fields: a correctly-launched agent is not flagged stale, and a running agent that's missing a flag its own persisted spec now calls for IS flagged stale.
