### Fixed
- **`escalation-loop.ts`'s two `deps.comments(...)` reads treated a failed fetch as "nothing there" and read the wrong resource for a project-keyed target, so a blocked PROJECT agent could never be unblocked by an `ANSWER` (BUTCHR-127/BUTCHR-159).** Both call sites `.catch`ed a rejected read into `[]`. At the dedupe site (`escalate()`) that posted a duplicate escalation on a transient Jira blip — a NOISE bug, bounded and self-healing on the issue tier. At the directive site (`handleBlocked`) it was worse: `rows = []` made `directive` stay `null`, which fell straight through the early `return` into the 15-minute follow-up gate — neither of that gate's two terms reads the fetch outcome — so a failed read didn't just lose the `ANSWER`, it told the boss the daemon was still waiting while the unread answer sat a few rows above the nudge. On the project tier the read wasn't transient: an issue-shaped read against a bare project key is the wrong resource, so it failed (or read the wrong content) on every single call — the dedupe could never find its own prior comment, and the directive read could never find an `ANSWER`, permanently.
- Fixed by routing both reads through `deps.ownChannelComments` (`createOwnChannelComments`, `src/tools/speak.ts`, already wired for the sustained-unresponsive alarm) — the tier-aware reader that resolves an issue key to its Jira comments and a project key to its Confluence root-doc footer comments, storage-format-unwrapped — AND making both fail CLOSED on a rejected read (write nothing, retry next poll), in that order: routing alone, without fail-closed, still fails open transiently; fail-closed alone, without routing, would have permanently silenced a project agent's only audible signal (its dedupe read fails every call, so the fail-open was the sole reason a blocked project agent was ever heard at all). A suppressed write only delays — it fires on the next poll whose read succeeds, never lost.
- Removed the now-dead, issue-only `comments` dep from `EscalatorDeps` and its wiring in `src/daemon/index.ts` — checked for other consumers first (none; every other `deps.comments` in the codebase belongs to a different detector's own, unrelated deps interface) — since `ownChannelComments` is now the only comment-read this module needs, for either call site.
