### Fixed
- **No merge-instructing channel claims `reviews[].commit.oid` "records what the reviewer saw" anymore — that was false.** Confirmed on two PRs: on #135, the review body (immutable text) quotes the approved sha `45ae7783…`, but `reviews[].commit.oid` — GraphQL and REST agree — instead returns `c331c0b8…`, a merge commit whose first parent is the approved sha and second parent is an ancestor of `main`. On #136 (three reviews), an OLDER review still held its original recorded sha while a LATER review's recorded commit had already moved, matching the current head each time it was re-read — so `reviews[].commit.oid` can drift forward across repeated base-merges, and the field this check reads (the LAST decisive review) is exactly the one most likely to have been rewritten. Only a review's own written-at-submission body text stays fixed; we do not assert a specific rewrite mechanism beyond what was observed. The corrected claim, and a new caveat, now appear in every channel `test/unit/merge-check-guard.test.ts`'s `MERGE_INSTRUCTING_BRIEFS`/`MERGE_INSTRUCTING_DOCS` name plus the daemon's own PR-review-state nudge: `briefs/task.md`, `briefs/story.md`, `docs/agent-model.md`, and `prReviewStateNudge` (`src/agents/pr-nudge.ts`, doc comment and rendered string both) — each now also names the existing move for a suspected base-merge: ask for a re-review at the new head, or point at the append-only `[review] APPROVED ... @ <sha>` ticket comment, which GitHub cannot rewrite. The check itself is untouched — it stays strictly better than the `reviewDecision`+`headRefOid` pair it replaced (which failed on every push) — only the surrounding text changes.
