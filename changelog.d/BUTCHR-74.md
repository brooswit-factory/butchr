### Fixed
- **No merge-instructing channel claims `reviews[].commit.oid` "records what the reviewer saw" anymore — that was false.** Verified live on PR #135: the review body (immutable text) quotes the approved sha `45ae7783…`, but `reviews[].commit.oid` — GraphQL and REST agree — instead returns `c331c0b8…`, a merge commit whose first parent is the approved sha and second parent is an ancestor of `main`. GitHub silently re-points a review's recorded commit whenever the branch takes a base-merge, and a base-merge is the ordinary path, not an exotic one (GitHub requires one whenever `main` advances under an open PR). The corrected claim, and a new caveat, now appear in every channel `test/unit/merge-check-guard.test.ts`'s `MERGE_INSTRUCTING_BRIEFS`/`MERGE_INSTRUCTING_DOCS` name plus the daemon's own PR-review-state nudge: `briefs/task.md`, `briefs/story.md`, `docs/agent-model.md`, and `prReviewStateNudge` (`src/agents/pr-nudge.ts`, doc comment and rendered string both). The check itself is untouched — it stays strictly better than the `reviewDecision`+`headRefOid` pair it replaced (which failed on every push) — only the surrounding text changes, to say plainly that the check cannot detect a head move caused by a base-merge and is not sufficient on its own.

### Added
- **The guard now pins the caveat, not just the field name.** `test/unit/merge-check-guard.test.ts`'s existing explicit-list positive assertion (unchanged: `MERGE_INSTRUCTING_BRIEFS`, `MERGE_INSTRUCTING_DOCS`, never widened to a directory sweep) now also requires every merge-instructing channel to match a new `BASE_MERGE_CAVEAT` pattern. Anchored on the single token `base-merge` rather than a full sentence, deliberately: a phrase-length match reddens on ordinary rewording and invites weakening the assertion out of spite, while a single distinctive token survives a rewrite and only fails on an actual deletion. **This caveat is provisional, not a permanent property of the system, and the guard says so at the assertion site:** BUTCHR-52 is filing the actual remedy for the base-merge hole; if that lands, `reviews[].commit.oid` re-pointing stops being true, this assertion is expected to go red, and that red means "update or remove this text," not "the test broke." Mutation-tested in both directions and confirmed live: deleting the caveat from `briefs/task.md`, `briefs/story.md`, `docs/agent-model.md`, or the nudge each independently turns the new assertion red; the pre-existing forbidden `reviewDecision,headRefOid` sweep still reddens on reintroduction; deleting `reviews[].commit.oid` from a merge-instructing channel still reddens the pre-existing field-name assertion; an unrelated new file under `docs/` stays green throughout.
