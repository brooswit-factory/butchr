### Fixed
- **A `singleton`/`persistent` rule's boss was never woken by its implementer, on ANY daemon — the cross-daemon fix in BUTCHR-388 (PR #372) silently stopped working the moment BUTCHR-397/398 gave that boss's own rule an `execution` mode other than `swarm`.** Regression test (`test/unit/rule-engine.test.ts`, "BUTCHR-406: cross-daemon boss wake regression"): two disjoint daemon views over one linked pair of tickets, run through the real `discovery.related()` and `runResourceLoop` change detection — passed for `swarm`/undeclared, failed for `singleton`/`persistent` on unmodified `main`.
- **Cause: `relatedForRules` (`src/rules/resource-type.ts`) gated a listener's own edge on `activeSet.has(listener.agentKey)`, using the bare PER-RESOURCE agent key every `RuleMatch` carries regardless of its rule's `execution` — but for a `singleton`/`persistent` rule, the id `runResourceLoop`'s `active` set actually contains is the QUERY-level key (`encodeQueryAgentKey`), never the per-resource one.** So a singleton/persistent boss's own key was never `active`, the check always failed, and both the `Implements` (up) and `Relates` (inward) edges were silently dropped before `notify` ever saw them — no crash, no log line, just a boss that never hears.
- **Fix: a listener is active when EITHER its per-resource key OR its rule's query-level key is in `active`, and the watcher recorded is whichever key is ACTUALLY running** (the query key for `singleton`/`persistent`, the per-resource key for `swarm` — identical to before for `swarm`, so that path is byte-for-byte unchanged). Local to `relatedForRules`'s `implementsEdge`/`relatesEdge`/`record`; no change to staffing, execution-unit grouping, or `scopeRelated`/`scopeRelatedResources`.
- Not part of this fix: the `staffed:false` observer-rule mechanism (BUTCHR-404/BUTCHR-402), which stays parked (`origin/BUTCHR-402-observer-parked`) pending a separate decision — this PR's regression test deliberately involves no observer rule.
