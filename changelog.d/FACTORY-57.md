### Added
- **New `github-pr` resource provider and rule type: one agent per matching GitHub pull request (FACTORY-57, implementing FACTORY-56, epic FACTORY-55).** A rule naming `resourceProvider: "github-pr"` discovers PRs with a GitHub pull-request search query (`is:pr` is applied automatically; a query shaped to ask for plain issues is rejected at rule-load time — the mirror of `github-issue`'s own `is:issue` restriction), staffed one agent per matched PR in `<workspace root>/github-pr/<rule>/<owner%2Frepo%23n>`, with new `github_get_pr`/`github_pr_add_comment` MCP tools acting only on the caller's own PR (`src/resources/github-pr.ts`, `src/rules/github-pr-type.ts`, `src/daemon/github-pr-loop.ts`, `src/tools/github-pr.ts`). A PR's agent is stopped exactly the way a closed issue's already is — no special-cased merge/close code — purely because the rule's own query (e.g. one including `is:open`) stops matching the PR once GitHub reports it merged or closed.
- **`github-pr` is a first-class `ResourceRef` kind** (`src/resources/github-pr-ref.ts`, `resource-ref.ts`'s union/parse/format), so a PR can be a managed link and a linked-eventing target the same way a GitHub issue already is. It shares GitHub's own owner/repo#number identity shape with `github-issue` (GitHub issue and PR numbers share one counter per repo) but the two never collide: the canonical `github-issue:`/`github-pr:` provider prefix carries the whole distinction, and `pollGithubLink` (`src/jira-watch/external-poll.ts`) already accepted a `"github-pr"` kind since BUTCHR-436/437's own linked-eventing work — only `src/resources/link-reconcile.ts`'s managed-link mapping needed a new case, no poller change.
- **Both `github-issue` and `github-pr` share the SAME `GITHUB_TOKEN_FILE`/`BUTCHR_GITHUB_ORGS` config — no second token or env var was added.** Finding (documented in `.env.example`): a classic PAT's `repo`/`public_repo` scope already covers both providers fully; a fine-grained PAT needs BOTH "Issues" and "Pull requests" repository permissions (Read and write) — reading/searching PR metadata is gated by "Pull requests", but posting or reading either provider's comments goes through the shared `/issues/<n>/comments` REST endpoint, which is gated by "Issues" regardless of whether the number is a plain issue or a PR.
- Docs updated to match: `docs/provider-capabilities.md`'s inventory (now 9×6), `docs/resource-links.md`'s `ResourceRef` kind table and managed-link mapping table, and `README.md`'s provider-rules section.

No behavior change for any rules file without a `github-pr` rule: existing `github-issue`, `jira-work`, `filesystem` (etc.) rules load and behave identically (`test/unit/rules-mixed-providers.test.ts` pins this against a representative mixed-provider fixture), and every pre-existing test assertion in `test/` is unchanged.
