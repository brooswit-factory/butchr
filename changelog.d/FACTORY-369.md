### Added

- **A managed session's unanswerable dialog is no longer silently dropped (FACTORY-369/FACTORY-358/FACTORY-367).** A managed session (director/manager/admin/advisor — filesystem-managed, not backed by a Jira ticket) resolves to `issue === null` at both `escalation-loop.ts` escalation entry points (`onBlocked`'s reported dialog, and `onNoPrompt`'s sustained unparseable pane, on its existing sustained-observation gate). `issue === null` still means "never hand a bogus key to Jira's `addComment`" — that stays unchanged — but it now routes to a new `#team-admin` Rocket.Chat post instead of dead-ending. The post is made by the daemon process itself: no spawned or resumed Claude session, no Jira comment as the delivery mechanism, so it can still reach a human on a host where every Claude session (including the mentioned `@admin-assembly`/`@director`) is down for the same credential failure that blocked the session in the first place. The text stands alone for a human — session name, pane id, question, options, fingerprint and capture path, each a labeled line — and mentions `@admin-assembly` normally, `@director` for the admin-assembly self-reference case.
- One post per new (pane, fingerprint) episode, plus a short follow-up once a notified episode's dialog clears; a per-pane hourly rate cap backstops the dedupe against a fingerprint that drifts poll-to-poll (a known, separate defect — FACTORY-378 — in the underlying dialog-text extraction) so a flapping/drifting pane is bounded rather than unbounded.
- New `Config.managedEscalationRocketChat` (env: `BUTCHR_TEAM_ADMIN_ROCKETCHAT_URL`/`_USER_ID`/`_TOKEN_FILE`, optional `BUTCHR_TEAM_ADMIN_ROOM`, default room `team-admin`) — a credential and Nexus grant deliberately separate from the existing account-management-only `rocketchat` config. Not configured: the daemon starts normally and every would-be escalation still emits a loud, complete `[managed-escalation]` journal line carrying the same payload the post would have carried — never a crash, never a silent drop. A transport failure (RC down, a refusal, anything) is logged and never latches the episode as handled, so a transient failure delays rather than loses the escalation, and never crashes the daemon or wedges the escalation loop.
- `src/resources/rocketchat.ts` gains `createRocketChatPoster`/`RocketChatPoster` — a narrow "post this text to this room" interface built on the same request plumbing as the existing account-management `RocketChatClient`, but from its own separate credential, and injected into `escalation-loop.ts` as `EscalatorDeps.teamAdminNotify` rather than a bare `fetch` inlined into escalation logic.
- `jira-work` resource agents' escalation behaviour is unchanged; existing escalation tests pass untouched.
