### Fixed
- **The project wake watermark can no longer be moved backward, and a failed watermark write no longer leaves a project waking on its own already-posted write (BUTCHR-214/226, defects 1 and 1b).** `advanceProjectWatermark` (`src/resources/project.ts`) used to blindly overwrite the stored `version`/`comment` watermark with whatever a caller passed. Confluence footer-comment ids are not monotonic with creation time (already measured in BUTCHR-198/202), so a suppression write (`speakOnOwnChannel`, e.g. a daemon complaint posted to wake a resource) could draw an id *below* the current watermark and regress it — the project then read `"active"` on a stale comment it had already handled, not on the write that actually caused it, and kept doing so until the next `check_in`. The write is now monotonic under today's max-numeric-id order (never lower than the stored value); BUTCHR-195/199 own updating this expression if their migration changes what "newest" means for this field. Independently, the watermark write is deliberately fail-open (a bookkeeping failure must never fail `report_to_boss`/`ask_boss`, BUTCHR-105) — a *persistent* rejection (measured live: a 403 from missing project-write permission) left the watermark permanently behind the page's true max, the identical "wakes on its own write" symptom by staleness instead of regression. A rejected write is now also held in this process's own in-memory fallback (never persisted, resets on restart) and merged into both the next read and the next write attempt, so a later successful write — from any caller — absorbs what an earlier one could not durably record.
- **A project's own `set_doc` call no longer wakes it (BUTCHR-214/226, defect 2).** The wake predicate compares three axes — page version, newest comment id, and per-epic comment ids — but only the comment axis had a self-wake suppression. Every root-doc body edit bumps Confluence's own page version, and nothing but the project agent's own `check_in` ever advanced the stored version watermark to match, so a project that keeps its doc current (every agent's explicit instruction) woke itself deterministically, every single time. `setProjectDoc` now advances the project's version watermark to the version its own `ops.updatePage` call produced (identity-of-write, not a read-back — a read-back could pick up a foreign edit landing in the gap and wrongly suppress a genuine wake). A foreign edit — any `updatePage` call this function didn't make — still wakes the project exactly as before; this is a stated non-negotiable and is covered by tests that fail if the suppression widens.
- **A deleted top comment no longer produces a permanent spawn loop `check_in` can never clear.** The monotonic guard above initially applied to every write, including `check_in`'s — but `check_in` computes the max over EVERYTHING it currently observes, which can legitimately be LOWER than the stored watermark when the previously-newest comment is deleted, and `projectVerdict` compares by exact inequality, so a watermark strictly *above* the observation is exactly as unequal (and wakes the project) as one below. A guard that only ever raises the ceiling therefore turned a deletion into a spawn loop `check_in` could never clear, since ids are drawn non-monotonically from a wide range with no guarantee a higher one ever arrives again. Fixed by distinguishing the two write shapes explicitly, at the call site (`patch.reconcile`, set only by `check_in`): a **suppression** write (`speakOnOwnChannel`, the version-axis equivalent) is a partial fact and never lowers; a **reconciling** write (`check_in` only) is a complete observation and may set the watermark authoritatively, including downward — restoring the recovery `check_in` always had, while keeping the new guard on the writer that actually caused the regression defect above. **This is not a theoretical nicety:** root-doc comment deletion is expected traffic on this exact surface — BUTCHR-183/185's shipped peer-messaging harness has already deleted a stray comment it posted onto a peer project's root doc as cleanup, and such cleanups concentrate on recent (plausibly high-id) comments, the worst possible distribution for a high-water mark. `check_in` must stay authoritative downward because the page genuinely loses its top comment in normal operation, not only in a contrived scenario.
- **Known, stated cost of the monotonic guard (now narrower than first shipped):** a *suppression* write's own contribution to the max-id ceiling is strictly non-decreasing — it can no longer regress, but it also can never lower again once raised by one. Since Confluence comment ids are drawn from a wide, non-monotonic range, a max-id watermark was already under-delivering before this fix (BUTCHR-195 measured only 6 of 17 real comments on one root doc would ever have been "seen" under this scheme); this guard makes a suppression write's ceiling ratchet strictly upward rather than occasionally, accidentally, dropping back down, while `check_in`'s own reconciling write retains full authority to correct it (including downward) whenever it actually runs. Trading a spurious self-wake loop for a slightly higher ceiling between check-ins is the right trade, but the accumulated deafness underneath it between check-ins is real and is BUTCHR-195/199's to clear, not fixed here.
