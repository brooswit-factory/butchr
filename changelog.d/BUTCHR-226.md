bump: patch

### Fixed
- **The project wake watermark's version axis can no longer be moved backward, and a failed watermark write no longer leaves a project waking on its own already-posted write (BUTCHR-214/226/260, defects 1b and the version half of defect 1).** `advanceProjectWatermark` (`src/resources/project.ts`) used to accept whatever `version` a caller passed with no floor at all. It is now monotonic (never lower than the stored value) — a real Confluence page version never legitimately decreases, so this floor has no exception. (BUTCHR-227 landed on `main` while this was in review and independently replaced the *comment*-axis scalar with a seen SET, compared by membership rather than magnitude — BUTCHR-260 reconciled the two: the comment axis needs no monotonic guard of its own, since a set can only grow. See that ticket's changelog entry for the comment-axis fix itself.) Independently, the watermark write is deliberately fail-open (a bookkeeping failure must never fail `report_to_boss`/`ask_boss`, BUTCHR-105) — a *persistent* rejection (measured live: a 403 from missing project-write permission) left the watermark permanently behind the page's true state, the identical "wakes on its own write" symptom by staleness instead of regression. A rejected write is now also held in this process's own in-memory fallback (never persisted, resets on restart) and merged into both the next read and the next write attempt, so a later successful write — from any caller — absorbs what an earlier one could not durably record.
- **A project's own `set_doc` call no longer wakes it (BUTCHR-214/226, defect 2).** The wake predicate compares three axes — page version, seen comment ids, and per-epic seen comment ids — but only the comment axis had a self-wake suppression. Every root-doc body edit bumps Confluence's own page version, and nothing but the project agent's own `check_in` ever advanced the stored version watermark to match, so a project that keeps its doc current (every agent's explicit instruction) woke itself deterministically, every single time. `setProjectDoc` now advances the project's version watermark to the version its own `ops.updatePage` call produced (identity-of-write, not a read-back — a read-back could pick up a foreign edit landing in the gap and wrongly suppress a genuine wake). A foreign edit — any `updatePage` call this function didn't make — still wakes the project exactly as before; this is a stated non-negotiable and is covered by tests that fail if the suppression widens.
- **The version axis is also the operator's own emergency wake channel, and identity-of-write protects it against a subtle race.** Because the comment axis can silently fail to notice a real comment, an operator can force a wake by bumping the root doc's page version directly — used in anger on a real incident. `setProjectDoc` uses the version *its own write produced* (from `ops.updatePage`'s return value), never a value read back afterward — if it did read back, a foreign version bump racing into the gap between the write and that separate read would be watermarked as if it were the agent's own, silently swallowing exactly that emergency channel. **A known, stated limit, not fixed here:** a foreign version bump followed by the project's own `set_doc` call *before the next poll observes the foreign bump* still gets coalesced into the agent's own write and loses its wake — inherent to a single scalar watermark comparing only "have I acted through this version," not "was every intermediate version seen."
- **(BUTCHR-260) Superseded, and removed rather than adapted:** an earlier round of this fix also put a monotonic guard *and* an explicit `patch.reconcile` escape hatch (letting `check_in` alone lower the watermark, e.g. to recover from a deleted top comment) on the comment axis. BUTCHR-227's seen-set makes that machinery moot — nothing is ever evicted from a seen set, so there is no "ceiling" left for a deletion to invalidate and nothing for a reconcile bypass to protect. Verified, not assumed, before removing it: an audit of every remaining wake-path caller found no place left that derives a "newest" or a bound from the seen set. Deleted along with it: `monotonicMaxId`, the `reconcile` flag/parameter, and the characterization tests that exercised deletion recovery under the old scalar.
- **The monotonic floor above is scoped to the version axis only, and carries no accumulated deafness.** Confluence page versions are genuinely monotonic by construction, so the floor never discards a legitimate observation. This is a different claim from the *comment*-axis deafness BUTCHR-195 measured (cited here third-hand, via two relays, not re-measured by this change): only 6 of 17 real comments on one root doc would ever have been seen under a max-id watermark. That deafness belonged to the max-id scalar the comment axis used to have — BUTCHR-227's seen-set removed that scalar — and is not this change's to own. This change does not add to that deafness; it also does not fix it.
- **Why the defect-1b fallback takes this shape rather than another, so a later fix doesn't have to re-derive it (BUTCHR-292, a shelved third self-wake axis gated on this increment, is told to read this entry and stay consistent with it rather than invent a second approach to the same failure).** Not "make the write fatal" — refused, since the write's `.catch` exists so a bookkeeping failure never fails the caller's `report_to_boss`/`ask_boss`/`set_doc` (BUTCHR-105); that constraint is what the whole shape is built around, and it's the first thing a fresh reader will try to "fix". Not a bare retry — considered and rejected: it fixes only a transient failure, and the measured incident (a persistent 403 from missing project-write permission) is not transient, so retry alone would leave it unfixed. Not a durable, persisted pending record — considered and rejected: it would change what the `wake` property stores or add a second write surface, which needs sign-off from BUTCHR-195/199 (who own that field's meaning), and is unnecessary here since this fallback changes nothing about what is persisted, only what this process additionally consults in memory before its next read or write. The cost accepted, stated rather than hidden: it is **restart-losing** — the fallback lives only in this process's memory, so a daemon restart drops a pending, unwritten watermark, and a persistent-failure incident that outlives a restart before its write succeeds resumes waking the project until it does.
