### Added
- **`set_doc`/`set_project_doc` now refuse a write that is both over a 50,000-character budget AND larger than what is currently stored (BUTCHR-250).** Guards the only place a doc's size can grow, on both write-path callers (a ticket's own doc and a project's root doc), so a monotonically-growing shared page like a project root doc can no longer silently outgrow the MCP result cap `docs/tool-result-size-cap.md` measured. The refusal names the current stored size, the proposed size, the budget, and the remedy (a linked child page under the root doc's index). Deliberately **not** a plain ceiling: a page already over budget can still be corrected, compacted, or shrunk — an estimated-post-storage `proposed` no larger than `stored` is always allowed regardless of budget — so an oversized page is never bricked, only prevented from growing further. Both comparisons run against `estimateStoredLength(proposed)`, not a bare `proposed.length`: Confluence's storage layer re-encodes some characters (a literal em dash, curly quotes, at least one Greek letter observed live) into longer named XML entities, and comparing raw lengths against an already-post-transform `stored` was measurably unsound in the permissive direction — a write that swapped stored entities for their shorter literal form could score as a shrink while the stored page did not shrink at all. Verified not to be BUTCHR-specific: the guard is a pure size predicate taking no project key, and `test/unit/docs.test.ts` exercises it against non-BUTCHR project keys, plus a regression arm using real non-ASCII characters that fails against the pre-fix raw comparison. See `docs/root-doc-write-budget.md` for the budget's derivation method, the read/write-path argument, the per-ticket-vs-root-doc scope decision, the entity-encoding finding, and a blast-radius table measured across every project this bound protects.
