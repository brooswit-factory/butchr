### Added
- **A `project` resource type (`src/resources/project.ts`), the second instance of `ResourceType<T>` (BUTCHR-64) after the issue tier — discovery, activation, three wake-trigger event rules, and spawn config, with zero edits to `src/daemon/loop.ts` or the `ResourceType`/`Discovery`/`EventRules`/`SpawnConfig` interfaces.** Discovery reads `GET /rest/api/3/project/search?status=live`, then filters `lead.accountId` CLIENT SIDE against this credential's own `GET /rest/api/3/myself` — MEASURED live: the server-side `leadAccountId` query param is silently ignored (a bogus id returns every live project unfiltered), so client-side filtering is the only filter that actually filters. A project is ELIGIBLE — not resident — only when it is also led by this credential AND carries a readable `butchr` entity property naming a root doc; MEASURED live, independently on two credentials: the archive project and one sample project both 404 on that property while every product project and ASSIST return it populated, and `archiveProject` on that property is a POINTER (every readable property names the same archive project) rather than a per-project flag, so no project key or archived-ness check is ever hardcoded.
- **Activation is written against `Activation<T>.verdictFor(): "active" | "asleep" | "inactive"` (BUTCHR-66's widened seam, landing alongside this PR), a PURE, synchronous comparison of fields discovery already gathered against durable per-project watermarks** (root-doc version, newest footer-comment id, per-in-review-epic newest-comment id) stored in the existing `butchr` project entity property's new `wake` sub-key — chosen over a doc-body marker (silently lost on the next full-body `set_doc` replace) or a second Confluence property (a second read surface) or extending the Jira-keyed own-write ledger (MEASURED unusable for a project key: `search("key IN (...)")` silently returns empty for a bare project key). `eventRules.poll` reuses the exact same watermark comparison for the "already-awake agent, tell it something changed" nudge path, plus a prev/next structural diff so an unchanged poll produces zero notify-stage work.
- **Two hazards this story owned, both closed: (1) a project's own `report_to_boss`/`ask_boss` no longer wakes itself in a loop** — `speakOnOwnChannel` (`src/tools/speak.ts`) now advances that project's `wake.comment` watermark to the id its own `commentOnPage` call just created, synchronously with the write; a foreign comment never goes through this function, so it is never watermarked and still wakes the project. **(2) a blocked project agent's daemon-side escalation no longer dies silently in a log** — `src/daemon/index.ts`'s escalator now posts through `speakOnOwnChannel` instead of `ops.addComment` directly, so a resolved PROJECT id (previously a guaranteed-404 `ops.addComment` call, since a project key is not addressable as a Jira issue) lands as a comment on the project's own root doc instead; an issue id's behavior is byte-identical to before.
- Three additions to the `AtlassianOps` surface (`src/tools/atlassian.ts`/`atlassian-real.ts`), each because neither existing Atlassian client had the capability, per the same pattern that added `commentOnPage`/`getPageComments`: `searchProjects` (always requests `expand: "lead"` — MEASURED live: omitted, `lead` comes back `null` on every project), `getMyself`, `setProjectProperty` (MEASURED live: writable even on a project this credential does not lead — gated on Administer Jira/Projects, not leadership), and `getPageVersions` (a real batching win — MEASURED live: N root-doc versions in one call — used for the rule-1 poll; footer comments are deliberately NOT batched, since a batch-shaped `footer-comments?id=` call was MEASURED to return a plausible, silently WRONG count).
- `PROJECT_POLL_INTERVAL_MS` (5 minutes): the interval this story chose and states, per the call-count budget in its own doc comment (`src/resources/project.ts`) — a resource whose activation may legitimately answer `asleep` is, by definition, one where minutes of latency are acceptable.

### Changed
- None to the ISSUE tier: `ISSUE_ACTIVATION`, `src/resources/issue.ts`, and `src/daemon/loop.ts` are untouched by this PR — confirmed by the full existing test suite passing unmodified. The `Activation<T>` interface widening itself (`isActive` -> `verdictFor`) is BUTCHR-66's edit, landing as its own PR; this story's PR contains no loop or interface edit.

### Note
- **A stated, deliberate gap, not a silent one:** this story advances the COMMENT watermark (the one write call site — `speakOnOwnChannel` — squarely in its own scope). The VERSION and per-epic watermarks have no write call site inside this story: advancing them requires the project agent to check in as its last act before exiting, which is BUTCHR-66's wake-mechanism "exit" step or the project tool surface (BUTCHR-65) to wire, not this story's project-resource-type module. `advanceProjectWatermark` (`src/resources/project.ts`) is exported and tested, ready for that hook to call.
