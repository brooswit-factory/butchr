### Added
- **A `project` resource type (`src/resources/project.ts`), the second instance of `ResourceType<T>` (BUTCHR-64) after the issue tier — discovery, activation, three wake-trigger event rules, and spawn config, with zero edits to `src/daemon/loop.ts` or the `ResourceType`/`Discovery`/`EventRules`/`SpawnConfig` interfaces.** Discovery reads `GET /rest/api/3/project/search?status=live`, then filters `lead.accountId` CLIENT SIDE against this credential's own `GET /rest/api/3/myself` — MEASURED live: the server-side `leadAccountId` query param is silently ignored (a bogus id returns every live project unfiltered), so client-side filtering is the only filter that actually filters. A project is ELIGIBLE — not resident — only when it is also led by this credential AND carries a readable `butchr` entity property naming a root doc; MEASURED live, independently on two credentials: the archive project and one sample project both 404 on that property while every product project and ASSIST return it populated, and `archiveProject` on that property is a POINTER (every readable property names the same archive project) rather than a per-project flag, so no project key or archived-ness check is ever hardcoded.
- **Activation is written against `Activation<T>.verdictFor(): "active" | "asleep" | "inactive"` (BUTCHR-66's widened seam), a PURE, synchronous comparison of fields discovery already gathered against durable per-project watermarks** (root-doc version, newest footer-comment id, per-in-review-epic newest comment id) stored in the existing `butchr` project entity property's new `wake` sub-key — chosen over a doc-body marker (silently lost on the next full-body `set_doc` replace), a second Confluence property (a second read surface), or extending the Jira-keyed own-write ledger (MEASURED unusable for a project key: `search("key IN (...)")` silently returns empty for a bare project key). `eventRules.poll` reuses the exact same watermark comparison for the "already-awake agent, tell it something changed" nudge path, plus a prev/next structural diff so an unchanged poll produces zero notify-stage work.
- **A new `check_in` tool verb (`src/tools/defs.ts`), project-caller only: the project agent's own last act before exiting, closing the loop the watermark design depends on.** Re-reads the project's current root-doc version, newest footer comment, and every currently-in-review epic's newest comment id directly from Jira/Confluence (never trusts a caller-supplied value), then advances `wake` accordingly. The per-epic `epics` write is a REPLACE of the whole map, not a merge — deliberately, since that replace is what prunes an epic that has left review, making its next re-entry detectable again by absence (see the next bullet).
- **Two hazards this story owned, both closed: (1) a project's own `report_to_boss`/`ask_boss` no longer wakes itself in a loop** — `speakOnOwnChannel` (`src/tools/speak.ts`) now advances that project's `wake.comment` watermark to the id its own `commentOnPage` call just created, synchronously with the write; a foreign comment never goes through this function, so it is never watermarked and still wakes the project. **(2) a blocked project agent's daemon-side escalation no longer dies silently in a log** — `src/daemon/index.ts`'s escalator now posts through `speakOnOwnChannel` instead of `ops.addComment` directly, so a resolved PROJECT id (previously a guaranteed-404 `ops.addComment` call, since a project key is not addressable as a Jira issue) lands as a comment on the project's own root doc instead; an issue id's behavior is byte-identical to before.
- Five additions to the `AtlassianOps` surface (`src/tools/atlassian.ts`/`atlassian-real.ts`), each because neither existing Atlassian client had the capability, per the same pattern that added `commentOnPage`/`getPageComments`: `searchProjects` (always requests `expand: "lead"` — MEASURED live: omitted, the `lead` key is ABSENT from every project entirely, not merely `null` — see the "two review-found defects" note below for why that distinction matters), `getMyself`, `getProjectPropertyOrNull` (a 404-to-null read, mirroring `getRemoteLink`'s existing convention, leaving `getProjectProperty`'s throw-always contract untouched for `docs.ts`), `setProjectProperty` (MEASURED live: writable even on a project this credential does not lead — gated on Administer Jira/Projects, not leadership; read-modify-write, NOT atomic — stated risk, accepted, see the op's own doc comment), `getPageVersions` (a real batching win — MEASURED live: N root-doc versions in one call — used for the rule-1 poll; footer comments are deliberately NOT batched, since a batch-shaped `footer-comments?id=` call was MEASURED to return a plausible, silently WRONG count), and `getIssueComments` (newest-first, capped at 20 — the SAME endpoint/ordering/cap as `src/atlassian/client.ts`'s existing `comments()`, used by BOTH discovery and `check_in` for an epic's newest comment id, so the two can never disagree — see the third review-found defect below).
- `PROJECT_POLL_INTERVAL_MS` (5 minutes): the interval this story chose and states, per the call-count budget in its own doc comment (`src/resources/project.ts`) — a resource whose activation may legitimately answer `asleep` is, by definition, one where minutes of latency are acceptable.
- **BUTCHR-82: `test/unit/project-caller-disposition.test.ts` — an ENFORCED guard, run at `bun run check` time, closing the gap the story's own "27 registry keys, zero gaps" completeness check left open: nothing failed when a new verb landed with no project-caller decision recorded anywhere. It did — `correct_worker` (BUTCHR-41/BUTCHR-60) shipped mid-story with the decision made in code but never declared anywhere a guard could see.** The guard is a hand-authored `DISPOSITIONS` map, diffed BOTH directions against the tool registry read dynamically (`Object.keys(atlassianTools(...))`, never a hardcoded count), one of four dispositions required per verb: `refuses` (throws for a project caller), `project-only` (throws for an issue caller instead — `check_in`), `permitted` (works for a project caller, with its own description required to say so), `agnostic` (acts on an explicit argument, never the caller's own identity — the jira_*/confluence_* passthroughs). **"Declared" means a line in the map a human wrote, never inferred from whether a verb calls `refuseProjectCaller`/`requireProjectCaller`** — `correct_worker` is deliberately `permitted` and calls neither, so a marker keyed on the gate helper would have misread its own positive control as undecided. The `permitted` bucket also carries a description-marker check (every such verb's own description must mention a project caller) — the mechanism that would have caught `correct_worker`'s now-fixed false claim ("no AGENT can ever correct an epic's description"), since that defect was in the DESCRIPTION while the runtime behaviour was already correct; a guard that only drove behaviour would have missed it. The red-then-green proof of the mechanism uses a throwaway verb name the test constructs and owns, not a live one — a control borrowed from the live registry is one another story can revise out from under it, and it fails in the most seductive direction (green because the world moved, not because the guard works). **Stated limit, not left implicit: this does not prove a `permitted` verb's description is TRUE, only that it is not silent about a project caller** — see the test file's own header comment for the full statement of what it does and does not catch.

### Fixed
- **Two defects found and fixed during review, before merge, both in rule 3 (epic entered/commented-on-while-in-review):** (1) a per-epic watermark that only ever grew (merged, never pruned) could not detect an epic RE-ENTERING review with no new comment (`submit_to_boss` transitions status; it does not necessarily comment) — a stale map entry from the prior review episode compared equal and the project wrongly stayed asleep. (2) The first fix attempted — watermarking the epic's own `updated` field instead of a comment id, since `updated` also moves on a status transition — was itself wrong: this daemon's OWN `agent:*`/`pr:*` label sync bumps `updated` on every label write, and `ISSUE_JQL` has no issuetype filter, so an in-review epic is label-synced identically to any other active ticket (MEASURED live on a real ticket: 8 label changes in 17 minutes, `updated` exactly matching the last one — faster than this story's 5-minute poll interval, so an `updated`-keyed watermark would be behind on EVERY poll for as long as anything sat in review — permanently active, not occasionally noisy). The actual fix: the comment id stays the compared value (immune to label churn — a label write is not a comment), and re-entry is caught by the `check_in` tool REPLACING the whole `epics` map with the currently-in-review set on every check-in, so a departed epic is pruned and re-entry is detected by absence again.
- A bare `catch` around the project entity-property read conflated a genuine 404 (the correct ineligibility signal) with any OTHER failure (rate limit, timeout, permission change) — both resolved to the same "ineligible" outcome, which `projectVerdict` turns into `"inactive"`, which lands in NEITHER `desiredFrom` nor `atRestFrom`'s sets, which the reconciler then STOPS — so one transient read failure on any one of a poll's N property reads could kill a running project agent mid-work. Fixed with the new `getProjectPropertyOrNull` (see above): only a genuine 404 resolves ineligible; any other failure now propagates and fails the whole poll, consistent with every other read in `discovery.search()`, so a flaky poll changes nothing rather than silently reporting a project gone.
- **A third defect, found during review: `check_in`'s epic-comment write and discovery's epic-comment read used two DIFFERENT readers that could disagree.** `check_in` originally read an in-review epic's comments via `getIssue`'s embedded `fields.comment` block — MEASURED live: this block is ASCENDING/oldest-first with an unconfirmed cap, so if ever truncated, `newestCommentId` over it would silently return a stale id, disagreeing with discovery's own reader (newest-first, always correct). Fixed by giving both a single shared reader — the new `getIssueComments` op, above — rather than leaving agreement contingent on a cap nobody has found.
