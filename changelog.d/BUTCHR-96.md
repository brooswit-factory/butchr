### Fixed
- **A project agent's escalation captures could never be evicted, because the eviction regex required an issue-key shape (BUTCHR-96).** `escalation-loop.ts` writes an escalation capture as `` `${issue}-escalation-${timestamp}.txt` ``, but a project caller's resolved id is a bare Jira project key with no `-<digits>` suffix (e.g. `BUTCHR`, not `BUTCHR-68`) — a residual of BUTCHR-67's HAZARD 2 fix, which widened the escalation's comment routing to project callers but not this filename recogniser. `ESCALATION_CAPTURE_NAME` required `-\d+`, so a project-shaped capture was written but never recognised as "ours": it was invisible to the eviction sweep and the 50-file cap never applied to it, so captures accumulated without bound. The regex now admits an optional `-\d+` segment, matching both an issue id and a bare project key, while staying disjoint from session-limit-watch's own capture names (`-unrecognised-` / `-no-reset-time-`) via the literal `-escalation-` segment — asserted by new tests that feed each module's capture-shaped filenames to the other and assert neither evicts the other's files.
