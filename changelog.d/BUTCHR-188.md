### Added
- **New `list_peers` verb: a PROJECT caller can now enumerate the other projects it can reach (BUTCHR-184/BUTCHR-188).** Communication in this factory has so far been vertical only (boss/worker); `list_peers` is the enumeration half of letting two projects talk sideways — the write half (`tell_peer`) is a sibling story. Takes no arguments (same reasoning as `check_in`/`get_doc_comments`: the only estate a project can enumerate is the one it lives in) and returns `{ results: [{ key, name }] }` — the caller's own key is excluded, and no root-doc page id or url is returned (resolve that fresh at send time instead of caching a value that can go stale). Refuses an ISSUE caller: peers are a relationship between projects, and an issue talks only to its boss and its workers. Uses the project tier's existing ELIGIBILITY rule (live, led by this credential, carrying a readable `butchr` entity property naming a root doc) via a newly extracted, single shared resolver (`resolveEligibleProjects`, `src/resources/project.ts`) that `loadProjects` now also consumes — not the staffing allowlist, which is a rollout gate, not an eligibility rule, so an eligible-but-not-yet-staffed project can legitimately appear here.
