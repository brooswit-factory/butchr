### Added
- **A live residency census, independent of `agent.list()`, guards the spawn path against a blind herdr agent list — including at COLD START (BUTCHR-287).** Measured live: a fresh daemon's first poll logged `WARNING: [crashloop] the entire desired set (9/9) is in plan.spawn this poll` and then spawned anyway, attempting six duplicate agents against tickets that were alive and working the whole time — saved only by `agent_pane_busy`, a race BUTCHR-242 exists to close. A steady-state transition guard (prior poll saw residency > 0, this poll reads 0) cannot cover this: the incident *is* the first poll of a fresh process, so there is no prior observation for a transition check to fall from. Closing the cold-start case needs a second, LIVE source of truth about residency — this ticket.
- New `src/agents/residency-census.ts`: the pure parts of the census — `panesFor`/`groupOwnedPanes` (ownership joins on a pane's `cwd`, the SAME `buildWorkspace()` convention the reaper already relies on, never on `agent.list()`) and `aggregateVerdict` (combining each of an issue's panes' own live/dead/unknown verdict into one residency verdict — "resident" the instant any pane is live, "vacant" only if every pane is definitively dead, "unknown" otherwise; a thrown `processInfo` call, a missing `process_info`, or an empty `foreground_processes` are all UNKNOWN, never proof of either state — same discipline `staleIssues()`/`paneVerdict()` already apply).
- `HerdrHerd.residency(candidates)` and `HerdrHerd.residentIssues()` (`src/agents/herd.ts`): the herdr-I/O half, reusing the exact `processInfo`/`isClaude` check `closeStranded()` already trusts as the reaper's decisive safety layer. `residency()` is the candidate-scoped API the guard itself consumes (cost proportional to `plan.spawn`, not the whole fleet); `residentIssues()` is a minimal, whole-herd `Promise<readonly string[]>` sweep exposed as a reusable unit for a future consumer (e.g. BUTCHR-284's admission cap, whose own `residency` dependency is already shaped this way) — built but deliberately NOT wired to anything in this increment; that follow-up is owned elsewhere, triggered by a measurement rather than by this ticket.
- New `src/agents/residency-guard.ts`: `createResidencyGuard()` — the per-poll orchestration. A candidate the census finds `"resident"` is withheld THIS POLL ONLY; `"vacant"` spawns normally; `"unknown"` spawns normally too UNLESS the whole (multi-member) desired set is in `plan.spawn` this poll (the same fleet-wide-blind shape `crash-loop.ts` already computes as `fleetWide`), in which case it's withheld for up to a bounded number of consecutive suspicious polls before decaying to a normal spawn — a persistent census failure must never freeze a ticket forever. A census call that itself rejects fails OPEN (every candidate spawns), so a broken guard can never become a liveness hazard bigger than the duplicate-spawn hazard it exists to close. NEVER shrinks `desired`: a withheld id is offered again next poll exactly like an ordinary not-yet-reached `plan.spawn` entry (the BUTCHR-218 liveness trap this fleet has already paid for once).
- Wired into `reconcileNow` (`src/daemon/loop.ts`) as new optional `ReconcileOptions.checkResidency`, called immediately after `planReconcile` — before `opts.admission` (BUTCHR-284) and `checkCrashLoop`, both of which now read its output instead of raw `plan.spawn`. The reason, not merely the order (written that way because the order may not survive a future refactor where the admission cap consumes this census as its own residency input rather than a preceding filter): a spawn candidate that already has a live agent must be removed from the list before anything downstream rations or counts against that list, because rationing a list that contains phantoms under-delivers real work, and counting a withheld phantom as a genuine attempt manufactures a false `[crashloop]` complaint on a resource that was never in trouble. Threaded through `GenericLoopDeps`/`runResourceLoop` and wired into BOTH the issue and project loops (`src/daemon/index.ts`), each with its own guard instance (its own unknown-streak tracker, same "one instance per loop" discipline `RespawnGuard`/`ReapGuard` already follow).
- **The reaper needs no change — it already has an equivalent, unconditional safety layer.** `strandedCandidates()`'s ownership-vs-`agent.list()` join is exposed to the identical blind read this ticket is about (an empty agent list makes every live, butchr-owned workspace a candidate), and its grace period only delays candidacy, never prevents it — but the decisive layer, `closeStranded()` → `workspaceVerdict()` → `paneVerdict()`, performs the SAME `processInfo`/`isClaude` live-claude check this ticket's own census does, unconditionally, before any actual close: a live claude vetoes regardless of how a workspace became a candidate. The BUTCHR-111 caveat — that the reaper's second safety layer guarded against an "alive but unlisted" state argued reachable but never observed live — is withdrawn: it has now been observed live, at n=6, on a real herd, and the layer held.
- Spawn fan-out concurrency is unchanged (out of scope per the parent epic's ruling on BUTCHR-242's own measurement).
