### Added
- **`correct_worker(key, description?, summary?, why)` — a boss can correct one of its own workers' description and/or summary IN PLACE, archiving the previous text first (BUTCHR-60, per the design decided and reviewed on BUTCHR-41).** Until now no agent in this fleet could edit a ticket's description or summary at all: every correction was a comment posted UNDERNEATH text that stayed wrong (or simply stale) forever. The failure is silent — an agent reads a ticket's description carefully and its comments quickly, which is the normal and correct ratio, so the stale header outlives the correction and an agent builds against it while believing it read the ticket. `correct_worker` fixes this the only way that needs no new reading discipline from anyone: it makes the description/summary actually right, at the source `jira_get_issue` already reads.
- **Two legitimate use cases, one verb, one marker.** `why` is "why the text changed", not only "what was wrong": a boss also reaches for this when it holds a genuinely new fact its worker's ticket predates — a late-arriving requirement added after the child was already filed — which is not an error in the original text, just text that stopped being current. Both land in an archive comment tagged with the exported `CORRECTION_MARKER` (`[correction]`, right after the identity tag) so every change to authored text, and its stated reason, is one grep away across the whole corpus.
- **Archive before overwrite — the ordering is the design, not decoration.** `correct_worker` reads the worker's CURRENT description/summary, posts them as the PREVIOUS VERSION in a `[correction]`-tagged comment, and ONLY THEN performs the edit; if the archive comment fails, it refuses and nothing is touched. If the edit fails after a successful archive, one harmless extra comment sits on the worker and its description/summary are unchanged — safe to retry. This is why no rendered "correction block" was needed: the audit trail lives in the comment stream, which this factory already treats as the event log, and the description holds what is true now. Today the truth sits in a comment under wrong text; after this, the wrong (or superseded) text sits in a comment under the truth.
- **Refuses the caller's own key, before any Jira read** — the same shape `prioritize_worker` already uses for the same class of reason: your own brief is your boss's judgment, never your own, and an agent that could rewrite its own definition of done could launder a failure into a success indistinguishable from one that was always right. Also refuses a key that isn't one of the caller's own workers, refuses when neither `description` nor `summary` is given, and refuses an empty/whitespace `why`.
- **Two limitations, stated rather than discovered.** (1) Ownership at the epic tier is exactly what `assertOwnWorker` checks, not a matter of which tiers happen to exist: a PROJECT caller may correct a target that is a member of its own project AND an Epic, so a project agent CAN correct one of its own epics' descriptions with this verb — the caller's own key stays refused at every tier regardless, nobody corrects themselves. Where `assertOwnWorker` accepts no caller for a given ticket, the recourse is a person editing it directly in the Jira UI, which is the intended path here, not a workaround. (2) A `description` is read live, so a correction reaches every future reader immediately, including a fresh spawn — but a `summary` is SNAPSHOTTED into a workspace's `brief.md`/`CLAUDE.md` at build time, so correcting it updates Jira, the board and every future read, but will NOT rewrite the `brief.md` already on disk for an agent currently running on that worker; the tool's own description carries this caveat (not only its result), since a caller decides whether to reach for the verb before any result exists.
- The wake path is entirely inherited, not built: the edit bumps Jira's `updated`, the daemon's existing poll diff nudges on it, and the existing own-write ledger suppresses the ping for the correcting boss while still delivering "your ticket was updated — re-read it" to the worker. Covered by tests rather than re-implemented.
- Documented in `briefs/story.md` and `briefs/epic.md` next to `prioritize_worker`/`shelve_worker`, checked by the existing brief↔tool-surface drift guard.
