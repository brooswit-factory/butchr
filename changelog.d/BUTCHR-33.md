### Added
- **Two new MCP tools, `get_doc` and `set_doc`, give every ticket a Confluence doc that's findable in both directions (BUTCHR-33, the substrate for BUTCHR-27/BUTCHR-25).** Ticket -> doc is a Jira remote issue link (`globalId: "butchr:doc"`, upserted idempotently, so it renders in the Jira issue's own web-links section for a human to click through). Doc -> ticket is a Confluence label (`butchr-ticket-<key lowercased>`) — a real schema field, not a title convention or a line of prose. `get_doc(key?)` is a pure read (the caller's own doc by default, any ticket's on request) and creates nothing, ever, on a hit or a miss — a ticket with no doc resolves to `{ found: false }`, never an error and never a lazily-manufactured page. `set_doc(body, title?)` — no key parameter at all, so overwriting another ticket's doc isn't expressible — is a full-body replace that ensures the caller's own doc exists first, creating it lazily and nesting it under the boss's doc (resolved through the Implements link, recursively, bottoming out at the project's root doc from a `butchr` Jira project entity property). A freshly created doc gets a deterministic, obviously-provisional title (`[unwritten] <KEY> — <summary>`); `set_doc` refuses to omit `title` while that marker is still present, so an agent can't write real content and leave the page reading as unwritten.
- This makes doc creation under `set_doc` **convergent** under retry, not atomic — true atomicity (ticket + doc + both links, or nothing) is a separate, still-open problem for the ticket-creation story. What ensureDoc's ordering guarantees: every partial failure leaves a state a retry recovers from without ever producing a duplicate page, because the child-listing step that recovers a partially-written doc is an exhaustive, cursor-paginated DIRECT read (never a CQL label search — Confluence's CQL index lags a fresh label/page by enough to make a naive retry create a permanent duplicate, and rule (d) never lets normal operation delete one). A second, defense-in-depth guard against two callers racing to create the same doc concurrently rides on Confluence's own unique-title enforcement, since the provisional title is deterministic from the issue key: the loser's create gets a 400 instead of a duplicate page, and retries the scan once to adopt the winner's page.
- New `AtlassianOps` ops backing this: project entity property reads, remote-link read/upsert, exhaustive child-page listing, page-label reads, and an atomic create-page-with-label op. The last one is a genuinely separate op from the existing `createPage` (and its `confluence_create_page` tool) — the atomic label-at-create call needs Confluence's legacy v1 content API, whose response shape differs from the v2 shape `createPage`/`confluence_get_page` return, so no existing caller's behavior changes at all.
