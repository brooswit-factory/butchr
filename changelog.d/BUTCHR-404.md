### Added
- **Observer rules: `staffed: false` (BUTCHR-404).** A rule engine daemon's `discovery.search()` used to serve two masters from one array: the desired agent set it staffs, and the `latest` cache its relationship walk (`relatedForRules`) reads to decide whether ticket R's boss hears ticket C's change — an edge needed BOTH ends in that same array. A ticket staffed by a DIFFERENT daemon was therefore never visible to this daemon's relationship walk either, so `report_to_boss` etc. posted correctly on the child but the cross-daemon boss never woke. `staffed?: boolean` (default `true`) on `Rule` (`src/rules/rules.ts`) lets a rule be searched every poll for relationship purposes WITHOUT ever being staffed: `createRuleResourceType`'s `discovery.search()` (`src/rules/resource-type.ts`) now keeps the FULL match list (including `staffed: false` matches) in its own `latest` cache for `related()` to read, but filters those matches out of what `search()` RETURNS — the one choke point every Jira-writing or agent-spawning consumer downstream reads (staffing/spawn via `desiredFrom`/`atRestFrom`, label sync, and the parked/abandoned detectors). `relatedForRules` itself needed no change: it only ever needed the match present in `latest`.
- Config validation REJECTS a `staffed: false` rule that also declares `brief` or `agentPreferences` — both are meaningless without an agent, and allowing them would let a typo silently half-staff a rule. Rejected at validation time, not merely ignored at runtime.

### Known gaps
- **This ships the mechanism only.** No live rules file gains an observer rule as part of this PR — wiring one into a daemon's actual `rules.json` (naming the other daemon's ticket by JQL, e.g. via a `childRule`/`inwardConnectionRules` target) is a separate, config-only follow-up. Merging this PR does not by itself make BUTCHR-392 hear BUTCHR-398.
- Full end-to-end reliability of the upward-report path also needs BUTCHR-376 (a same-daemon foreign-comment/cursor-suppression bug) — orthogonal, not touched here.
