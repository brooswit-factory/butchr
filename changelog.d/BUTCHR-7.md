### Added
- **Per-PR changelog fragments (`changelog.d/<TICKET>.md`) replace branch-time version bumps — the version is now assigned at MERGE, not at branch cut (BUTCHR-2/BUTCHR-7).** Every branch that touched `src/`, `schema/`, or `package.json` used to have to write `package.json`'s version and a dated CHANGELOG heading, guessed from whatever `main` read when the branch was cut. With several PRs open at once — this fleet's normal state — that guess collided: two branches claiming the same version, the loser paying for a rebase, a version edit, a CHANGELOG re-head, a full re-run of `bun run check`, and in the worst case a formal approval stranded on a sha that could no longer merge, for zero source changes. Fragments make that collision structurally impossible: two concurrent PRs each add their own uniquely-named file, so there is no shared line to conflict on. `scripts/release/gate.ts` (PR-time, `ci.yml`'s `release-gate` job) now requires exactly one new `changelog.d/*.md` fragment per gated PR, and rejects a branch that bumps `package.json` or adds a dated CHANGELOG heading itself. `scripts/release/collate.ts` (merge-time, `release.yml`) collates every fragment present on `main`, computes the next version from the HIGHEST declared bump level among them, writes `package.json` + a collated dated CHANGELOG entry, deletes the consumed fragments, and commits+pushes that to `main` before publishing.
- **`release.yml` gained a `concurrency: { group: release-main, cancel-in-progress: false }` group and a fetch/reset-to-`origin/main` step immediately before reading `package.json`/collating fragments**, so two merges landing seconds apart serialize (the second run's job does not even start — checkout included — until the first's finishes) rather than racing to compute or publish the same version twice. `cancel-in-progress: false` is deliberate: `true` would cancel the second merge's release run outright, silently stranding its fragment unreleased — worse than a queued wait. See the PR description for the full interleaving.

### Changed
- **`main` keeps carrying the real, published version — no dev placeholder.** `main` has no branch protection (`GET /repos/brooswit-factory/butchr/branches/main/protection` → 404 as of 2026-08-30), so a workflow push to `main` is possible; that's what makes writing the real version there at merge time viable instead of falling back to an unreadable placeholder, which would lose the in-repo durable record for no benefit here. This relies on a push made with the default `GITHUB_TOKEN` not re-triggering further workflow runs — otherwise `release.yml`'s own version-bump push would re-trigger itself. That is documented GitHub Actions behavior, not something this PR could execute: no PR in this story pushes to `main` (every task PR in BUTCHR-2 targets the `BUTCHR-2` integration branch), so it stays unexecuted-but-asserted until this story lands on `main` and the workflow actually runs there.
