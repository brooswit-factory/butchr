bump: minor

### Fixed
- **A boss has never heard its implementer: the rule engine's related walk has delivered nothing, ever (BUTCHR-388).** Measured on wroosbit: **198 `[notify]` lines in 24 hours, every one self-addressed** (`X ← X`), zero where recipient ≠ subject — with the raw extraction printed first as a control, because a silently-broken parser and a genuine absence look identical. So `changeNudge`'s `about !== issue` branch (*"X (related to your Y) … re-read it, then act on what changed"*) has apparently never rendered in production, and **every parent/child handoff in this fleet has silently depended on a human noticing**. One traced instance: `SICKOS-78 (Task, booswrit) → SICKOS-73 (Story, wroosbit) → SICKOS-70 (Epic, booswrit)` — PR merged 22:33Z, neither parent ever learned, nothing moved for 18 hours, presenting as three broken agents rather than one missing edge.
- **Cause 1: every `Implements` edge was gated on the listener's rule declaring `relationships.childRule`.** No rules file in this fleet declares one, so no edge was ever built. `src/jira-watch/routes.ts` has always stated the intended rule with no gate — *"a boss hears what implements it"* — and the legacy `createRelated` honoured it *"regardless of assignee"*. The rules engine added the gate on top of a mechanism that never needed it; this removes it.
- **Cause 2, the load-bearing half: the related set was built only from THIS daemon's own matches.** `byIssue` comes from `matches` and an edge needs *both* ends in it, so a boss could never hear an implementer matched by the other daemon's rules. With Epic/Task/Bug on booswrit and Story/Sub-task on wroosbit, **a parent and its child are never on the same daemon** — so cause 2 alone would have left every reported case broken even with cause 1 fixed. `discovery.related` now fetches the `Implements` targets its own search cannot see (`foreignImplementerKeys` + one `key in (...)` search).
- **The root cause was already written down in butchr's own source.** `src/agents/stall-remediation.ts` rejects a herd probe for its `labels` dep because *"a boss's worker is staffed under a DIFFERENT account than the boss … so a probe wired here would be structurally blind to every worker it could ever be asked about."* **The codebase knew about the cross-daemon split and worked around it in the stall path, while the notify path was built as if it did not exist.**

### Changed
- **A guarantee is deliberately withdrawn: every rule matching the boss ticket now hears its implementer, not only the rule that declared `childRule`.** The gate was doing two jobs and only one was costed — *whether* a boss hears (dead in production, as measured) and *which* rule hears when one ticket is matched by several rules (given up on purpose).
  **Why this is `minor` and not `major`, per this repo's own definitions** (`CHANGELOG.md` § Versioning: MAJOR is "a restructuring/rewrite that breaks a lot, requiring reimplementation"; MINOR is "a change to an existing feature that breaks just that feature"): this changes one feature's routing and requires no reimplementation by anyone. **No consumer can be relying on the withdrawn behaviour** — it never fired here (verified against both live rules files: booswrit's rules are `issuetype = Epic|Task|Bug`, wroosbit's two enabled ones are `Story|Sub-task`, and its other two are disabled *and* a different provider, so no ticket matches two rules on either daemon), and it **cannot** be satisfied across daemons by construction, since a rule id is per-file and a ticket matched only by the other daemon has no local rule to name. **The failure mode of the change is an extra wake, not a lost one.**
  **What would make it `major` instead:** a consumer running overlapping rules *and* relying on `childRule` to suppress the other matching rules' agents. If that consumer exists, this breaks it — and the accompanying tests now assert the new behaviour positively so the withdrawal is visible rather than inferred from a diff.
- **The related walk's doc comment carries the withdrawal with a read-before-restoring-it header**, so the next person to see an ungated `Implements` edge does not "fix" it back.

### Added
- `foreignImplementerKeys`, `FOREIGN_RULE_ID` and `FOREIGN_FETCH_LIMIT` (`src/rules/resource-type.ts`). A foreign related entry's id is deliberately **not** an `encodeAgentKey` value, so it can never collide with a primary agent key or be decoded as one.
- **Both degradation paths say so rather than failing quietly** — the shape this ticket exists to fix. A failed cross-rule fetch logs and falls back to the same-daemon set; **crossing `FOREIGN_FETCH_LIMIT` logs how many implementers will not be heard**, because the slice takes the first N of a *stable* key order every poll, so an overflow starves its tail indefinitely rather than deferring it to a later poll.

### Known gaps
- **BUTCHR-390** — when several rules match one heard ticket, the entry's id is the smallest agent key, which is arbitrary; the foreign path has the same problem in a second form (the id inherits the *listener's* provider). Unreachable until a fleet runs overlapping rules or providers sharing a link graph; **BUTCHR-383 (Features) is the likely first.**
- **BUTCHR-389** — the `[butchr:stall]` wake fires once per ticket and never again, so a parent whose blocker clears hours later is never re-woken. Separate defect; this PR does not address it.
