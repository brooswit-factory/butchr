### Added
- **Rule-launched agents (jira-work, jira-project, github-issue, github-pr, filesystem) can opt into "lizard mode" too: `permissionMode`/`lizardMode` on a `Rule` (`rules.json`).** Same field names, same semantics, and the SAME daemon-side permission-answer timer DROVR-42 shipped for managed-session definitions — no second timer, no second prompt parser. `permissionMode` (one of `default`/`acceptEdits`/`bypassPermissions`/`plan`/`auto`) is forwarded onto the spawn spec by every rule kind's `specFor*` builder and gets FACTORY-43's existing stale-argv safety for free (that plumbing was never managed-session-specific). `lizardMode: true` opts a rule's agents into the permission-answer timer's scan, resolved live from the already-loaded `rules` list (`ruleLizardModeOf`/`lizardModeLabelFor`, exported pure functions in `src/agents/permission-answer-loop.ts`, unit-tested independently of `src/daemon/index.ts`) rather than a second poll — a rule never sets a single fixed vendor the way a managed-session definition does, so unlike that field there is no Codex-vendor validation rejection; an agent that happens to land on Codex/Agy simply gets the same silent no-op an absent `permissionMode` already gives there. Absent fields mean today's behaviour exactly for every existing rule. See `docs/execution-modes.md`'s "`permissionMode` and `lizardMode`" section and `docs/permission-answer-loop.md`.
