### Fixed
- **`finish_without_a_boss` no longer lets an Epic in a project with its own project tier self-close with no review (BUTCHR-92/BUTCHR-326).** Its boss check previously read only the caller's `Implements` inward issue link — a Jira project is not an issue, so an epic's project-tier boss never showed up there, and the verb transitioned every epic straight to Done regardless of whether a project was watching it. Measured live: one daemon's journal recorded six epics self-closed this way since 2026-09-09 (SICKOS-10, BUTCHR-195, CNDLX-14, SICKOS-20, BUTCHR-216, BUTCHR-207), on a host that runs more than one daemon, so an undercount.
- A caller now HAS a boss if EITHER it carries an `Implements` inward link (today's check, unchanged, byte-identical message, still checked first, so a linked caller costs no extra Jira I/O) OR it is an **Epic** that is a member of an **eligible** project (`resolveEligibleProjects`, the same single resolver `list_peers`/`tell_peer` already use, called with no `preFilter` — eligibility is a Jira fact every daemon reads the same way, unlike the `BUTCHR_PROJECT_ALLOWLIST` rollout gate, which is deliberately never consulted here). The branch-(b) refusal names the project key and points at `submit_to_boss` — the project's own `finish_worker` is the exit BUTCHR-189's rule requires one to have.
- Gated on Epic specifically, not "any member of the project": `assertOwnWorker`'s existing project-caller branch already refuses a Story/Task target as not-an-Epic, so an ungated branch (b) would point a bossless Story/Task at a `submit_to_boss` → `finish_worker` path with no exit, stranding it In Review forever. The "member of this project AND an Epic" test is now one shared predicate (`isEpicMemberOfProject`) reused by both `assertOwnWorker`'s project branch and this new gate, so the two can never drift apart. A bossless Story/Task sharing an eligible project is a known, accepted, narrow gap this does not close — it keeps today's behaviour until `adopt_worker` gives it an `Implements` link.
- **Fails closed**: if the eligibility read throws (anything other than a clean not-found on the project's `butchr` property), the call refuses with a distinct message naming the underlying error, rather than ever treating "could not look" as "no boss".
- `briefs/epic.md`'s closing step, the tool's registered description (`src/tools/defs.ts`), and its own doc comment (`src/tools/relationship.ts`) are updated in this same PR so a deployed gate never refuses what a still-stale brief instructs.
